### 0.1 一句话目标

把 DWC 从“能进化”推进到“能用同一组事实证明：候选是否**更有效、是否更省钱、是否值得在指定预算下运行**”。

### 0.2 不是目标

- 不是把 HarnessPro 的九套 harness、提示词、五档画像或工具阈值复制进 DWC。

- 不是用 LLM 合成测试替代真实任务验收。
- 不是允许系统自主改评估器、放宽质量门或绕过人工主权。

## 1. 总体架构与不可交换的依赖

```text
论文与真实任务证据
        ↓
[1] 真实性能—成本测量
        ↓ 没有统一测量，不做双目标裁决
[2] 固定评价 + 基线保底 + Pareto 选择
        ↓
[3] 多 rollout 轨迹诊断
        ↓ 证据驱动，而非为了凑候选
[4] cost-first / balanced / performance-first 三意图候选
        ↓ 同一评价协议重新测量
[5] 任务级执行画像 + 运行时收敛
        ↓ 先 shadow，后受控应用
独立 held-out 验收 → 人类批准 → 备份、读回、台账、可回滚
```

**依赖不可交换：** ①是②的前置；②是自动筛选的前置；③④的候选必须回到①②复评；⑤只能在有对照证据后进入真实任务。不能先上三档画像，再补成本测量。

### 1.1 统一闭环

```text
轨迹事实 → 证据诊断 → 多意图候选 → 固定测试
       → 性能保底 / Pareto 过滤 → 多运行点保留
       → 独立验收 → 受控落地 → 可回滚
```

### 1.2 设计原则

1. **声称 = 实测**：每项计划必须带可复跑验收，不把设计写成进展。
2. **缺数据 ≠ 0**：缺 usage、价格、评价或 effect 时，显式 `not_reported / not_measured / undefined`。
3. **预测 ≠ 结果**：候选说明中的预期节省与最终测量分栏保存。
4. **父代继续参赛**：每轮子代不能仅凭“更新”就淘汰父代。
5. **固定评价先于候选比较**：不允许为迎合新候选而移动测试与判据。
6. **基础设施失败不冒充任务失败**：环境故障单独分类，已发生的成本仍保留。
7. **先影子后生产**：自动写生产配置必须晚于独立验证与人类批准。
8. **机制宁少勿滥**：能复用现有 loop/judge/replay/evo_targets/credit 的，不另造平行系统。

## 2. 当前基础与真实缺口

### 2.1 可复用基础

| 现有组件 | 可承担角色 | 不得误称为 |
|---|---|---|
| `harness/loop.py`、`scripts/dwc_evo_round.py` | 失败聚簇、提案、trial、落地与轮次 | 完整 HarnessPro 进化器 |
| `organs/judge.py` | 现有任务评价与失败签名 | 固定、充分的独立验收 |
| `harness/run_term.py` | term 轨迹、judge、成本快照与因果记录 | 完整 LLM 成本计量 |
| `organs/credit.py` | 编辑收益、成本、采纳归属 | 每次 LLM 调用的真实 usage 账 |
| `organs/evo_targets.py`、`evo_driver.py` | 白名单产物、备份、读回、回滚与有界调整 | 候选自由改代码的许可证 |
| `llm/client.py` | 可配置 reasoning effort、调用计数与降级状态 | 任务级画像选择器 |
| `llm/task_exec.py` | 15 轮上限、重复动作收敛与阶段提示 | 已验证的任务自适应预算 |
| `organs/effort.py` | 基于 gain 的预算调度纯函数 | 已接生产的调度器 |
| `organs/router.py` | 高效/浪费/失败/环境失败的路由 | 候选级 Pareto 选择器 |
| 记忆与 `effect_ablation` | 召回效果对照的雏形 | 记忆收益的因果证明 |

### 2.2 必须销掉的缺口

1. `CostLedger` 的抽象 `step_cost` 不能与真实 token、美元或延迟混用。
2. LLM provider usage 尚未形成覆盖成功、工具调用、流式/非流式、重试与辅助调用的统一任务账。
3. 当前候选 winner 选择不是 performance-cost Pareto 选择。
4. 现有失败签名不足以解释“成功了但钱花在哪”。
5. 固定轮数/重复次数护栏不等于按任务分配预算。
6. 合成测试、judge 与真实验收之间必须保留边界和独立反例。

## 3. 工作流 W1 · 真实性能—成本测量

**状态：PLANNED / FROZEN；优先级：最高；后续所有工作流的前置。**

### 3.1 目标

建立从每次模型调用到每次任务、每个候选的统一测量链，回答：

- 这个任务真的成功了吗？由哪个 evaluator/version 判定？
- 它花了多少输入、缓存输入、输出、推理 token？
- 调用了几次模型和工具、经历多少轮、耗时多久？
- 重试、fallback、judge、query expansion、诊断等辅助开销是否也被计入？
- 哪些数值是 provider 实测，哪些只是配置估算？

### 3.2 拟建对象（实现时定稿，当前不得当作已存在）

- `src/dwc/observability/task_metrics.py`：统一指标结构与校验。
- `src/dwc/observability/usage_pricing.py`：显式价格配置与成本估算。
- `var/task_metrics.jsonl`：append-only 任务测量台账。
- `config/pricing.json`：模型、价格来源、价格日期；无配置不猜价。
- `tests/test_task_metrics.py`、`tests/test_llm_usage.py`。

### 3.3 最小数据契约

```text
schema_version
task_id / term_id / candidate_id / parent_id / rollout_id
call_role                 # solver / judge / retry / fallback / expansion / diagnosis
pass / pass_rate / evaluator_id / evaluator_version
input_tokens / cached_input_tokens / output_tokens / reasoning_tokens
llm_calls / tool_calls / rounds / wall_time_ms
provider_cost_estimate / pricing_version
abstract_step_cost        # 保留现有语义，禁止与美元/token 相加
usage_status              # reported / partial / not_reported
measurement_status        # measured / invalid_candidate / infrastructure_error
evidence_ref              # 原始 session / response / trajectory 的可追溯引用
```

### 3.4 强制规则

- client 的成功、tool-call、流式与非流式路径都保留原始 usage。
- 重试和辅助模型调用必须归到发起它的 task/candidate，不能成为“免费开销”。
- 缺 usage 时 `usage_status=not_reported`，不能用 0 冒充零成本。
- 成本金额标 `estimate`，并记录价格来源和日期；无价格配置时只报 token。
- `CoP = total_cost / successful_tasks`；成功数为 0 时输出 `undefined`。
- 基础设施失败不得直接记为候选能力不足；测量失败与任务失败分栏。
- 既有 `abstract_step_cost` 保留，不破坏旧 replay/credit 口径。

### 3.5 验收门

1. 同一任务的每次 LLM 调用可从 task report 追到原始 session/response 证据。
2. 成功、tool-call、重试、fallback、usage 缺失各有确定测试。
3. 汇总值由明细计算，测试不允许手写一个无法追溯的总数。
4. 现有抽象成本口径不变，旧相关测试不因“统一账本”被偷换概念。
5. **此阶段禁止自动调参与生产应用。**

## 4. 工作流 W2 · 固定评价与双目标候选选择

**状态：PLANNED / FROZEN；依赖：W1。**

### 4.1 目标

将候选选择从“单一最高分”升级为：

> **同一固定协议 → 基线通过率保底 → 淘汰 Pareto 被支配者 → 保留有部署意义的多个运行点。**

### 4.2 选择协议

设候选 \(h\) 在固定验证集上的通过率为 \(PR(h)\)，平均成本为 \(C(h)\)：

1. `PR(h) < PR(h0)` 的候选不得因便宜而入选。
2. 若 \(h'\) 在性能和成本都不差于 \(h\)，且至少一项严格更好，则 \(h\) 被支配。
3. 父代与子代放在同一候选池评价，不因新旧而偏袒。
4. 从非支配集合选 lite/medium/heavy 代表；它们首先是**评价模式**，不是永久产品档位。
5. held-out 数据不得参与训练、过滤、权重选择或画像选择。

论文参考权重为 lite `(1,2)`、medium `(1,1)`、heavy `(2,1)`。**这些只作为 DWC 的待校准初值，不是已验证默认值。**

### 4.3 拟建对象

- `src/dwc/harness/pareto_select.py`：纯函数选择器。
- `src/dwc/harness/candidate_metrics.py`：候选评价记录与版本契约。
- `config/validation_protocol.json`：固定任务集、评价器版本、rollout 规则。
- `tests/test_pareto_select.py`、`tests/test_candidate_protocol.py`。

### 4.4 必须覆盖的边界

- 通过率或成本最大值等于最小值，归一化分母为 0。
- 同分候选、重复候选、父子同分、空集合。
- 候选评价缺 usage、评价中断、环境失败。
- 小样本通过率波动；不能只按一次 rollout 的微小差异宣布支配。
- 固定评价版本改变时，旧分数不能直接与新分数混合。

### 4.5 验收门

1. 构造已知候选集，单测确定基线过滤、Pareto 过滤、父代保留与三模式选择。
2. 所有边界行为显式、确定、可复跑，不能悄悄除零或随机挑一个。
3. 同一历史轨迹离线重放可重建同一前沿。
4. 独立 held-out 集从未进入选择路径，并有测试证明。
5. 结果明确标 `offline / shadow / production`，不得把离线结果称为真实收益。

## 5. 工作流 W3 · 多 rollout 轨迹诊断

**状态：PLANNED / FROZEN；依赖：W1；评价时使用 W2 的固定协议。**

### 5.1 目标

从“为什么失败”扩展到两个同等重要的问题：

- **失败是否稳定复现，根因证据在哪里？**
- **即使成功，哪些探索、工具调用、上下文与验证没有产生足够价值？**

### 5.2 诊断输入与输出

输入：同一任务在同一候选下的多次 rollout，关联的指标、工具调用、状态变化、输出和最终评价。

输出最小契约：

```text
problem_type             # correctness / waste / instability / infrastructure
frequency                # 出现 rollout 数 / 总 rollout 数
performance_impact
cost_impact
trajectory_refs[]        # 文件、事件区间、原始证据
first_effective_step
redundant_step_ranges[]
failure_signature        # 有则保留，无则显式缺席
confidence / unknowns    # 证据不足之处不得填满
```

### 5.3 诊断内容

- 同一失败是否跨 rollout 稳定出现。
- 哪些调用重复且没有新状态或新证据。
- 哪一步首次产生有效状态变化。
- 收尾、恢复、重复验证分别用了多少轮和 token。
- 与其他候选相比，哪处修改伴随什么测量变化。
- 环境失败与 harness 可修问题必须分桶。

### 5.4 约束

- 复用 `failure_sig`、`effect_ablation`、session 与现有 replay，不另造无来源的“诊断分”。
- 多次 rollout 的目标包括区分随机波动，不能将一次偶然成功当成稳定能力。
- 默认给规划者诊断摘要和证据引用，不必把整个长轨迹反复塞入上下文。
- 跨候选比较只能描述观察到的关联，不能直接声称单点因果。

### 5.5 验收门

1. 构造重复成功、稳定失败、随机波动、环境失败四类轨迹，分类正确。
2. 每条成本诊断都有事件级证据，不允许“看起来浪费”。
3. 能区分第一次有效步骤与后续无效重复。
4. 缺轨迹、缺 usage 时诊断显式降级，不生成虚构的成本归因。

## 6. 工作流 W4 · 三意图候选生成

**状态：PLANNED / FROZEN；依赖：W1–W3。**

### 6.1 目标

每个有证据的父代分别生成三类改进，而不是让同一提示词偶然决定优化方向：

| 意图 | 优先目标 | 不得牺牲 |
|---|---|---|
| `cost-first` | 去掉低价值探索、重复与冗余上下文 | 必要验证、基线性能、可恢复性 |
| `balanced` | 改善性能/成本前沿，而非机械平均两种方案 | 失败修复与无谓开销同时核算 |
| `performance-first` | 对有证据的失败增加有效推理、验证或恢复 | 不在所有任务上均匀加预算 |

### 6.2 候选计划契约

每份计划必须包含：

```text
parent_id / intent / diagnosis_refs
modified_component / change_description
expected_performance_effect / expected_cost_effect
regression_risks / preserved_behavior
validation_protocol / rollback_handle
predicted_vs_measured_status
```

- 候选可以来自现有 evolver、dream、参数驱动器或受控代码提案。
- 每个候选在独立 workspace/产物副本中形成，可比较、可撤销。
- 父代不自动退出；候选必须经 W1/W2 重测。
- 三意图是生成时的搜索方向，不保证一定会产出三个不同非支配结果。

### 6.3 禁止事项

- 禁止为了凑齐三类而复制同一改动、换名字。
- 禁止以“性能优先”为由跳过成本记录。
- 禁止以“成本优先”为由减少必要验证或隐藏未完成状态。
- 禁止候选修改固定评估器、held-out 数据或质量门。

### 6.4 验收门

1. 三类计划的输入证据、修改对象和风险均可审计。
2. 每份候选都有独立标识、父代、评价版本与回滚句柄。
3. 相同候选协议下与当前 DWC 比较 PR、C、CoP、L 及波动。
4. 阶段结束只产生 shadow 候选，**不自动 apply**。

## 7. 工作流 W5 · 任务级执行画像与运行时收敛

**状态：PLANNED / FROZEN；依赖：W1–W4 的 shadow 证据。**

### 7.1 目标

根据**当前任务可观察特征**分配推理与工具预算，让简单任务不过度探索，复杂任务保留必要验证；预算接近耗尽时优先形成最佳可用交付，而不是无期限继续。

### 7.2 初版画像（保守、少量、可审计）

| 画像 | 可观察条件 | 适用原则 |
|---|---|---|
| `lean` | 小范围、明确接口、可本地验证、至多两个主要不确定性 | 少探索，直接验证后收尾 |
| `standard` | 多文件/多接口、若干可行动不确定性，或条件不明 | **默认**；不因为“看起来难”升级 |
| `deep` | 确定性强 oracle、多个可区分假设、需要候选比较 | 多轮能产生新证据时才增加预算 |
| `research` | 多来源事实重建、版本/日期/出处核对 | 增加来源覆盖与交叉验证预算 |

画像包含：reasoning effort、提示阶段、工具/轮数上限、输出恢复方式、final 保留预算。

### 7.3 分阶段实施

1. **规则画像先行**：条件明确、默认 standard、理由落盘。
2. **shadow 评估**：画像只记录“会选什么”，不改变真实执行。
3. **小流量启用**：与默认路径同题对照，观察 PR、成本、CoP 和未完成率。
4. **模型分类器另行评审**：只有规则画像证明有价值后才考虑；分类器自身成本必须入账。
5. **无改善即撤回**：画像与结果无稳定关系，或分类成本高于节省，就不保留。

### 7.4 运行时收敛规则

- 阶段建议与硬性上限分开；不能把提示词当成已执行的预算约束。
- 接近上限时停止低价值探索，保留 final 和必要修复空间。
- 有具体失败、未完成交付或变异后的交付物时，不得仅因进入 convergence 阶段就假装完成。
- 长输出若压缩，原始内容必须可定点恢复；禁止不可逆地丢掉验证证据。
- 所有阈值是 DWC 待校准参数，**不得照抄 HarnessPro 的 14/26/44 等数字**。

### 7.5 验收门

1. 未知、错误和分类器不可用都回退 standard，并记录原因。
2. 简单任务不能靠减少必要检查换取账面节省。
3. 复杂任务的验证覆盖率不因画像而下降。
4. 超预算时能 best-effort 收尾，同时如实标未完成。
5. 先 inbox shadow，后小比例真实任务；生产配置写入沿用现有备份、读回、台账与回滚。

## 8. 测试、验收与部署纪律

### 8.1 五层验证

| 层 | 验证内容 | 通过条件 |
|---|---|---|
| 单元 | usage 汇总、指标缺省、Pareto 边界、画像回退 | 确定性测试全绿 |
| 历史重放 | 同一轨迹重建指标与候选前沿 | 可复现、口径不漂移 |
| 对照实验 | 当前 DWC vs shadow 候选 | 同任务、同预算、同评价协议 |
| 独立验收 | held-out 任务、人工反例、真实交付检查 | 无评价器泄漏，无隐藏失败 |
| 生产 Canary | 小流量、可观测、可回滚 | 人类批准，异常立即撤回 |

### 8.2 统一报告指标

必须同时报告：

- PR / pass（含 evaluator 版本）；
- 平均成本 C；
- Cost-of-Pass（成功为 0 时 undefined）；
- 延迟 L（辅助，不单独作为优化目标）；
- rollout 次数、波动和样本量；
- 无效候选、环境失败、usage 缺失比例；
- 预测值与实测值的差异。

### 8.3 部署禁止线

- 不得自动修改 evaluator、held-out、质量门或铁律。
- 不得把 shadow/offline 测量写成生产提升。
- 不得将抽象成本、token、美元混为一个数字。
- 不得让候选生成者单独决定自己的测试和验收。
- 不得未经批准进行整个代码库的自主编辑。
- 不得因某个候选“更便宜”而允许基线性能下降。

## 9. 论文积累期的计划变更协议

### 9.1 每篇新论文先做五项审计

1. **真值源**：成功/成本/效果由谁测量，是否可能是自报或共用盲点？
2. **代码证据**：公开的是方法、训练管线、产物还是仅说明文档？
3. **可迁移接口**：对应 DWC 哪个现有组件，是否已有同职责实现？
4. **冲突与增量**：与本计划五项是互补、重复还是矛盾？
5. **最小验证**：能否先离线/重放/shadow 验证，而不是直接上生产？

### 9.2 变更分级

| 类型 | 例子 | 处理 |
|---|---|---|
| 证据补充 | 新引用、风险、实验口径、论文限制 | 可记录到研究笔记，待实施前统一纳入 |
| 局部细化 | 数据字段、测试用例、诊断维度 | 不自动变更计划；随论文波次评审 |
| 范围变化 | 新增 W6、替换 Pareto、调整五档画像 | **必须用户确认** |
| 依赖/主权变化 | 先做画像后做测量、允许自动部署 | **必须用户明确批准** |

### 9.3 当前预留的论文增补位置

```text
PAPER_QUEUE / 待综合审计：
- 真实成本与 CoP 的评价协议
- 固定合成测试的可靠性与反例生成
- 多 rollout 轨迹压缩与失败/浪费归因
- 多目标候选选择、噪声与小样本判定
- 任务难度/不确定性画像与预算分配
- 与记忆、技能、RULES、prompt OTA 的协同或冲突
```

**在论文波次评审前，本计划五项的范围和顺序保持不变。**

## 10. 解冻与实施顺序

用户后续明确解冻后，按以下顺序执行，不并行跳过依赖：

1. **W1 测量闭环**：只观测，不调参。
2. **W2 离线双目标评估器**：历史重放与单测，不宣称收益。
3. **W3 多 rollout 诊断**：先证据面，后诊断摘要。
4. **W4 三意图 shadow 候选**：同题对照，不自动应用。
5. **W5 执行画像与运行时收敛**：先 shadow，再小流量，再决定是否自动化。
6. **独立验收后受控落地**：复用现有 `evo_targets` 备份、读回、台账与回滚。

每个工作流完成后必须重新跑相关测试、全量测试与 `gate.py`，并报告真实执行结果；不得沿用计划中的预测作为验收。

## 11. 明确不引入清单

- HarnessPro 九套 benchmark 专用 harness 与任务指令。
- 14/26/44 等工具阈值和五档分类体系的机械复制。
- Linux x86-64 RTK 二进制作为当前 Windows 主机的默认依赖。
- “低推理 = 更好”“少工具 = 更好”“通过合成测试 = 真实完成”。
- 以多目标为名另造与现有 evolver、judge、credit 平行的重复系统。
- 未经验证的模型分类器、自动画像调整或生产自动部署。

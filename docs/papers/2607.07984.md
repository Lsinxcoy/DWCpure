# Agentic Neural Architecture Search（AgentNAS）：LLM 负责造搜索空间，常规 NAS 负责搜

- 版本：`arXiv:2607.07984v1 [cs.AI] 8 Jul 2026`；作者 Seokhoon Jeong、Mijung Kim、Taehwan Kim（UNIST 人工智能研究生院）；代码 `https://github.com/alroimfebruary/AgentNAS`（Abstract 自报，**仓库可访问性未核**）。

## 一句话总结

把「谁来定搜索空间」与「谁来搜」拆成三段可分别消融的流水线：Phase 1 让 LLM 在 160 次评估预算内搜出 seed 架构 + 训练配方（Planner–Code Generator–Explorer 循环），Phase 2 让 LLM 把 seed 分解成带名字、可互换槽位的 **slotted architecture**（模块级槽 + 加法胶水槽 + 学习率虚拟槽，硬上限 20 槽 × 8 备选），从而**免人工**得到一个有界、任务专属的搜索空间，Phase 3 交给常规 NAS（默认 regularized evolution）在槽位间做组合式重搜；17 个任务上 **11 个 SOTA**（NAS-Bench-360 8/10、Unseen NAS 3/7），Unseen NAS 平均误差 13.06% vs 最强基线 15.04%。分工结论是**互补而非取代**——LLM seed 单独已打平/超过多数已发表基线，NAS 在 LLM 饱和之后再加一层组合重排；**但 Appendix A.4 的三种子数据我逐格算过：把 seed 42/43/44 平均后，NAS(P3) 只在 6 个消融任务中的 3 个优于 seed(P1)，另 3 个反而更差**，而主表 Table 1/2 恰好等于 seed 42 那一列（12/12 格我对上了）。

## 核心方法（细颗粒度）

### 0. 问题定性（论文自陈的缺口，§1/§2）

- 搜索空间是人手工设计的瓶颈：「every method still presupposes a hand-engineered search space that demands domain expertise and must be rebuilt for each new task」（§1）；CFG 类方法「ultimately shift the manual engineering burden from architecture design to grammar design」（§2.1）。
- 现有 LLM-NAS 工作把两件事混在一起：「all of these approaches conflate two distinct roles—expanding the space of possible architectures and exploring it」（§1），于是「can an LLM replace NAS?」和「what is the optimal division of labor between LLMs and NAS?」两个问题都无法回答。
- 论文声称的空位（§2.2 收尾）：「no prior work uses the LLM to construct a bounded, task-specific search space that is then handed off to a conventional NAS algorithm」。
- 关键洞察（§1）：分解要「preserves the LLM's macro-structural decisions (depth, width progression, backbone type) while exposing combinatorial degrees of freedom at the module level, precisely where NAS is most effective」。

### 1. Phase 1：LLM 驱动的 seed 搜索（§3.1 + Appendix A.7.2/A.8.1）

- 三动作 Planner 状态机：`<EXPLORE>`（起一个 Data Explorer 子 agent 在沙箱里写代码看数据）、`<EXPERIMENT>`（提候选并评估）、`<STOP>`（给 `<FINAL_SELECTION>` 结束）。
- **预算**：原文 `max evaluations= 160`；`patience= 64` 次**连续成功但无改进**的评估才停。
- **不对称计数规则**（Appendix A.7.2 逐字）：失败评估（rejected/oom/error/timeout）**消耗 160 预算但不增 patience**；理由原文：「The motivation is asymmetric: the budget protects against runaway compute, while patience protects against runaway wall-clock with no metric movement」。
- **代理训练**：`proxy epoch fraction= 0.3`（原文 `proxy epochs= max(1,round(0.3·E full))`，文本层把 `E_full` 抽成 `E full`），warmup/cosine/step/plateau 的时间参数同倍缩放并 floor 到 1；另加 **3600 s GPU 时间硬上限**（用 CUDA event 配对计时，**排除**数据加载与评估时间，避免慢盘惩罚架构）；VRAM 上限 `max vram mb= 11,264`（RTX 2080 Ti 11 GB），`torch.cuda.max memory allocated`（原文此处有缺空格抽取瑕疵）按 epoch 采样，OOM 报 `status="oom"`。
- **终训两波**（`top k final= 8`，正好占满 8 卡）：Wave 1 全 epoch、留出 val 选 best checkpoint（**下游一切决策只用 Wave 1 指标**）；Wave 2 在 train+val 合集从头训、用 last checkpoint、held-out test 只评一次（**Wave 2 才是论文主表的 test 列**）；两波共用 `final time limit s= 86,400`（24 h GPU 时间）。
- 每批后 `state.json` 落盘（pod 重启可断点续跑）。
- 上下文管理（A.8）：五个 agent（Planner / Data Explorer / Code Executor / Modularizer / Slotted Architecture Planner），Planner 提示里硬写「NO pre-trained weights. All models trained from scratch.」以及**训练配方白名单**（optimizer ∈ sgd|adam|adamw、scheduler ∈ cosine|step|warmup_cosine|plateau|none、增广 ∈ mixup|cutmix|random_erasing；**AMP/fp16/bf16、torch.compile、梯度累积一律不支持，超白名单字段被静默丢弃**）。
- Data Explorer 的反幻觉规则逐字：「NEVER fabricate "**Execution output:**" or any output block in your own message — outputs come back to you in the NEXT user turn.」「Do NOT produce <REPORT> until you have actually executed at least one ```python``` block and observed real output.」

### 2. Phase 2：slotted 架构合成（§3.2 + A.7.1 + A.8.4/A.8.5）

- **Slot Planner** 输入 = seed 源码 + 训练配方 + Data Explorer 报告，输出 = `scaffold_code`（把可搜组件换成 `SLOT_xxx()` 调用）+ `slots` 定义（JSON）。
- **两类槽**：
  - *Module-level slots*：整块替换（`nn.Module` 粒度的粗粒度、内部自洽变换），"while preserving the internal coherence of each block"（前半句因断词被抽成 `mutates the seed byre- placingcomponents`，我不改写原文瑕疵）。
  - *Additive glue slots*：夹在模块之间、作用于模块输出，**默认 Identity**（"the seed's behavior is preserved unless NAS actively selects an alternative"），用于让 NAS 加额外算子/激活/跳连而不动邻接模块内部。
- **学习率虚拟槽**：µ ∈ {0.25, 0.5, 1.0, 2.0, 4.0}（因为模块替换会改参数量，seed 的最优 LR 会失效）。
- **为什么不做"每个算子一个槽"**：原文「this enlarges the search space excessively (up to∼1090 configurations in our preliminary experiment)」——即 ~10^90（文本层丢了 `^`）。
- **硬上限**：原文 `is instructed to produce exactly max slots= 20 slots, each with up tomax alternatives per slot= 8 alternatives`（`upto` 是文本层缺空格）；超限在**解析后**按声明顺序截断/截断备选表，**不重发 prompt**（理由：Slotted Architecture Planner 是 single-call agent，重发等于整段 Phase 2 重跑）。
- **Modularizer Agent**（Phase 1.5）：当 seed 是 block-stack 模式时，先把重复 stage 包成独立 `nn.Module`，硬约束逐条写在提示里——「No parameter add/remove. sum(p.numel()) must match exactly.」「No op-type changes (no ReLU<->GELU, BN<->LN, Conv<->DWConv, etc.)」「Forward-pass behavior must be IDENTICAL to the original (bit-equivalent under torch.allclose(rtol=1e-5, atol=1e-6) ...)」，失败重试上限 5 次。**不做这步的后果有实测**（Table 14，见主结果）。
- Slot Planner 提示要求「Define 10-20 fine-grained slots」、每个槽 4–8 备选且**必含 seed 选项、领域新算子、标准算子、Identity 与 Zero**（「Include identity AND zero for EVERY slot」——让 NAS 能证明某组件没必要）。

### 3. Phase 3：slotted NAS（§3.3 + A.3 + A.7.2）

- 默认 **regularized evolution**；附录另测 random search 与 GDAS（GDAS 因连续松弛不兼容而**剔除学习率虚拟槽**）。
- 种群初始化（16 个个体）：seed 1 个（备选与 seed 全同）+ ⌊(16−1)/3⌋=5 个**单槽变异** + 5 个**双槽变异** + 5 个均匀随机；随机搜索消融则改成 16 个 i.i.d. 均匀样本。
- 进化参数：`tournament size= 5`、50/50 单/双槽变异、`max generations= 10`（初始种群 + 9 波子代）→ 软上界 160 次评估，与预算天花板对齐；**实际常常 patience 先触发**。
- 预算/patience 与 Phase 1 相同（160 / 64，独立计数）。
- 候选训练协议与 Phase 1 完全一致；搜完后 top-8 走同款两波终训。

### 4. 验收规则 / 实验协议（§4.1–4.3）

- **选择规则 = non-seed best**（原文作 `anon-seedbest selection rule`，抽取缺空格）：跨 Phase 1 与 Phase 3 取验证指标最好的架构报其 test 分；种群里含 seed，所以若 NAS 从不改进，**输出就是 seed**——为揭穿这种空转，原文「To unmask such a null-NAS scenario, we report the second-best architecture's score in this case.」
- **test 永不进入流水线**：「Only validation metrics are used for selection; test metrics are never exposed to the pipeline.」
- **LLM 与提示跨 17 任务零调参**：所有 LLM 角色用 Claude Sonnet 4.6、temperature 0.7、各自独立上下文窗口，「The same model and prompt templates are used across all 17 tasks without per-task tuning.」消融另用 Claude Haiku 4.5 与 Claude Opus 4.6。
- 硬件：单卡 RTX 2080 Ti（11 GB），整套 pipeline 用 8× RTX 2080 Ti。
- **盲测设置**（Unseen NAS 复刻原竞赛协议）：任务 README 换成合成最小 spec（输入 shape、类别数/输出 shape、loss 名、指标方向），占位名 `TASK_X`，并把这个标签传播到 Code Executor 与 Slotted Architecture Planner 系统提示；「The benchmark loader and the labels themselves are unchanged—blind mode only affects what the LLM agents can read, not what the harness trains on.」
- **基线取数**：NAS-Bench-360 四类（WideResNet-16-4 / GAEA DARTS / benchmark 提供的任务专家架构 / einspace RE from WRN），前三者取自官方 NAS-Bench-360 评测、einspace 取自其论文；Unseen NAS 三类（ResNet-18 / 六种常规 NAS 的逐任务最优 / einspace 全变体的逐任务最优），同理取自官方与 einspace 论文。**注意**：基线是**转引**来的数字，非本篇重跑。

**其余主结果（正文/图）**

- 预算—性能轨迹（§5.2, Fig 3）：LLM 采样在 480 预算内普遍饱和（三模型皆然），NAS 在饱和点之后继续改进；Spherical 上三模型都 160 饱和而 Sonnet 的 NAS 继续涨；Language 上「Sonnet benefits from both mechanisms simultaneously, with LLM-320+NAS slightly outperforming LLM-480」；边缘情形：CIFARTile 上 Opus 在 160 已很强，两者都不再涨；Darcy Flow 上「Sonnet saturates early and NAS fails to improve, whereas Opus benefits from both」，归因到搜索空间质量：Sonnet 的空间把 seed 的 einsum 谱卷积**保留在所有备选里**，「leaving NAS with no meaningful variation in the spectral layers」，而 Opus 提供了逐通道频谱滤波的分解备选。
- 三个案例的"NAS 改了什么"（§5.3）：Chesseract = **功能补偿**（缺 gating 就补 ReZero/sigmoid/GLU/SwiGLU，已有就重组到 merge 点；给全局 Transformer 补 depthwise 3×3 做局部混合，但**不给局部 CNN 加全局注意力**）；CIFARTile = **一致的通道重标定**（补 SE，或叠 Coordinate Attention/ECA），归纳为「if absent, add it; if present, diversify it」；Darcy Flow = **搜索空间质量决定成败**。
- 效率（Appendix A.1，Table 4–7）：Unseen NAS 上 Ours(P1+P3) wall-clock 7–116 h（CIFARTile 最贵 116 h），GPU time 26–367 h；参数量普遍小于 einspace（如 AddNIST 6M vs 20M、Chesseract 2M vs 11M），但 NAS-Bench-360 上比 GAEA/Expert 大得多（CIFAR-100 23.4M vs 4.9M；Satellite 67.3M vs 3.4M），且 **Phase 3 常把参数量压回去**（Spherical 19.7M→15.4M；Satellite 67.3M→54.7M）；FLOPs 上 10 个 NAS-Bench-360 任务中 6 个低于 GAEA。原文明说「AgentNAS is more expensive than supernet-based methods such as GAEA」。
- 训练配方（Table 8）：LLM 逐数据集搜配方，与 einspace 的单一固定配方对比；**8/17 个数据集上 NAS 改了学习率**（表中带 `→`，如 Spherical 0.001→0.004、ECG 0.001→2.5×10⁻⁴、Deepsea 3×10⁻⁴→1.2×10⁻³）——这是"学习率虚拟槽确实被用上"的直接证据。
- 随机种子（§5.2）：三种子下「all seeds remaining competitive against published baselines」（结论按"仍具竞争力"表述，非"仍 SOTA"）。

## 与 DWC 的映射（机制 | DWC 现状 | 判定）

| AgentNAS 机制 | DWC 现状（代码级） | 判定 |
|---|---|---|
| **Phase 2：LLM 把 seed 分解成带槽搜索空间**（免人工、任务专属、有界 20×8） | `organs/candidates.py::CandidateGenerator` 是**trace-grounded 确定性生成**：模块头自陈「DWC src 实测 grep 零 LLM 接入 ⇒ 第一版只能是确定性退化形态」，纪律③ 是「推不出 ⇒ 返回 `need_llm=True` + 原因」；`_llm_generate`（375 行）在但默认不走 | **缺（结构在、生成那一半未启用）**：DWC 有"从证据推出候选"的面（R1 range 边界、R2 类型不匹配两条规则），但没有"LLM 主动构造候选空间"的环节；落点 = 把 `_llm_generate` 接上并让 `need_llm` 触发真实调用 |

## 综述 L 定位

- **L2（Improvement Strategy Autonomy）· Model and Training Search · (2) Architecture Search**。综述 §3.3.3 逐字收编：「AgentNAS starts from the observation that modern NAS still depends on manually engineered, task-specific search spaces. It uses an LLM to produce a task-specific seed architecture and then derives a structured search space from that design for subsequent combinatorial search」（`Jeong et al. [2026]`）。
- **综述 §1.1（Scaling Burdens in Model Development）**的定性更值得记：「AgentNAS addresses part of this bottleneck by using an LLM to propose a task-specific seed architecture and construct its search space, **but candidate selection still depends on combinatorial search under an externally specified objective**」——综述特意保留了"目标仍是外部指定"这半句，正是 L2 与 L3/L5 的分界（「L2 autonomy concerns the search for a better system configuration; it does not imply authority to redefine what constitutes successful performance」）。
- **技术族**：综述 **Table 4**（L2 代表系统的四列表）中的一行，逐字为 `AgentNAS | Architecture search | LLM-generated task-specific seed architecture + derived structured search space | Fixed validation metric`。同表的邻行是 `AutoKernel | Kernel experiment | Profile–rewrite–benchmark loop | Fixed correctness + speed`（f=5 那篇），两篇同族不同行——**族位是"Architecture Search"，外部固定项是"验证指标"**。
- **structural / effective（用综述 §3.6 的 L5 判据类推本篇，本篇本身不在 L5 表内）**：
  - *structural*：**有**——Phase 1 的 seed 与配方是 Phase 2 的输入、Phase 2 的 slotted 结构是 Phase 3 的搜索空间，产物跨阶段持久并控制后续一轮；验收准则外置（`Fixed validation metric`，test 永不进流水线）。满足综述 §3.6 原文 "an AI-directed change persists and controls a later improvement round" 的结构要件。
  - *effective*：**部分有、且比正文口径弱**——(a) 有对照：Table 3 的"同 seed、只换空间"证明 LLM 空间优于 einspace 语法空间（Spherical 53.51 vs 66.37、CIFARTile 21.99 vs 39.35，160 vs 500 evals，这是全篇最干净的 effective 证据，但只有 2 个任务）；(b) 反证：Table 10 三种子均值下"NAS 在 seed 之上再涨"只成立 3/6；(c) 综述 §1.1 的 "but candidate selection still depends on combinatorial search under an externally specified objective" 意味着综述并未把它当作"改进机制被改进"的证据使用。
- **与综述 Table 8（L5 评估六维）无关**：本篇不测"改进机制被继承"，只测单批任务的性能。

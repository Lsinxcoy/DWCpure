## 1 · 机制清单

| # | 机制名 | 一句话描述 | 出处 |
|---|---|---|---|
| M1 | **Drop** | 把选中的 KV cache 从后续注意力中排除，**不改轨迹文本** | §3.3 |
| M2 | **Repos（Reposition）** | 用 RoPE 旋转调整保留 key 的位置编码，压缩位置索引，**不 re-prefill** | §3.3 |
| M3 | **策略三元组** | `trigger`（何时）/ `selector`（丢哪些）/ `reposition`（何时压缩位置） | `agent/policy.py:26-40` |
| M4 | **历史依赖** | 同一 token 序列在不同 cache 操作序列下产生不同 cache 状态 ⇒ **前缀匹配不足以正确复用** | §3.4 |
| M5 | **cache 策略的 RSI** | 用 LLM 迭代改进 cache 策略，第 3/6 轮相对 Standard 降本 15.6% / 17.8% | §5.4 / Fig.4 |
| M6 | **Cache-as-Tool（CAT）** | 把"丢哪些 cache"暴露成一个工具，让 agent 自己决定 | §5.4 / Table 4 |
| M7 | **token 记账三元组** | `cached_tokens` / `drop_skipped_tokens` / `repos_tokens`（`usage.prompt_tokens_details`） | README |
| M8 | **位置索引与逻辑索引解耦** | 位置编码不再随逻辑轨迹增长，否则小 cache 也会撞模型上限 | §3.2 |

## 8 · 关键数字

### 8.1 三种上下文管理的对比（GPT-OSS-120B，前 100 个 BCP 任务）

| 方法 | 相对成本 | 精度 |
|---|---|---|
| 全上下文（基线） | 1.00× | 基线 |
| **Trim**（只留最近 12 轮工具响应） | **1.85×** | — |
| **Summary**（48K 阈值） | −7% | **−5pp** |
| **AKV（rolling drop）** | **更低** | **更高** |

> Trim 反而贵 1.85 倍 —— 因为改动前缀导致 retained context 必须重新 prefill。
> 这是整篇最反直觉、也最有用的一条。

### 8.2 主结果（平均）

| 对比 | 成功率 | 成本 |
|---|---|---|
| vs Standard | +1.3 ~ +2.1% | **−27.7%** |
| vs Text Engineering | +0.9 ~ +8.7% | **−21.9%** |

GPT-OSS-120B / BCP：**61.9 vs 57.5**（Standard），成本 11.4 vs 13.1 美分。

### 8.3 服务性能（GPT-OSS-120B，峰值并发）

| 指标 | 提升 |
|---|---|
| 平均延迟 | **1.36×** |
| P95 延迟 | **1.51×** |
| 输入吞吐 | 1.53× |
| 输出吞吐 | 1.18× |

### 8.4 消融

| 配置 | BCP | SWE |
|---|---|---|
| Standard | 56.0 / 13.5¢ | 41.0 / 19.1¢ |
| Tool drop | 55.0 / 7.1¢ | 41.0 / 9.4¢ |
| Tool drop + repos | **56.5 / 8.2¢** | 36.5 / 14.2¢ |
| Reasoning drop + repos | 56.5 / 8.7¢ | 34.5 / 7.8¢ |
| Both drop + repos | **62.0 / 10.9¢** | 41.0 / 9.5¢ |

**repos 单独把 BCP 从 55% 拉到 62%** —— 因为不压缩位置索引就会撞模型上限、直接停摆。

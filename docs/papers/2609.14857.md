## 1. 问题

### 论文自己承认的缺口

ModularRSI 的问题陈述写得比 RRSI 更工程化——它不是"过拟合"，而是**三个耦合挑战，每个都锚在不同的粒度上**（§1 原文逐条）：

**(1) 数据级：拿不到高质量的演化经验。**
"Harness RSI requires executable long-horizon terminal tasks with reliable environments and correctness feedback, but **constructing such an evolution dataset at sufficient scale and diversity is costly and difficult**."
即使有人自动生成终端相关实例，"ensuring their environment completeness, task validity, and evaluator reliability **at scale** remains challenging"。
**后果（这句是全文的立论基础）**："existing Harness RSI methods typically rely on data from downstream benchmarks for evolution … which makes it difficult to determine whether the evolved harness captures generalizable improvements or **merely adapts to benchmark-specific patterns**."

**(2) 轨迹级：不知道该改什么。**
"Individual or one-sided execution trajectories **entangle systematic harness deficiencies with task-specific reasoning and solution details**."
从单侧证据（只看失败轨迹，或只看一条轨迹）优化，"may therefore introduce task-specific behaviors that transfer poorly to unseen tasks"。

**(3) 机制级：即使知道该改什么，不知道改哪个组件。**
"even when a recurring behavioral deficiency is identified, **it remains unclear which harness component should be modified**."
论文明确点名了现有做法的问题：即使有工作做局部诊断与修复（Chen et al. 2026a = HarnessFix），"many approaches still optimize or rewrite large portions of the harness … This large modification space can **entangle unrelated mechanisms**, making targeted and reliable evolution difficult."

**论文的自陈缺口总结（Table 1 之后的原文）**："To address these limitations, we construct a **benchmark-disjoint evolution dataset** and propose ModularRSI, which **decomposes the harness into functional modules** and performs self-evolution through **contrastive trajectory analysis**."

### §7 Limitations and Conclusion 原文（全文唯一的局限章节，两条）

1. "we **do not conduct a dedicated ablation that isolates the contribution of contrastive trajectory analysis**, although our trajectory analysis and case studies provide supporting evidence."
2. "due to computational cost, our main evolution experiments use **only a subset of the 2,000 curated evolution instances**. We leave broader comparisons and larger-scale studies to future work."

**注意第 1 条的严重性**：ModularRSI 的三个卖点里有两个（contrastive、modular）——modular 有 Table 4/5 的直接消融，**但 contrastive 没有**。而 contrastive 恰恰是它相对其他所有 harness 方法的原创点之一。**论文用 §6.5 的"contrastive pair 比例随演化下降"（Figure 3）与三个案例来替代消融，这不是因果证据。**

## 2. 核心机制

### 2.1 三阶段总览（§3.1）

ModularRSI 由三阶段构成：

1. **Contrastive Trajectory Sampling and Analysis** — 从成功与失败执行中识别反复出现的 harness 弱点
2. **Module-wise Harness Evolution** — 把这些发现转成局部化的函数级更新
3. **Validation Gates** — 用程序检查、泛化导向的 diff 审查、执行验证来过滤提案

**关键的架构决策（全文强调）**："During module-wise evolution, the modules are evolved **independently without sharing intermediate updates**, allowing them to be processed in parallel." 五个模块从同一个初始 harness 各自独立演化 3 个 epoch，最后才做 **Cross-Module Integration**。

**另一个关键决策**："The agent under evolution itself serves as the **Code-Modify Agent** for both trajectory analysis and harness modification." ← 这是一个**同源**设计（被改的对象与改它的 agent 是同一个），论文不认为这是问题。**这个选择有代价，见 §5.2 与 §6.4。**

### 2.2 五个功能模块（§3.2 + Appendix A）

论文的划分原则：harness 里的"基础设施级组件"（sandbox 初始化、并行执行、LLM 通信）"mainly concern system infrastructure rather than task-solving behavior"，**因此被排除在演化范围外**。只演化"mechanisms that directly mediate agent–environment interaction"。

| 模块 | 职责（论文原文） | Protocol 签名（Appendix A.1 Listing 1） |
|---|---|---|
| **1. Agent Loop** | "Controls the iterative reasoning–action–observation process, including execution flow, interaction control, and recovery behavior." | `AgentLoop.run(initial_prompt, original_instruction, observation, context_mgmt, tools, verification, chat, ctx) -> AgentLoopResult` |
| **2. Observation Management** | "Processes environmental feedback by preserving task-relevant information while filtering or compressing noisy observations." | `Observation.capture(prev: ObsState, ctx) -> tuple[ObsResult, ObsState]` |
| **3. Tool Use** | "Manages the selection, invocation, and validation of external tools." | `ToolSet.parse_llm_response(response) -> LLMResponseParseResult`；`ToolSet.execute(call: ToolCall, ctx) -> ToolResult` |
| **4. Context Management** | "Maintains and organizes interaction history across execution steps, including information retention, compression, and retrieval." | `ContextMgmt.maybe_compress(chat, original_instruction, ctx) -> CompressResult`；`ContextMgmt.force_summarize(...) -> CompressResult` |
| **5. Task Completion Detection** | "Determines whether the task has been completed or further interaction is required." | `VerificationLoop.should_terminate(state: AgentLoopState, ctx) -> tuple[bool, str]` |

**交互关系的精确表述（Appendix A 原文，值得抄）**：
- "The outer box is Agent Loop, and the central Loop control box represents its runtime logic: maintaining execution state, scheduling calls, handling retries, and deciding whether to continue."
- "Before execution, **the composer selects one implementation for each module**."
- "The completion detector **returns a recommendation**; Agent Loop maintains the state and controls whether execution continues."
- "Observation Management returns **current environment feedback**, whereas Context Management updates the **accumulated conversation history**." ← 这两个模块的分工边界是论文特意澄清的（因为名字极易混淆）。

初始 harness 是 **Terminus-2 from Harbor**，"reorganize its behavioral mechanisms into these five modules"。

### 2.3 对比式轨迹采样与分析（§3.3，式 1）——本文最原创的机制

对每个演化实例 `x_i`，roll out K 次得到 `(tra_i^1, …, tra_i^K)`，每条由任务自带 evaluator 给二元奖励 `r_i^k ∈ {0,1}`。**按奖励三分**：

```
𝒢_i = Positive     ,  Σ_k r_i^k = K      （全成功）
      Contrastive  ,  0 < Σ_k r_i^k < K   （有成功也有失败）
      Negative     ,  Σ_k r_i^k = 0      （全失败）                        (式 1)
```

**Trajectory Memory** 机制：跨演化 epoch 存储每个任务的历史轨迹与奖励，"This allows experience from previous epochs to provide additional contrastive evidence when the current rollouts alone are insufficient."

**三组的不同分析路径（这是全文最值得抄的设计）**：
- **Contrastive 组**：同任务的成功与失败轨迹**配对比较**，识别与不同结果相关的 function-level 因素。
- **Negative 组**（全失败）：**先查 Trajectory Memory** 找该任务此前成功的轨迹。若存在，配对做对比分析；若不存在，退化为单侧诊断，识别"repetitive loops, incorrect tool usage, ineffective recovery, or premature termination"。
- **Positive 组**（全成功）：分析**质量与效率**机会——"redundant actions, repetitive exploration, or unnecessary tool calls"。

**为什么 Positive 组也要分析**（论文的隐含论证）：全成功意味着任务已解，但执行路径可能冗余。**这是把"效率"而非只"正确性"当优化目标**——与 RRSI 的成本门呼应（见 §6.4）。

**实现的路由桶细化（Appendix B，Table 8）**——把三组拆成 7 个桶：

| 方法级分组 | 实现桶 |
|---|---|
| Positive | `all_pass_efficient`, `all_pass_wasteful` |
| Contrastive | `mixed` |
| Negative | `fixable_fail`, `stuck_fail`, `unreachable_fail` |
| **Excluded** | **`infra_only`** |

"The buckets select an analysis path. **They do not change the reward of a trajectory.**" 且 "Tasks with infrastructure-only failures are **excluded from harness diagnosis**." ← **这一条是 DWC 最该抄的单点机制**：把基础设施故障从"agent 能力不足"里摘出去，否则演化会试图用 harness 改动去修环境 bug。

**结构化 finding 记录（Appendix B 的 schema，字段名逐一可抄）**：
```
task                  标识任务
lens                  分析模式
locked_module         本轮允许被修改的模块（硬边界）
is_culprit            因果判定（true/false）
divergence            相关轨迹证据摘要
would_change_outcome  反事实判断："提议的模块改动是否可能改变任务结果？"
fixable_now           系统现在能否据此行动
suggested_change      具体改动建议
other_module / note   负向归因时的替代解释
parse_status          结构化输出是否解析成功
```

**论文特意展示了两种记录**（Listing 2）：第一条 `is_culprit: true`，`divergence` = "The passing roll ran build and package commands. The failing roll ran no build or validation command and repeatedly declared completion."，`would_change_outcome` = "Yes. A completion gate that requires validation evidence would force the missing build-and-check stage."，`fixable_now: true`。
**第二条 `is_culprit: false`** —— "The second finding **abstains from an unsupported edit**." ← **"弃权"是一等输出**，这个设计比"每次都必须给个建议"更稳健。

### 2.4 模块级 harness 改动（§3.4）

两个提升改动可靠性的机制：

**(1) Modification Target Selection（改动目标选择）**
"For each batch, we first **consolidate semantically similar diagnoses that target the same function** into candidate modifications. Each candidate is then assigned a **vote count based on the number of distinct tasks that provide supporting evidence**."
→ **跨任务证据聚合**：一个候选改动的支持度 = 有多少个**不同任务**提供了支持证据。论文的用意："favoring modifications supported across multiple tasks while **reducing the influence of instance-specific failures**"。
**注意这是硬编码在 prompt 里的排序偏好（Appendix C.2 的 `SUPPORTING_FINDINGS` 字段），不是一个显式的算法步骤。**

**(2) Evolution History（演化历史）**
为每个被改的函数维护历史，记录"previous code changes and the functionality introduced by each revision"。把它暴露给 Code-Modify Agent，"subsequent updates can better preserve previously evolved functionality while **avoiding repeated or contradictory modifications**"。
→ **目标是抑制"演化振荡"（oscillation）**，机制是"已引入的功能列表"作为约束上下文。

### 2.5 三道验证门（§3.5）——本报告认为最值得抄的一节

**(1) Program Check（程序检查，纯静态）**
"A series of static checks on the modified harness, including:
- **AST validation**
- **import checks**
- **protocol compliance**（协议合规：改动后的实现是否仍满足该模块的 Protocol 签名）
- **discovery-contract verification**（发现契约：该实现是否仍能被组合器发现 / 注册）
- **static self-attribute audits**（静态自属性审计）

If a modification fails any of these checks, we use the **recorded diffs to roll back the affected function to its previous version**."
← **回滚靠的是 diff 记录，不是 git**（因为 function-level 回滚要精确到函数粒度）。

**(2) Diff Review（diff 审查，防任务特定化）**
"we ask the Code-Modify Agent to review each modification diff. The agent checks whether the introduced changes **encode task-specific solutions, heuristics, or conditions that are unlikely to generalize** beyond the current training instances."
被判定为过度任务特定的改动**直接拒绝并回滚**。
→ 这一门与 RRSI 的 Leakage Screening 是同一意图，**但执行者是同源 agent**（见 §5.2）。

**(3) Execution Validation（执行验证）**
"After each modification, we **randomly sample two tasks from the current batch** and execute them using the updated harness. If the modification introduces **runtime errors or violates the expected execution protocol**, we use the recorded diffs to roll back."
← **样本量只有 2 个任务**，论文未报告这个数字的选择理由，也未报告因此漏过多少次坏改动。

### 2.6 Cross-Module Integration（§3.6）

五个模块独立演化后合并。"Since independently optimized modules may introduce **duplicated mechanisms, conflicting behaviors, or inconsistent interactions** when composed together, direct combination may not produce a coherent final system."

整合 epoch 的具体步骤：整合后的 harness 在演化任务上跑 → Code-Modify Agent 分析轨迹找**跨模块冲突** → 精炼模块交互（"removing duplicated mechanisms, clarifying module responsibilities, and adjusting coordination logic"）。
**"After integration, the evolved function library is frozen and no further modifications are allowed during downstream evaluation."** ← 冻结纪律，DWC 必须抄。

### 2.7 Function Library Management（§3.7）——两机制的分工很清楚

函数库是**扩张的**（"an expanding library of evolved functions"），但用两个机制控制复杂度：

**(1) Function Merge（函数合并）**
在模块内，用 LLM 比较函数描述与行为，合并 "highly similar or overlapping functionality" 的函数，"reducing redundancy **while preserving their learned capabilities**"。

**(2) Task-Aware Function Composition（任务感知函数组合）**
每个演化出的函数带一个自然语言描述当前行为的说明。执行前：给 LLM 任务描述 + 所有候选函数描述 → LLM **选出一个任务相关的子集** → 只有这些函数被激活。
**关键**："Those mechanisms are used during **both trajectory collection and downstream evaluation**." ← 训练/演化时与评估时用同一套 composer 逻辑，**这一点保证了评估口径与演化口径一致**（若训练时全开、评估时按需开，收益会被记错）。

**与 RRSI 的对比要点**：RRSI 的成本门用 `ΔC`（token 数）做代理，ModularRSI 的 Task-Aware Composition 是**结构性降本**——同样一份库，不同任务激活的子集不同。**这两种降本路径可以叠加。**

### 2.8 Benchmark-Disjoint 演化数据集（§4）——这是本文最重要的"资产贡献"

**构造流程**：
1. 从主流终端相关基准（TerminalBench 与 SWE-Bench 家族）提取**高层领域信息**（任务类别标签）。论文强调："downstream benchmarks provide **only high-level domain guidance** for resource retrieval; **no benchmark instances or task-specific information** are used during task construction."
2. 人类标注员用这些类别标签作检索指引，从 GitHub / HuggingFace / Kaggle / Linux kernel docs 检索公开资源。
3. 用检索到的资源作原料，**构造 Harbor 格式的新可执行任务**。
4. **多阶段质量控制**（论文列了四步）：
   - **LLM-based filtering**，评三方面：`Environment Completeness`（依赖/文件/工具齐备）、`Practicality and Non-triviality`（排除人为造出的过简任务）、`Evaluator Validity`（测试套件须检验功能正确性而非表面完成信号）
   - **Executable validation**：reference `solution.sh` 必须通过全部任务专属测试，且**空提交不得获得正奖励**
   - **Manual review**：人工复核任务清晰度、环境完整性、evaluator 正确性
   - **LLM-based semantic similarity screening**：移除与下游基准高度重叠的实例
5. 产出 **2,000 个 benchmark-disjoint 演化实例**（Figure 2 显示类别分布较均衡，TB-related 与 SWE-related 两组分布大体可比）。

**"空提交不得获得正奖励"这一条是数据集质量的硬底线**——比"通过测试"更强。**这是 DWC 建演化集时最该抄的一条验收。**

## 3. 关键实验与数字

### 3.1 设置

- **评测基准**：**TerminalBench 2.0**（**89** 个长程终端任务）与 **SWE-Bench-Verified**（**500** 个人工验证的真实仓库任务）。"we use the original released benchmark versions and conduct all evaluations under the **Harbor framework**."
- **演化数据**：从 2,000 个中抽 **TB-related 120 + SWE-related 120**（"Due to computational and time constraints"）。
- **演化预算**：单模块演化与联合模块演化均 **3 epochs**。batch size **10**。模型 TPM 限制 **2M tokens/min**。
- **指标（四个，§5.2）**：
  - **Acc**：所有 rollout 的平均成功率
  - **Pass@3**：3 次独立 rollout 中**至少 1 次成功**即算解出
  - **`Pass³`（Pass 3）**：3 次 rollout **全部成功**才算解出（"measures the consistency and reliability"）
  - **StepNum**：每次 rollout 平均交互步数（越低越高效）

`Pass@3` 与 `Pass³` 的对照使用是本文的一个亮点：**它把"能偶尔做对"和"稳定做对"分开度量**。RRSI 只报单一分数。

### 3.2 主结果 1：跨基准迁移（Table 2，backbone = DeepSeek-V4-Flash-Preview）

| Evolve Set | Eval. Setting | SWE-Bench-Verified Acc ↑ | Pass@3 ↑ | `Pass³` ↑ | TerminalBench 2.0 Acc ↑ | Pass@3 ↑ | `Pass³` ↑ |
|---|---|---|---|---|---|---|---|
| No Evolution | — | 73.40 | 83.20 | 62.80 | 47.57 | 58.43 | 30.34 |
| **TB-Related** | **Out-of-Domain** | **75.80** | 84.67 | 66.20 | — | — | — |
| | **In-Domain** | — | — | — | **52.43** | 65.17 | **35.96** |
| **SWE-Related** | **In-Domain** | **76.45** | **85.30** | **66.80** | — | — | — |
| | **Out-of-Domain** | — | — | — | 49.40 | 60.67 | 30.34 |

**论文点名的三处**：
- In-domain：TerminalBench 47.57 → **52.43**；SWE-Bench 73.40 → **76.45**。
- **跨域迁移**：TB-related 演化出的 harness 在 SWE-Bench 上到 **75.80**；SWE-related 演化出的在 TerminalBench 上到 **49.40**。
- **`Pass³` 在 TerminalBench 上 30.34 → 35.96**："harness evolution not only increases average task-solving capability but also **enhances execution reliability, reducing stochastic failures** across repeated trials."
- **一处诚实的持平**：SWE-Related 的 `Pass³` 在 TerminalBench 上是 **30.34，与 baseline 完全相同**（Table 2 明确列出）。**即"跨域迁移只涨了均值，没涨稳定性"。论文未对此做任何讨论。**

### 3.3 主结果 2：跨模型迁移（Table 3，冻结 harness，只换推理模型，TerminalBench 2.0）

| 推理模型 | 方法 | Acc ↑ | Pass@3 ↑ | `Pass³` ↑ |
|---|---|---|---|---|
| GLM-5.2 | Baseline | 59.55 | 70.79 | 46.07 |
| GLM-5.2 | **ModularRSI** | **61.80** | **74.16** | **49.44** |
| MiniMax-2.5 | Baseline | 41.57 | 56.18 | 24.72 |
| MiniMax-2.5 | **ModularRSI** | **44.94** | 57.30 | **30.34** |
| DeepSeek-V4-Flash | Baseline | 47.57 | 58.43 | 30.34 |
| DeepSeek-V4-Flash | **ModularRSI** | **52.43** | 65.17 | 35.96 |

三个模型的 Acc / Pass@3 / `Pass³` **全部改善**。最显著的是 **MiniMax-2.5 的 `Pass³` 24.72 → 30.34（+5.62）**——**越弱的模型从 harness 改进里获益越多**。论文只说"These results demonstrate that ModularRSI learns transferable improvements to the agent execution process rather than exploiting model-specific behaviors"，未讨论这个反向关系。

### 3.4 关键消融：模块化是否必要（Table 4，TerminalBench 2.0）——**本文最有说服力的一个实验**

| 方法 | Acc ↑ | Pass@3 ↑ | `Pass³` ↑ | StepNum ↓ |
|---|---|---|---|---|
| Baseline | 47.57 | 58.43 | 30.34 | 34.70 |
| **Non-modular Evolution** | **46.44** | 64.04 | **24.72** | 29.03 |
| **Joint All-Module Evolution** | **44.19** | 61.80 | **24.72** | 44.34 |
| **ModularRSI（独立演化 + 整合）** | **52.43** | 65.17 | **35.96** | 35.57 |

**这是全文最重要的一张表，两个反直觉读数**：
1. **Joint all-module 演化（44.19）与 Non-modular 演化（46.44）都低于 baseline（47.57）。** 论文的结论："This suggests that **restricting the modification scope helps reduce interference** when optimizing the harness."
2. **`Pass³` 更狠**：两个退化方案都掉到 **24.72**（baseline 30.34）——**稳定性损失比均值损失更大**。这说明"无约束的大范围改动"不只是效率问题，它**系统性地破坏了执行的可靠性**。
3. **步数也有信号**：Joint 演化把 StepNum 拉到 **44.34**（baseline 34.70，+27.7%）——**步数暴涨与 Acc 下降同时发生**，符合"改动造成绕路"的解释。非模块化反而降步数（29.03）但 Acc 与 `Pass³` 双降——**更短的路走不到终点**。

| 方法 | Acc ↑ | Pass@3 ↑ | `Pass³` ↑ | StepNum ↓ |

| Tool Use | 50.19 | 62.92 | 30.34 | **41.28** |

## 4. 它假定了什么

**A1 · "benchmark-disjoint" 可以靠人工标注 + LLM 语义相似度筛查达成。**
论文的构造流程依赖：(a) 人类标注员按类别标签检索；(b) LLM-based semantic similarity screening 移除与下游基准重叠的实例。**隐含假设**：类别级别的检索引导不会意外引入基准实例。**论文未报告**重叠筛查的召回率——即"还有多少 benchmark 实例实际上漏进了演化集"。**这是一个必须打的问号**：SWE-related 演化实例全部围绕 GitHub 仓库构造，与 SWE-Bench-Verified 的仓库领域天然高度重叠，语义相似度筛查能否真的区分开，论文没有数据。

**A2 · 同一任务的成功与失败轨迹之间存在"可归因的 function-level 差异"。**
Contrastive 机制的全部有效性建立于此。§4 里三个案例支持了它，但**没有任何量化**证明"对比两条轨迹得到的诊断，比只看失败轨迹得到的诊断更可泛化"。**这是 §7 自陈的缺口，也是 A2 与结论之间唯一的桥。**

**A3 · 模块边界是清晰且稳定的。**
五模块划分把"基础设施"与"行为机制"分开，理由是前者"mainly concern system infrastructure rather than task-solving behavior"。**隐含假设**：一个 harness 的所有行为机制都能归入这五个槽，且跨轮不漂移。**DWC 的母巢做不到这一点**——它的核心问题是"零实现"，即组件还不存在。**ModularRSI 的整个框架（`locked_module` 硬边界、`ModuleCtx` 共享上下文、跨模块整合）都要求模块边界是既成事实。**

**A4 · 独立演化 + 后期整合 优于 联合演化。**
Table 4 支持（A: 52.43 vs B: 44.19）。**隐含假设**：模块之间的耦合是"冲突 / 重复"型的，可以用一次整合 epoch 修好，而不是"需要共同演化才能对齐"型的。**论文未报告整合阶段实际修了几处冲突、是否还有残留**。且**整合只有 1 个 epoch**——如果冲突需要多轮才能收敛，这个结论可能不成立。

**A5 · 同源 agent（Code-Modify Agent）能可靠地自审 diff。**
§3.5 的 Diff Review 与 §3.1 的 "the agent under evolution itself serves as the Code-Modify Agent" 是同一个 agent。**隐含假设**：一个能写出改动、能诊断失败的 agent，也能判断自己写的改动是否任务特定化。**这个假设的检验方式与 `2607.12790` Double Ratchet 的核心发现直接冲突**（同源自评会共谋塌缩）。**论文未报告 Diff Review 的误判率**（既没有放过任务特定的例子，也没有误杀通用改动的例子）。

**A6 · 三道门可以在只有 2 个执行验证样本的条件下足够。**
"randomly sample two tasks from the current batch"。**隐含假设**：两个任务足以暴露 runtime error。**这对"语法/导入/协议"类错误成立（静态检查已覆盖大部分），对"语义退化"类错误不成立**。而语义退化恰是最难察觉、也最伤 transfer 的一类。**论文未报告 2 任务抽样的检出率。**

**A7 · 演化集难度"中等居中"最好。**
§6.6 支持（76.45 vs 74.25）。**隐含假设**：这个结论不随演化框架改变。**实际上它与 RRSI 的 `m_draft` 探索机制、Table 9 的 40.67% 对比率是同一件事的三种表述**——三者共同说的是"演化集要能产出对比信号"。**但论文没有做交叉验证**：Medium-centered 这个分布在 Joint 演化（44.19，失败的那个方案）下是否还是更好？**未报告。**

**A8 · 2,000 个实例构成的分布能代表"通用终端能力"。**
Figure 2 显示类别较均衡，但 **TB-related 与 SWE-related 两组的重叠"limited by their distinct construction sources"** ——论文用构造来源不同来论证两组不重叠。**隐含假设**：构造来源不同 ⇒ 能力分布不同 ⇒ 一组演化的 harness 对另一组是真正的 OOD。**Table 2 的跨域增益（75.80 / 49.40）支持了这个假设的弱版本**（跨域也涨），**但 Out-of-Domain 的 TerminalBench Acc 只从 47.57 涨到 49.40（+1.83），远小于 In-Domain 的 +4.86** ——**迁移增益只有同域的 38%**。**这说明 benchmark-disjoint 解决了"记忆基准"，没有解决"跨域能力稀疏"。**

## 5. 可迁移到 DWC 的点 / 不可迁移的点

### 5.1 可迁移（每条给 DWC 侧接口）

**(M1) `infra_only` 排除桶（Appendix B, Table 8）→ DWC 的失败归因第一层分流。**
搬什么：把"基础设施故障"从"agent 能力不足"里摘出去，**不进入 harness 诊断**。这是单条最高性价比的机制。
DWC 侧接口（新建 `src/dwc/evolution/failure_router.py`）：

    # 对齐 ModularRSI 的 7 个路由桶
    BUCKETS = ("all_pass_efficient", "all_pass_wasteful", "mixed",
               "fixable_fail", "stuck_fail", "unreachable_fail", "infra_only")

    def route(rollout_rewards, error_class) -> str:
        # infra_only 不进入诊断；否则演化会试图用 harness 改动去修环境 bug。
        # 对 DWC 的具体化：tool-call 超时 / 上下文截断到 API 上限 / 网络 5xx
        # 应归入 infra_only，而非 fixable_fail。

**为什么这条对 DWC 最关键**：DWC 的 `2609.04128` 报告里已经记录了"核心功能零实现、445 万行读后零产出"这类系统性失败。**如果这些失败被归到 `fixable_fail`，演化会尝试用 harness 改动去修它们——那是纯浪费。** `infra_only` 是防止这种浪费的第一道分流。

**(M2) `unreachable_fail` / `stuck_fail` / `fixable_fail` 三分（Table 8）→ DWC 的"可修复性"预判。**
搬什么：Negative 组内部再分三类——**可修 / 卡死 / 不可达**。这三类的处理策略完全不同（可修→提改动；卡死→提 recovery hint；不可达→弃权）。
DWC 侧接口（接 M1）：

    def classify_failure(trace, error_class, n_distinct_attempts) -> str:
        # fixable_fail : 有明确工具/参数错误且尚未尝试过替代路径
        # stuck_fail    : 同一动作重复 N 次后仍失败 → 对应 RRSI 的 recovery hint 类改动
        # unreachable_fail: 当前权限/工具/上下文下不可能成功 → should fixable_now = False

`(unreachable_fail → 弃权)` 这一条对应 Listing 2 的 `is_culprit: false` 与 `fixable_now: false` 记录。**"弃权是一等输出"这个设计值得单独抄。**

**(M3) 五模块划分（§3.2 + Listing 1）→ DWC 母巢的组件协议化。**
搬什么：把 DWC 的执行链拆成五个有明确输入输出契约的模块，**特别是区分 Observation Management 与 Context Management**（论文特意澄清：一个返回当前环境反馈，另一个更新累积对话历史）。DWC 母巢的 `context_mgmt` / `client_tool` / `skill` / `memory` / `subagent` 与这套划分高度重叠。
DWC 侧接口（新建 `src/dwc/harness/modules.py`）：

    from typing import Protocol, tuple
    # 直接对齐 Listing 1 的五个签名，命名保持一致以便对照
    class AgentLoop(Protocol):
        async def run(self, initial_prompt, original_instruction, obs, context_mgmt,
                      tools, verification, chat, ctx) -> AgentLoopResult: ...

    class Observation(Protocol):
        async def capture(self, prev: ObsState, ctx) -> tuple[ObsResult, ObsState]: ...

    class ToolSet(Protocol):
        def parse_llm_response(self, response: str) -> LLMResponseParseResult: ...
        async def execute(self, call: ToolCall, ctx) -> ToolResult: ...

    class ContextMgmt(Protocol):
        async def maybe_compress(self, chat, original_instruction, ctx) -> CompressResult: ...
        async def force_summarize(self, chat, original_instruction, ctx) -> CompressResult: ...

    class VerificationLoop(Protocol):
        async def should_terminate(self, state, ctx) -> tuple[bool, str]: ...

**"完成检测器只返回建议，Agent Loop 掌握是否继续"**——这条职责划分必须照抄，否则 termination 逻辑会被多个模块各写一份。

**移植前提（诚实）**：M3 只在 DWC **已有可切分的模块**时成立。母巢的"零实现"意味着这一步得先做一次纯人工切分，**这不是演化，是重构**。

**(M4) `locked_module` 硬边界（Appendix B schema）→ DWC 的单模块编辑锁。**
搬什么：每条 finding 记录必须声明 `locked_module`，本轮**只允许改这一个模块**。
DWC 侧接口（在 `src/dwc/evolution/finding.py`）：

    @dataclass
    class Finding:
        task: str
        lens: str                      # 分析模式
        locked_module: str             # 本轮唯一允许改的模块，硬边界
        is_culprit: bool               # 因果判定，允许 false（弃权）
        divergence: str                # 轨迹证据摘要
        would_change_outcome: str      # 反事实判断（Yes/No + 理由）
        fixable_now: bool              # 系统现在能否行动
        suggested_change: str
        parse_status: str = "ok"

**依据强度**：Table 4 的 Negative 结果（Joint 44.19 < baseline 47.57）是"必须硬边界"的直接证据。**但要注意反向条件**：ModularRSI 的硬边界是"五个模块各跑 3 epoch 再整合"，DWC 若只有一轮演化预算，可能拿不到整合的机会——见 §5.2。

**(M5) Program Check 五项（§3.5）→ DWC 的静态门。**
搬什么：**AST validation / import checks / protocol compliance / discovery-contract verification / static self-attribute audits** 这五项，逐项可抄。
DWC 侧接口（新建 `src/dwc/evolution/static_gate.py`）：

    def static_check(diff, module_protocols, registry) -> CheckResult:
        # 1 AST validation        —— 语法树可解析
        # 2 import checks         —— 新引入的 import 可解析
        # 3 protocol compliance   —— 改动后仍满足该模块的 Protocol 签名（接 M3）
        # 4 discovery-contract    —— 该实现仍能被 composer 发现 / 注册
        # 5 static self-attribute —— 该实现仍具备必需的成员
        # 任一失败 → 按 function 粒度回滚（靠 diff 记录，不是 git）

**"discovery-contract verification" 这一项是 DWC 独有的价值**：如果 DWC 用注册表 / composer 组装模块（正如 Task-Aware Function Composition），那么"改了函数但没注册"就是静默失效——静态可查。

**(M6) function-level diff 回滚（§3.5）→ DWC 的精确回滚机制。**
搬什么：三道门全部失败即回滚，回滚粒度是**函数**，靠**记录的 diff** 而不是 git。

        # 三道门的任一失败都走这里。diff_log 必须在每次改动后立即落盘，

**这是 M5/M7/M8 的共同基础设施**，优先级高于它们。

**(M7) Trajectory Memory 的可量化价值（Table 9 的 8.33%）→ DWC 的记忆跨轮复用指标。**
搬什么：不是搬机制（"存历史轨迹"本身不稀奇），而是**搬它的度量方式**——统计"当前全失败但在历史里找到过成功"的组占比。

### 5.2 不可迁移

- **不可迁移（框架前提，最硬的一条）：模块必须是既成事实。** ModularRSI 整个架构——`locked_module` 硬边界、`ModuleCtx` 共享上下文、Function Merge / Task-Aware Composition、Cross-Module Integration——**全部要求 harness 已被切成五个边界清晰的模块**。**DWC 母巢的已知状态是"核心功能零实现"**：组件还不存在。**因此 M3（模块协议化）在 DWC 上不是演化任务，是一次重构任务**，且必须先完成才能开始 M4/M5/M9。**这是三篇里对 DWC 最结构性的障碍。**

- **不可迁移（同源自评风险，结构性缺陷）：Diff Review 由 Code-Modify Agent 自审。** 论文明确 "The agent under evolution itself serves as the Code-Modify Agent for both trajectory analysis and harness modification"。按 `2607.12790` Double Ratchet 的实证结论（被评估对象与评估机制同源会共谋塌缩），**ModularRSI 的 Diff Review 是同源自评**。
  - **具体到 DWC**：如果 DWC 用同一个模型既做诊断又做 diff 审查，**"判断这个改动会不会过拟合"这个问题会退化为"我认为这个改动好不好"——两者由同一个先验给出，答案必然一致。**
  - **可行的折中**：DWC 可以在 Diff Review 这一步**换一个模型或换一种提示框架**（例如"请假设这个改动是别人写的，只判断它是否包含任务特定常量"），**成本很低但打破了同源**。RRSI 的三角色分离（proposer / analyst / critic）在这个维度上更稳。

- **不可迁移（无门触发统计）：三道门是系统的主要承重墙，但论文没测过它们值多少。** 没有一张表说 Program Check / Diff Review / Execution Validation 各拒了多少、各救回多少。**后果**：无法判断 ModularRSI 的 +4.86 Acc 来自"模块化"还是"门"。**DWC 若照搬这套门，必须自己加门触发计数器**——否则搬过来的是一组无法验证有效性的机制。

- **不可迁移（contrastive 无因果消融，论文自陈）：** §7 Limitations 第一条。Figure 3 的"对比率随演化下降"与三个案例**是相关证据不是因果证据**。**DWC 不应把"对比式轨迹分析"当作已验证的机制直接押注**——应按 M7 先建度量，再决定投入。

- **不可迁移（K 值与 rollout 成本）：式 1 的 K 未报告**，Table 9 提到 "five runs and subsequent replay"。若 K=5，240 个演化任务 × 3 epoch × 5 rollout × (1 + 5 模块独立) 的量级远超 DWC 预算。**DWC 若照搬五模块独立演化，每模块的 rollout 预算是独立的一份**——这个乘数必须先算清楚。

- **不可迁移（16 epoch 的对齐前提）：** Table 6 把 AHE / Meta-Harness 跑 16 epoch 来对齐 ModularRSI 的"5 模块 × 3 epoch + 整合"。**这个对齐方式隐含"轮数可比 = 预算可比"的假设**，但 ModularRSI 的 16 轮里每轮只改一个模块、候选池小，**实际 token 消耗未必与 16 轮全量演化相同**。**DWC 若引用 Table 6 的"ModularRSI +5.6 vs 基线"作为目标值，必须先核算真实预算。**

- **不可迁移（两张表的 baseline 不一致）：** Table 6 的 baseline **61.79** 与 Table 2/4/5 的 **47.57** 差 14.2 分，论文未解释。**任何跨表比较都是错的**——引用必须指明是哪一张表。

- **不可迁移（跨域迁移增益只有同域的 38%）：** TerminalBench Out-of-Domain 只涨 **+1.83**（47.57→49.40），而 In-Domain 涨 **+4.86**。**这说明 benchmark-disjoint 解决的是"不记忆基准"，不是"跨域能力稀疏"。** DWC 若指望"在 A 类任务上演化出的能力自动迁移到 B 类任务"，**数据是 1.83 而非 4.86**。

- **不可迁移（模型档位）：** 演化主模型是 DeepSeek-V4-Flash-Preview / 0731，评测涉及 GLM-5.2 / MiniMax-2.5，附录 F 的 LLM 评分用 **Opus-4.8**。**DWC 当前是托管/免费路由，能力档位低于这些模型。** Table 5 的关键观察——**越弱的模型从 harness 改进里获益越多**（MiniMax-2.5 的 `Pass³` +5.62）——**对 DWC 反而是好消息**，但也意味着 DWC 不能假设同样的绝对增益。

- **不可迁移（无统计口径）：** 全文无 error bar、无多 seed 方差、无显著性检验。TerminalBench 2.0 只有 89 个任务，Acc 47.57 → 52.43 是 5 个任务的差别。**DWC 若把 +4.86 当作设计目标而不做显著性判断，会踩到 Table 9 里那个 8 组无分数的坑。**

## 6. 与其他论文的关系

### 6.1 在 RSI 图谱上的位置

ModularRSI 是 **harness 自进化派里唯一在"数据层"动手的一篇**。其余各家（Self-Harness、AHE、HarnessX、RRSI）都在"用已有基准数据演化"这一层打补丁，**只有它去构造了一批与评测基准不重叠的数据**。这使它的 Table 6 成为整个领域的一个**参照性实验**：它把 AHE 与 Meta-Harness 拉到自己的协议下重跑，得到"约 1 个百分点"。

按 `2609.13406`（GAI 框架）的两个 dial 定位：
- **改进机制属于 agent 自身**吗？**部分是**。诊断与改动由被演化 agent 自身（Code-Modify Agent）执行，**但演化数据不是它自己产生的**（是人工标注员从外部资源构造的）。按 `2609.13406` 的严格标准，这**不是完全自举**——它是"外部构造经验 + 内部消化经验"。
- **度量锚定在系统外**吗？**是**——TerminalBench / SWE-Bench 的 evaluator 是外部冻结的，且 Pass@3 / `Pass³` 用**全分母**、无子采样。
→ **ModularRSI 是 GAI 框架下"度量锚定清晰、但经验来源外部"的一个实例。**这个定位比 RRSI 更保守，也更诚实。

### 6.2 与 `2609.24972` RRSI（同期、直接竞争，本批次最该并排读的一对）

| 维度 | ModularRSI | RRSI |
|---|---|---|
| 防 benchmark 记忆 | **数据层根除**：2,000 个 benchmark-disjoint 任务（Table 1 "Do Not Use Benchmark Data ✓"） | **搜索层压制**：critic 事前筛 + 门控接受，但 evolve set **就是**下游基准 |
| 证据归因 | **五模块硬边界**（`locked_module`）+ 同任务成功-失败对比 | **9 个软标签**（`𝒦`，不限制编辑边界）+ 编辑历史 `g_t(ℓ)` |
| 门 | Program Check → Diff Review → Execution Validation，**全部是"坏改动即回滚"** | 三个非补偿 AND（噪声地板 ∧ 成本规则 ∧ DomainGuard），**面向分数** |
| 成本处理 | **结构性降本**：Task-Aware Function Composition（事前不激活） | **度量性降本**：`ΔC ≤ β₀+β₁ΔS`（事后算账） |
| 效率是否被优化 | **是**：Positive 组专门分析冗余动作；StepNum 是正式指标 | **是**：成本门 + 轨迹步数都在报告里 |
| 关键负面结果 | **Joint / Non-modular 演化低于 baseline**（44.19 / 46.44 vs 47.57） | **未正则化演化的 evolve 分数最高但 transfer 最差**（92.8 / 40.3 vs 90.5 / 43.6） |
| 与对方的直接对比 | **无**（全文 0 命中 RRSI） | **有**（RRSI 未对比 ModularRSI） |

**三点实质互补**：

1. **两者合起来给出一条完整的因果链，而单看任一篇都得不出这个结论。** RRSI 证明"在基准上演化会过拟合"（Table 1：四个基线在 Harvey LAB evolve set 涨 3.6 分，但 OOD 均值 2 个低于 base、2 个持平）；ModularRSI 证明"不在基准上演化时，AHE 与 Meta-Harness 只涨约 1 个百分点"（Table 6）。**拼起来的结论是：那两个方法的表观收益主要来自基准记忆。RRSI 自己做了这个交叉实验的**（它有 benchmark-overfitting 的数据但没有 disjoint 数据），**ModularRSI 做了 disjoint 实验但没跟 RRSI 的表对照**。**这是两篇论文各自缺的那一半。**

2. **硬边界 vs 软标签：两者是不同强度的解，且各有代价。** ModularRSI 的 `locked_module` 强制单模块，实验证明这是必要的（Joint 44.19 < baseline 47.57）。RRSI 的 `𝒦` 只是归因标签，一个候选可以同时改多个组件，靠 `b_t → 1` 在末轮部分弥补。**RRSI 的软边界更灵活（能一次改两个互相依赖的组件），ModularRSI 的硬边界更安全（不会引入跨机制干扰）。** 若 DWC 的组件耦合度高，RRSI 路线更合适；若组件耦合度低，ModularRSI 路线更省心。

3. **降本路径互补，可叠加。** ModularRSI 的 composer 是**事前结构控制**（不激活不相关函数），RRSI 的 `ΔC` 门是**事后算账**（涨太多就不收）。**前者保证"不涨"，后者保证"涨了要付得起"。DWC 两个都该做。**

**一处必须诚实指出的分歧**：RRSI 的 critic 与 proposer **分离**（三个角色都是 Opus 4.8，但是不同 prompt 角色）；ModularRSI 的 Diff Review 由**同一个 Code-Modify Agent** 执行。**按 `2607.12790` 的结论（同源自评会塌缩），ModularRSI 的这一门结构上更脆弱。两篇论文都未讨论这个差异。**

### 6.3 与 `2606.14249` HarnessX（直接竞争，HarnessX 报告已提到 ModularRSI）

HarnessX 报告已指出："ModularRSI 更强的一个维度是 'benchmark-disjoint'"。补充三点：

- **组件划分的同构与分歧**：HarnessX 的九维 typed 组件与 ModularRSI 的五模块是**同一次分解的两种切法**。HarnessX 的九维包含 `memory` 作为独立维度；ModularRSI 的五模块**没有 memory 维度**（记忆被归入 Context Management）。**对 DWC 而言这是重要信息：DWC 的记忆能力在 ModularRSI 的框架里没有独立位置。**
- **HarnessX 的变体隔离 vs ModularRSI 的模块隔离**：HarnessX 按**任务簇**隔离变体（"variant isolation"），ModularRSI 按**功能模块**隔离。**两者是正交的**：前者防"任务间干扰"，后者防"机制间干扰"。HarnessX 自己在 GAIA 上 Δ=0.0（异质性触发停滞）正是"没有变体隔离"的代价；ModularRSI 的 Joint 44.19 正是"没有模块隔离"的代价。**DWC 若两者都不做，两种停滞都会遇到。**
- **HarnessX 的 held-out 缺口 vs ModularRSI 的 benchmark-disjoint**：HarnessX 明确不评估 held-out；ModularRSI 的进化数据与评测数据完全隔离且**经过人工复核 + 语义相似度筛查**。**在泛化证据的可信度上，ModularRSI 明显更强。**

### 6.4 与 `2606.09498` Self-Harness（同问题域，最简版本对照）

Self-Harness 报告已给出这个对照："ModularRSI 认为只对比失败不够"。展开说：
- Self-Harness 做的是 **verifier-grounded 聚类**（把失败按 verifier 信号聚类），本质上是**单侧**的。
- ModularRSI 的 **Contrastive 组**要求同任务同时有成功与失败（40.67% 的组），**Negative 组用 Trajectory Memory 回溯历史成功（再 +8.33%）**，**Positive 组分析冗余（36%）**。
- **关键增量**：ModularRSI 把 **"全失败且无历史成功"（14.56%）** 显式列为一个独立桶（`unreachable_fail` / `stuck_fail`），并允许**弃权**（`fixable_now: false`）。**Self-Harness 没有"弃权"这个概念**——它对每个失败簇都要提改动。
- **与 RRSI 的一致性**：三篇都指向"失败轨迹不够"这一判断，只是解法不同（Self-Harness 聚类、RRSI 靠编辑历史打标签、ModularRSI 靠同任务对比）。

### 6.5 与 `2607.12790` Double Ratchet（结构性冲突，必须点名）

ModularRSI 的 Diff Review 由 Code-Modify Agent 自审，即 **被评估对象（harness 改动）与评估它的机制（同一个 agent）同源**。Double Ratchet 的核心实证是：**当两个 dial 之一没有 grounded outside 时，会出现共谋塌缩**（一个 collapsed 的评估器可以训练出和好评估器一样好的 skill，甚至更好）。
**论文完全未讨论这个风险**，也未报告 Diff Review 的误判率。**这是 ModularRSI 相对 RRSI 的一个真实弱点**（RRSI 的 critic 是分离的角色）。

**但要给公平的反面**：ModularRSI 的 Diff Review 只判"是否任务特定化"这一个二元问题，且有前两道门（AST / import / protocol / discovery-contract / self-attribute）作为**纯规则、不依赖模型**的兜底。**Double Ratchet 描述的塌缩需要一个"可被共谋操纵的连续评分"，而这里的 Diff Review 是二元否决 + 五道静态规则**，共谋空间小得多。**结论：风险存在但有限，且 DWC 只需换模型或换提示框架即可基本消除。**

### 6.6 与 `2609.06396` MetaRSI（记忆与能力分配的互补）

MetaRSI 报告已提到 ModularRSI，并指出其价值："DWC 的记忆如果不记录'为什么失败'，检索时无法按成因路由，只能按语义相似度——这正是 ModularRSI 说的 'localizing recurring behavioral deficiencies within monolithic harnesses is difficult'。"

**展开**：ModularRSI 的 finding schema（`divergence` / `would_change_outcome` / `is_culprit` / `locked_module`）**本质上就是一份"带成因的记忆记录"**。而 MetaRSI 的四维学习签名 `κ(e)`（knowledge / reasoning / verification / distractor）是同一件事的另一种编码。
**互补关系**：ModularRSI 的 schema 是**面向 harness 修复**的（下游是"改哪个模块"），MetaRSI 的 `κ` 是**面向能力补全**的（下游是"要造哪类记录"）。**DWC 的记忆层应该同时承载两者**——`κ` 作为检索键，`divergence`/`is_culprit` 作为成因路由。
**注意 ModularRSI 的 schema 里没有 `memory` 维度**：它的五模块不含记忆。**这正是 MetaRSI 能补的位置。**

### 6.7 与 `2609.08183` NeoHorse-1（不同层级，但共享一条重要直觉）

NeoHorse-1 改的是**模型权重**（SFT + on-policy distillation），ModularRSI 改的是 **harness 代码**。但两篇共享一条具体直觉：
- **ModularRSI 的 Positive 组**："the analysis focuses on opportunities to improve execution **quality and efficiency**, such as redundant actions, repetitive exploration, or unnecessary tool calls."
- **NeoHorse-1 的发现**："the larger model is better able to **identify unproductive trajectories, revise its strategy** in response to environmental feedback, and **allocate a limited interaction budget** to actions that directly contribute to task completion."（PinchBench 案例中 9B 比 4B 少 70.8% 请求 / 76.7% 时间 / 83.6% token）
   > **数字出处**：PinchBench 案例与上述三个百分比均出自 `2609.08183` NeoHorse-1 原文，**非本文(2609.14857 ModularRSI)的实验数据**。本文实验见 §3。

**同一现象的两个层次**：NeoHorse-1 说"更强的模型自带这种判断"，ModularRSI 说"我们可以把这判断写进 harness"。**这是"能力 vs 脚手架"这一对经典权衡的一个具体实例。**
**对 DWC 的直接含义**：既然 DWC 的模型档位固定（不能换更强的），**那么"把效率判断编进 harness"就是唯一路径**——而 ModularRSI 的 Positive 组分析正是这条路径的具体实现。

### 6.8 与 `2609.14858` Dream-RSI 与 `2609.04128` Environment Evolution（数据侧的间接关联）

- **Dream-RSI** 用 replay world 做选择，需要历史；**ModularRSI 的 Trajectory Memory 也存历史**，但用途完全不同——Dream-RSI 的历史是"回放的仿真环境"，ModularRSI 的历史是"对比的证据来源"。**两者可以叠加**：用 Dream-RSI 的 replay 做选择，用 ModularRSI 的 contrastive 做诊断。
- **Environment Evolution（2609.04128）** 演化的是任务/环境本身；ModularRSI **明确构造了 2,000 个新任务**，但这些任务**在演化过程中是不变的**（用 120 个固定实例跑 3 epoch）。**两者可以互补**：用 Environment Evolution 的多样性注入来替代/补充 ModularRSI 的 Medium-centered 难度配比（M12）。**论文未涉及任务侧演化，这是 ModularRSI 的一个明确边界。**

### 6.9 一句话定位

**ModularRSI 是三篇里唯一在数据层动手的一篇，也是唯一给出"我的两个对照组都变差了"这个诚实负面结果的一篇。**它最有价值的三个贡献：(a) **benchmark-disjoint 演化协议 + 2,000 个实例**，加上 Table 6 的复现实验，给出了"现有方法的表观收益主要来自基准记忆"这个领域级实证；(b) **五模块硬边界 + Joint 演化低于 baseline 的负面结果**，证明了"限制改动范围"是必要条件；(c) **`infra_only` 排除桶与 `unreachable_fail` 弃权**，把"不该修的失败"从进化信号里摘出来。它最大的三个问题：(a) **contrastive 无因果消融（自陈）**；(b) **三道门无触发统计，无法知道系统靠什么在承重**；(c) **Diff Review 同源自审，结构上比 RRSI 的分离 critic 脆弱**。对 DWC 最关键的判断：**它的整个框架要求 harness 已被切成五个边界清晰的模块，而母巢的核心问题是"组件还不存在"——所以这篇能抄的是 finding schema、`infra_only` 分类、和"空提交不得正分"的数据门，而不是它的模块架构本身。**

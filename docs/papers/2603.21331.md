# AutoKernel: Autonomous GPU Kernel Optimization via Iterative Agent-Driven Search

- arXiv:2603.21331 · f=5（综述 2609.11873 引用频次 refmap.json：§3.3.3 + Table 2×3 + Table 4）
- 全文: papers/arxiv_2609.11873/refs/2603.21331.txt (34,197 字符 / 523 行, PDF 文本层, 正文硬换行约 100 字符/行)

## 一句话总结

把专家 kernel 工程师的手工循环机械化：profile 任意 PyTorch 模型 → Amdahl 定律给瓶颈排序 →
单 agent 每轮只改一个 kernel 文件 → 五阶段正确性门全过才计时 → `git commit` / `git reset`
keep-or-revert，一夜 300–400 次实验；**H100 上 34 个配置零失败**，起点 kernel（starter）
已在 16 个代表配置中 12 个赢过 `torch.compile(max-autotune)`；
**但"agent 迭代循环本身带来多少提升"论文没有给出任何前后对照数字** —— 主表测的是
starter，循环收益只有定性 tier 描述与两个社区个案。

## 核心方法（细颗粒度）

### 三阶段架构（Fig 1, §3）

- **Phase A profiling**（`profile.py`, 1,125 行）：接受本地 py 文件 / HF model id / 自定义模型类；
  `torch.profiler` + shape recording，默认 5 次 warmup + 10 次 profiling；每个 CUDA kernel 经
  **kernel 名模式匹配**归入 9 类操作（cuBLAS GEMM / CUTLASS / Triton / ATen 各有命名模式）。
  GPU 规格数据库覆盖 H100/A100/L40S/L4/A10/RTX 4090–3080 与 AMD MI300X–MI355X；未知卡从
  SM 数、频率、compute capability 估 FP16 峰值；AMD 设备名为空时读 `gcnArchName`。
  可选输出 Chrome trace JSON / CUDA 内存快照 / `torch.compile` 日志 / HTA 结果。
- **Kernel extraction**（`extract.py`, 648 行）：过滤出受支持操作类型，生成独立 kernel 文件 =
  starter 实现 + 模型专属 shapes（primary / half / double 三档）+ FLOPS 与 bytes 公式（供 roofline）
  + dtype 容差；优化计划按 **Amdahl impact** 排序并给 1.5×/2×/3×/5× what-if 投影。
- **Phase B 自主循环** = 论文 Algorithm 1（逐行语义）：
  `k_best←k; t_best←B(k); n_rev←0`；每轮 `k'←A.edit(k_best, history, roofline)` → `git commit k'`
  → `(pass, t')←B(k')`（五阶段正确性 + 性能）→ **若 `pass and t' > 1.01·t_best` 则 keep**
  （`n_rev←0`），否则 `git reset --hard HEAD~1; n_rev←n_rev+1` → `log(i, t', decision, description) to TSV`
  → `if C(n_rev, t_best, elapsed): break`。**accept 阈值是 1.01×**（需超过 1% 才算改进）。
- **Phase C**：端到端 verifier（正确性 + 端到端加速确认后才记录 speedup）。

### 节奏与不变量（§3.3）

- 单轮 ≈ **90 s** = 30 s 五阶段正确性 + 30 s Triton `do_bench` 性能 + 30 s agent 推理改码；
  **40 次实验/小时**，10 小时 = 300–400 次实验（Fig 1 标注 "∼40 iter/hour"、"300+ per run"）。
- **Single-file invariant**：agent 每轮恰好碰一个文件 —— "diffs small, reverts clean, and prevents
  coupled changes that are hard to isolate when a regression occurs"。
- Agent 读 `program.md`（**909 行**六级 playbook，见下）。
- 系统规模：**9,200+ 行 Python / 14 个核心脚本**，18 个 kernel 实现（9 Triton + 9 CUDA C++），
  4 个模型定义；`bench.py` 1,416 行、`orchestrate.py` 842 行、`bridge.py` 674 行、
  `bench_kb.py` 726 行、`export_hf.py` 868 行、`scorer.py` 351 行。

### Amdahl 编排与 move-on（Eq 1, §3.4）

`S = 1 / ((1−f) + f/s)`，f = 该 kernel 占总 GPU 时间比例，s = 达成的加速。
原文例："A 1.5× speedup on a kernel that accounts for 60% of total runtime yields 1.25×
end-to-end. The same speedup on a 5% kernel yields only 1.03×."
**换下一个 kernel 的四条判据**（原文逐条）：(1) 5 consecutive reverts；(2) 90% of GPU peak reached；
(3) 2 hours elapsed；(4) 2× speedup achieved。

### 五阶段正确性门（§4, Fig 2）

任何一阶段失败 **立即 REJECT，"Throughput is only measured after all five stages pass"**：

1. **Smoke test**：单个 128×128 前向，<1 s 抓编译错 / shape 错 / 粗数值错。
2. **Shape sweep**：8–10 个配置 × 3 dtype（FP16/BF16/FP32）。Table 2 的 matmul 八档逐格：
   tiny 128³ / small 512³ / large 2048³ / xlarge 4096³ / tall 8192×1024×1024 /
   deep_k 1024×1024×8192 / llm_qkv 4096×4096×512 / llm_mlp 4096×11008×4096。
3. **Numerical stability**：对抗输入（softmax→整行大相同值；matmul→极端动态范围；norm→近零方差）。
4. **Determinism**：同输入 3 次运行，**bitwise identical**（抓并行归约竞态 / 非确定性 atomic）。
5. **Edge cases**：非 2 幂维度（1023, 4097, 1537）抓 mask 与 tile 余数 bug。
   容差按 dtype：FP16 `atol=1e-2`、BF16 `2e-2`、FP32 `1e-4`。

### 六级 playbook（§3.3 的 909 行 program.md）

Tier1 block size（标称收益 10–50%）→ Tier2 memory access（10–30%：coalesced loads、L2 swizzling、
smem padding）→ Tier3 compute（5–15%：TF32 累加、epilogue fusion、loop-invariant hoisting）→
Tier4 advanced（5–20%：split-K、persistent kernel、Triton autotune、warp specialization）→
Tier5 architecture-specific（5–15%：Hopper TMA、Ampere `cp.async`）→ Tier6 kernel-specific
（attention online softmax、norm 用 Welford、tall-skinny matmul 用 split-K）。
**括号里的百分比是 playbook 写给 agent 的预期区间，不是论文测出来的数。**

### 双后端与覆盖（§5, §6, Table 3）

Triton 9 个 starter（JIT 编译 1–5 s，matmul 常到 cuBLAS 的 80–95%）+ CUDA C++ 9 个 starter
（WMMA 16×16×16、`__shfl_xor_sync`、`float4/half2` 向量化、无冲突 smem、双缓冲、`__launch_bounds__`；
`load_inline` + hash 缓存）。两后端同一 `kernel_fn()` 接口，benchmark 不变。
九类 kernel：matmul / flash_attn / fused_mlp（TFLOPS）+ softmax / layernorm / rmsnorm /
cross_ent / rotary_emb / reduce（GB/s）；每类有 `reference.py` PyTorch 参考实现当 oracle。

### 设计理由（§10，与 RSI 防作弊直接相关）

- **"Fixed evaluation, mutable code"**：benchmark 永不被 agent 修改 ——
  "This firewall prevents gaming the evaluation, a real risk when the candidate generator
  also controls the scorer."
- Git 即实验台账（每个实验 = 一个 commit，revert 用 `git reset` 抹掉，历史可 browse）；
  roofline 分类（compute-bound / memory-bound + % of peak）回灌给 agent 选 tier；
  结果写 **TSV**（无依赖、可读、git 友好、agent 易解析），不用数据库。

## 主结果（数字带原文短引，逐格读表）

**评测设置（§7）**：NVIDIA H100 80GB HBM3（132 SM, cc 9.0, CUDA 12.8），FP16，
CUDA event 计时，每配置 200 次迭代取 **trimmed mean（去掉最高最低各 10%）**；基线两个：
PyTorch eager（matmul 走 cuBLAS，其它走 ATen）与 `torch.compile(max-autotune)`。
" The full evaluation across 7 kernel types and 34 benchmark configurations completes in under
10 minutes wall-clock time. All 34 configurations pass correctness with zero failures."

- **负面结果（论文自己写明）**："Matmul remains hard ... Our Triton starter reaches 278 TFLOPS

  rotary 对 `torch.compile` 输（0.91×/0.61×）。
- **社区部署（§7.2，二手）**：vectorsum_v2 B200 榜首 **44.086 µs**（第二 44.249、第三 46.553，
  领先 0.163 µs ≈ 0.37%）；FP4 matmul Table 5 七形状对 CUTLASS **1.63×–2.15×**，
  最高 **2,898 TF/s @2048×18432×3072**（1662 vs 964 TF、0.023 vs 0.040 ms 等七行见原文），
  "a single AutoKernel prompt, requiring approximately 3 minutes of agent interaction"。
- **循环动力学（§7.3，纯定性）**：memory-bound 如 RMSNorm —— Tier1 扫 BLOCK_SIZE 256→4096
  "typically yields 10 to 30% improvement in the first 5 to 10 experiments"，Tier2 +10–20%（再 10–20 次），
  Tier3 5–10%，"After 30 to 50 experiments ... The orchestrator triggers move-on"。

## 与 DWC 的映射（机制 | DWC 现状 | 判定）

| AutoKernel 机制 | DWC 现状（代码级） | 判定 |
|---|---|---|
| Amdahl 先 profile、按"对全局的贡献"分配优化预算（"optimize what matters"） | 任务源排序 = 任务级 δ 降序（`core._task_deltas` → `weakness.task_delta_map`，再 `core._el_pick` 交给 `ELScheduler`）；**无"占全局代价比例"的权重** | **缺**（可映射）：`harness/run_term.py::CostLedger` 已记 `term_cost/cumulative_cost/rejected_cost`，可给 δ 乘一个 per-task cost-share 因子，落点仍在 C1 排序偏置域，不动 `WorldTree.select`（W4） |
| move-on 四判据（5 连败 / 90% 峰值 / 2 h / 2×） | 停滞只有两处：`el_sched.py` 的 `p̂≤τ`（B=8, τ=6/8）与 `evolver.stall_signal(score_history, window, delta)`；`state.cost_used` 预算存在但**不接进调度** | **半有**：`stall_signal` ≈ "5 consecutive reverts"（连续失败/无增益计数），缺"时间/预算上限"这条 —— 把 `CostLedger` 上限接成第 4 条 move-on 是具体补丁 |
| 五阶段门：正确性全过才测性能（firewall 在测量之前） | `Judge.evaluate` 判分 + `ProposalGate.check` 把关候选 + `judge.regression_check`；`Proposal._assert_single_change` 保证一处改动 | **确认型**：DWC 的门在"提案/落地"层而非"计时"层，结构同型（先验正确、后计量收益） |
| "Fixed evaluation, mutable code"：agent 永不改评分器 | W2/W5：`world_model` 的 `provenance` 单向 observed/simulated、"分数只来自 judge 观测"（`core.dream` 注释 "dream 不写树、不产分数"）；judge 真值源 `anchors` | **确认型**（同一条防作弊判据，DWC 用 provenance 表达、AutoKernel 用"文件只读"表达） |
| Single-file invariant + git 即台账（每实验一 commit） | `Proposal._assert_single_change`（单点改动断言）+ `evolver.record_edit`/`liquidity` 台账（`k1_coverage`、`liquidity_summary`、`gain(..., window)`） | **确认型**：DWC 已是"一改一记"，缺的只是"回滚 = git reset"这种可执行撤销（DWC 靠 Applier 落地前 gate，不做落地后回滚） |
| 六级 playbook：把专家知识按收益层级编码成 agent 指令（909 行） | 无 playbook；经验持久化只有 `evolver.Mutator.load_learned/persist_learned/check_entry`（按失败签名 key 存条目） | **部分可迁移**：可把 tier1–6 写成 `Mutator` 的 learned entries（按 signature 命中），但 tier 的"预期收益百分比"是 kernel 域先验，DWC 不能照搬数值 |
| 循环收益必须可测（否则 400 次实验只是烧算力） | `run_term` 有 T1–T4 前测/后测 + `TermReport`；`evolver.has_rise/has_drop/natural_rise/noise_delta` 区分自然波动 | **反向教训**：AutoKernel 恰好缺这个对照，DWC 已有 —— 说明"改动可测"是 RSI 最容易被跳过的验收项，不是可选项 |

## 综述 L 定位

- **L2（Improvement Strategy Autonomy）**，非 L3/L4/L5：综述 §3.3.3 "(4) Systems and
  Implementation Search" 逐字收编本篇 —— "AutoKernel begins from profiling rather than arbitrary
  code generation ... Candidate Triton or CUDA implementations are accepted only after correctness
  checks and measured GPU speedups"。Table 4 里它的行 = **"Kernel experiment | Profile–rewrite–benchmark
  loop | Fixed correctness + speed"**（外部固定限制 = 正确性 + 速度，improvement 自己定）。
- **技术族**：Table 2 **A5. LLM-guided Program / Code Search**（与 ADAS、AFlow、Harness Engineering、
  AIPC 同格；f=5 说明它在综述里是该族 L2 的代表样本之一）。
- **structural / effective**（用综述 §3.6 的 L5 判据类推到本篇的递归对象）：
  - *structural*：**有** —— 改动确实持久（git 分支 + TSV 历史），验收准则外置
    （fixed benchmark，对应 Table 4 的 "Fixed correctness + speed"），符合
    "an AI-directed change persists and controls a later improvement round" 的结构要件。
  - *effective*：**未证** —— 综述 §3.3.4 的原话正是它的坑："additional search compute can be
    mistaken for algorithmic improvement"。本文没有 starter→loop-N 的对照，所以"搜索找到了更好
    实现"与"多跑了几次实验"无法区分；effective 证据只来自社区个案（单点、无对照）。
- 与综述 Table 8（L5 评估）**无关**：本篇不测"改进机制被继承"，只测单任务性能。

## 一句话总结

把"模型上板部署"切成 **6 个各自带可验证出口的阶段**，用 **Agent Skills** 把 QAIRT 工具链知识显式注入 agent、用 **golden baseline + 逐阶段数值比对**把 agent 圈在可验证空间里做**有界修复（bounded repair）**——结构规则的视觉模型 **PyTorch→可跑的 QNN/SNPE 推理 7–20 分钟、API 成本约 0.7–10 美元**，但含不支持算子 / 动态形状 / 自回归解码的模型仍需人；它自己把定位钉死在"**受约束的自动化执行器**，不是端到端自主求解器"。

## 核心方法（细颗粒度）

### 1. 问题与自我定位

- 论文自己承认的缺口（§1.1）：研究型模型代码到边缘运行时之间隔着 ONNX 转换、算子替换、动态形状消解、图修复、运行时集成、前后处理适配、精度校验、硬件编译——"deployment remains a **knowledge-intensive and experience-dependent** task"。
- 研究问题（§1.2 逐字）："Given an existing deployment toolchain and validation workflow, can an LLM agent effectively take over repetitive engineering work in AI model deployment, and perform **bounded automatic repair** when conversion fails or runtime exceptions occur?"
- 关键句（§1.2，原文内层即双引号，故外层用「」）：「The key issue is not whether "an LLM knows every hardware detail," but rather whether, when domain knowledge is **explicitly provided** through Agent Skills, helper functions, and validation rules, the LLM can act as a task orchestrator and executor..."
- 论文类型（§1.4 自陈）："written as a technical report... rather than emphasizing large-scale statistically significant experiments under strictly controlled conditions."

### 2. 六阶段管线（§4.2，Figure 1 的文本形式）

```
PyTorch Model
 (1) 模型准备与 baseline 建立      ← golden reference（后面每一步都要回来比对）
 (2) ONNX 转换与接口校验          ← 前/推理/后 三模块拆分
 (3) QAIRT model build             ← --preserve_io / FP16 / Context Binary
 (4) 推理执行与精度对齐            ← AIPC loader 热补丁，不改原脚本
 (5) 量化与优化（可选）            ← W8A16 / W8A8；靠标准化前处理批量产校准样本
 (6) 性能分析与部署报告            ← qnn-net-run / snpe-net-run（论文自陈"still evolving"）
```

部署链本体（§3.1）：`PyTorch -> ONNX -> QAIRT (SNPE 或 QNN) -> Context Binary -> Runtime Inference`。

### 3. 三个介入层级的 model surgery（§4.4.1，本篇最可复用的结构）

| 触发事件 | 干预层 | 具体动作 |
|---|---|---|
| ONNX 导出失败 | **PyTorch 源码层** | 改 module 实现，消掉导出期的算子/形状不兼容 |
| QAIRT 转换失败 | **ONNX 图层** | patch 节点与属性，让转换工具能处理 |
| QAIRT 运行时失败（Context Binary 编译或推理异常） | **运行时接口层** | 按真实错误做兼容修复，必要时**回退到更早阶段**再修 |

- 手术的两类内容：动态形状→固定形状；不支持算子→等价算子组合。论文原句：「**AIPC treats model surgery as a core capability** in deployment automation rather than as an exceptional case.」

典型两级替换链（§6.1.4 YOLO26）：`Mod(a,b) = a % b` → `a - b*floor(a/b)` → **`floor` 在 QNN 转换也不被支持** → 必须再改写成纯基本算子组合 `Div + Mul + Sub` 才转得过去。论文说"this two-level replacement chain is the stage where **differences in agent behavior are most obvious**"。

### 4. Skills + 验证循环（§4.9 / §7.1 四条工程教训）

- Skills 不替代 SDK，作用是"provide **recommended steps and execution order**... explicitly constrain which repair level should be addressed first, and supply common failure patterns and suggested repair paths, thereby **reducing strategic drift** in long deployment chains"。
- 结论句（§4.9，原文内层双引号且逗号在引号内，故外层用「」）：「AIPC's automation capability comes largely from the combination of "**structured knowledge + tool capability + validation loop**," rather than from relying only on a stronger base model.」
- 四条教训逐字：**Modularity comes before end-to-end monoliths** / **Skill packaging comes before free-form prompting** / **Every step needs a verifiable exit** / **Human intervention should be treated as data, not failure**。
- 接口守恒策略（§4.5.1）：优先 `qnn-onnx-converter --preserve_io` 保 IO 顺序，代价是"may reduce performance in some cases"；副作用被明确记录——某些 SoC 上隐式保 FP I/O 会触发 `SocModel FP16 not supported`，workaround 是**绕开 QNN 量化路径改走 SNPE DLC 量化流**或不保 FP I/O。
- 精度顺序（§4.5.2）：NPU 模型**先 FP16**（易验精度、不需要校准数据），把量化不确定性推迟到阶段 5。
- 反 API 幻觉设计（§4.6）：`python aipc inference.py` 热补丁把 `onnxruntime` import 重定向到 `onnxwrapper`，或显式 `import onnxwrapper as ort; ort.InferenceSession(..., backend="QAIRT")`。三点好处原文：reduces API hallucination / facilitates alignment verification / limits the scope of changes。

### 5. 评估设计（§5）

- **执行协议 = 自然语言 prompt 五段**：`create example of [model]` → `create aipc project` → `show project configs` → `do all work for the plan` → 记录部署报告。
- **三个指标**：人工介入次数 / 端到端墙钟时间 / 失败模式类型。
- **数据口径（§5.4 关键句）**："Each row in the tables corresponds to **one independent run from scratch** and records the actual result of that run, **rather than a statistical average over repeated trials**."；成本"reported as an **empirical token-based estimate for reference only**"。
- **环境**：主实验开发机 = 目标机 = Snapdragon X Elite2（Win11，**消除了远程部署步骤**）；第二环境 x86-64 Ubuntu 24.04 主机 → Qualcomm RB8 ARM 板，经 SSH 传 artifact + 上板推理。QAIRT SDK 2.42 / QAI AppBuilder 2.0，"No additional specialized plugins were installed"。
- **两组 agent**：定量组 Qwen 3.5 Coder（32K, Qwen CLI）/ MiniMax 2.5（245K, OpenCode）/ MiMo-V2-Pro（1M, OpenCode）；部分阶段组 GPT-5.3 Codex（128K, Codex CLI）/ Gemini 3.1 Pro & Flash Preview（1M, Cline）/ Claude Sonnet 4.6（200K, Cline），全部 **auto-approve 连续执行模式**，模型状态截至 2026-03-30。
- **测试模型 7 个**：ESRGAN（超分，最规则）、YOLOv8（后处理 NMS 解耦）、LPRNet（MaxPool3d 导出失败）、YOLO26（新架构、算子兼容演进中）、YOLO-World（Einsum + 跨模态接口）、Whisper（编码-解码 vs NPU 固定形状）、DeepSeek-R1（**只作延伸观察，不进定量比较**）。
- ⚠ 复现口径（§5.2）："In the latest toolkit version, operator patching is supported by an **operator-patching database**, making many cases easier to resolve. To reproduce the original issue, the operator-patching database should be removed."

> "AIPC can complete deployment **from PyTorch to runnable QNN/SNPE inference within 7-20 minutes** for structurally regular vision models, with indicative API costs roughly in the range of **USD 0.7-10**."

### 负面结果 / 失败案例（论文报告了的部分）

1. **Whisper**：encoder 能上 NPU，**decoder 常回落 CPU**（动态形状 × 自回归 × NPU 固定形状批量偏好）；静态 reshape + 显式暴露 KV Cache 可能让 decoder 也走 NPU，但"still in an early exploratory stage, and the **experimental results have not yet been systematically organized**"（只有 MiMo-V2-Pro 的初步可行性）。
2. **DeepSeek-R1**："cannot yet complete deployment **reliably without significant human participation**."（不进定量表）
3. **本地小模型当驱动层全灭**（§6.2 逐字）："This paper also explored using lighter locally deployable models such as **gpt-oss-120b, Qwen-Next-80b, and Gemma 4**... **none of these models could stably complete functional verification** within the AIPC workflow, and they often experienced workflow interruptions."
4. **四类反复出现的失败模式**（§6.2.1，且论文强调它们**不是能力问题**）：① 无视 Skill 约束陷入反复试错（"each attempt lacked a clear validation exit, errors accumulated"）；② 把算子补丁**写盘成 ONNX 文件**再往下走，破坏可复现性（"The root problem is **noncompliance with the AIPC operation convention**, not lack of technical ability"）；③ 误判运行平台架构（Win on ARM 判成 x86_64）——原文「a form of "**silent failure**"」……「an incorrect premise formed during environment perception that **poisons all subsequent reasoning**」；④ 接口命名/文档含糊导致过早放弃（onnxwrapper 只实现 QNN 后端却留着 SNPE 语义的名字）。
5. **量化阶段未纳入完整评估**（§5.6）："The experiments in this paper mainly use QNN FP16 mode. The quantization stage requires appropriate calibration data and is **not yet included in the complete evaluation range**."
6. **报告阶段未定稿**（§4.8）："The implementation of this reporting stage is still evolving and **has not yet been finalized**"（原文其后接 ", but it already provides a basis for subsequent performance optimization and experience reuse"）

### agent 横向定性结论（§6.2，论文明确说不做排名）

- **Qwen 3.5 Coder**："Overall stable in standard workflows and usually able to follow Skill constraints step by step."
- **MiniMax 2.5**："still more prone to **workflow drift**, misinterpreting hardware warnings, or **bypassing Skills** to directly invoke low-level commands"（原文其后接 ", increasing runtime and result variance"）
- **MiMo-V2-Pro**："relatively high adherence to Skill constraints, and **zero-manual-intervention completion** on several structurally regular models."
- **中心结论（逐字）**："in deployment tasks, an agent's ability to **follow the workflow** is as important as its platform knowledge. A **medium-capability agent that follows process strictly** is often more suitable for engineering automation than a stronger but frequently drifting one."

**论文未报告**：任何重复试验的方差/置信区间；各 agent 在同一模型上的统计显著性差异；量化精度损失数值；Whisper 上 NPU 覆盖率；报告阶段产出格式。

## 与 DWC 的映射（机制｜DWC 现状｜判定，代码级具体）

| AIPC 机制 | DWC 现状（代码级） | 判定 |
|---|---|---|
| **每阶段一个可验证出口**（"Every step needs a verifiable exit"：golden output / shape check / path check / 数值比对贯穿全流程） | `organs/judge.py::score()` 同时报 `pass / fail / **not_evaluated**` 三个数，"未评价不许当 False 也不许当 True"；`regression_check()` 要求**两边判过的任务集合必须相同**才可比 | **确认型**（DWC 更严：AIPC 无"不可比"这个概念，只有过/不过） |
| **三级修复层级**（PyTorch 源 / ONNX 图 / 运行时；失败事件 → 该在哪一层改） | `organs/applier.py` 是唯一写可写面的器官，判据1 = setattr 后**读回比对**，判据2 = 必须有回滚路径；`evolver` 的 `editable_vocab()` 限定可改面 | **半有**：写后读回+回滚已同型；**缺"失败该在哪一层修"的分层定位**——DWC 的失败签名 `(c,q,m)` 不带"修复层"字段 |
| **Agent Skills 显式注入领域知识**，约束 repair level 与修复路径 | `config/dial_config.py` + `config/anchors/` 是可执行配置；`evolver.editable_vocab()` / `k1_coverage()` 规定"什么能改"；judge 的 `TRUTH_SOURCE` 指向 agent 不可写文件 | **同型确认**：`editable_vocab` 就是 DWC 版的"工程化空间"（AIPC 原话："let the agent work inside an engineered space"） |
| **"Human intervention should be treated as data, not failure"** + 未来工作 `error occurs -> query knowledge base -> apply repair -> validate result -> write back new knowledge` | 已实现：`MemoryKind.FAILURE_SIGNATURE`（进 EXPERIENCE，D6 门槛要求 `(c,q,m)`）→ `MemoryKernel.dream(c,q,m)` 把 N 条同类失败归纳成一条候选技能 `{"scene","method","boundary"}`，且**只读、不落库**，采纳由 learn/evolve 决定 | **强对应**：AIPC 只写在 §8.1 future work，**DWC 已经是它的实现形态**（dream = 错误知识库的读+归纳侧；写回侧由 evolver→applier 承担） |
| **失败模式：环境感知形成错误前提 → 污染后续全部推理**（Win on ARM 误判 x86_64） | `applier` 判据1 明写"治母巢 P0-3：返回 ok:True 但零副作用"；`judge`/`weakness`/`el_sched`/`replay`/`world_model` 全部带 `TRUTH_SOURCE` 声明 + 启动期 `_check_truth_source` raise | **确认型**：DWC 的"声明真值源 + 拿不到就 raise"正是对付静默失败的同族手段 |
| **成本放大风险**（一次未恢复的偏差 → USD 5 → 2–7×） | `el_sched.py` `B_WINDOW=8, TAU=6/8`，`STATUS_INSUFFICIENT/STALLED/NEXT_ENV/NEXT_GEN` 四态；`weakness` 的 `stall_signal(window, delta)` | **可迁移的度量思想**：DWC 目前**没有"修复链长度/重试成本"这类度量**（论文未报告 → DWC 也没有对应物），但 EL 调度的窗口结构可以直接挂上"连续多少次未恢复即判定漂移" |
| **模块化优先于端到端单体**（前/推/后三分，便于定位与批量产校准数据） | `WorldTree` 的 `observe(score, success)` 由调用方从 judge 回填；`replay.py` 只读与重排，"绝不生成新节点" | **同型确认**（同一思想：把可验证部分与不可验证部分物理分开） |
| **人工介入计数作为核心指标** | DWC 无人工环节，无该度量 | **不适用**（DWC 当前阶段无此物，不是缺陷） |

**最该抄的一条**：AIPC 的"失败事件 → 修复层级"映射表（§4.4.1 三行）。DWC 的 `(c,q,m)` 签名已经能聚类失败，但**不指出去哪一层修**；补一个 `repair_layer ∈ {actor 源码, 候选生成, judge 锚点, 配置}` 字段即可，落点是 `memory.py::EXPERIENCE_REQUIREMENTS[MemoryKind.FAILURE_SIGNATURE]` 加一个必填字段（D6 同款写入门槛，改动面极小）。

**不可迁移的**：QAIRT/SNPE/QNN 工具链知识本身（与 DWC 无关）；`--preserve_io`、量化校准、Context Binary 等硬件细节；以及**它全部结论所依赖的"有真实部署任务可跑"这个前提**——DWC 没有部署管线，所以 AIPC 对 DWC 的价值**只在方法论层（分层修复 + 验证出口 + 错误知识回写），不在任务层**。

## 综述 L 定位

- **L 几**：**L1（Autonomy over Improvement Execution）**，六个 pipeline level 中的**部署优化层**。综述 2609.11873 §3.2.5 标题即 `Deployment-Optimization Level`，AIPC 是该层的代表条目。
- **综述表格原行**（三列 = 任务 / 机制 / 外部固定约束）：`AIPC | Su et al. [2026] | Model deployment | Skill-guided deployment adaptation | Human-defined deployment procedure`。
- **综述正文原句**（§3.2.5）："AIPC encodes this deployment expertise into standardized, verifiable stages supported by Agent Skills and stage-wise validation. Given a trained model and a target Qualcomm AI Runtime environment, the AI agent executes the **predefined** deployment procedure to convert the model, handle deployment incompatibilities, perform quantization calibration, and validate the resulting implementation."
- **技术族**：Agent Skills 知识注入 + 分阶段验证循环 + 有界修复；对应 L1 的两个评估维度 **execution reliability**（能否在变化条件下正确执行规定过程）与 **persistence safety**（错误进入后续轮之前是否被发现）。
- **structural / effective 判定**：**两者均不成立，且不适用**——AIPC 没有持久修改"负责未来改进的机制"（Skill 与流程由人写，agent 只执行），按 11873 的定义连 structural 的门槛都没碰。它的 §7.1"把人工介入审阅后并入 Skill/流程模板"与 §8.1 错误知识库回写，**若落地则触及 L4（运行反馈改组件）**，仍不是 L5。本篇在 RSI 图谱中的角色是 **L1 层的部署侧证据**，不是递归系统。

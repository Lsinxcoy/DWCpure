## 一句话总结

一个把“**判分 = 比终态**”做到底的基准：每个域由 JSON 数据库 + Python API + Markdown 政策文档 + 用户场景标注组成，LM 扮用户与 agent 多轮对话，episode 结束后把**数据库终态与唯一标注真值比对**（`r = r_action × r_output ∈ {0,1}`），并提出 **pass^k**（k 次独立同任务试验**全对**的概率）来度量可靠性而非平均分。结果：gpt-4o function calling 在 τ-retail pass^1 = **61.2**、τ-airline **35.2**，但 **pass^8 掉到 <25%（retail）**；115 条零售轨迹的失败分解为**数据库推理错（约 55%）、规则理解错（25%）、复合请求漏做（19%）**；把政策从 system prompt 里拿掉，gpt-4o 在 airline 掉 **22.4pp**。综述只在 §1.1 把它当“端到端开发成本成为瓶颈”的证据引一次 ⇒ 在 L 框架中属 **框架外的评估协议**，但它给出的 pass^k 正是 effective 判定里“同预算独立评估”那一半需要的口径。

## 核心方法

### 1. 形式化与四件套（§3）

- 每个任务是一个 POMDP（S, A, O, T, R, U），且 `S = S_db ⊗ S_user`、`A = A_db ∪ A_user`、`O = O_db ∪ O_user`；政策文档的作用原文是 “one can think of this as partially describing the world model of the domain”。
- 数据库 “The contents of the database form the state sdb (Figure 2a), which is hidden from the agent and the user, and can only be read from or written to using API actions adb” —— agent 与用户都看不到库，只能经 API 读写；DB 转移是**确定的 Python 函数**，用户转移是**随机的 LM 采样**（gpt-4-0613），用户**看不到** agent 与工具的交互历史；用户发出 `###STOP###` 才结束 episode。
- 政策既有一部分**在 API 里硬检查**（用不在用户档案里的 payment ID ⇒ 返回 `"Error: payment not found"`），也有一部分**只在文档里**（行李额度按会员/舱位不同，但 agent 要自己在 `book_reservation` 里填数量）——附录原句：“The API does not check these for the agent, so the agent must make sure the rules apply before calling the API!”（改签与取消两节各出现一次）。

### 2. 任务实例与判分（§3）

- 任务实例两半：给用户的 instruction（**对 agent 隐藏**）+ 真值数据库写动作标注（可选真值输出）。关键设计约束（原文）：“The instruction sets up user identity, intent, and preferences in a way that guarantees only one possible outcome under the domain policy.”
- **reward**：`r = r_action × r_output ∈ {0,1}`，(1) 终态是否与唯一真值终态相同；(2) 对用户的回复是否包含必要信息（子串匹配）。原文自陈口径边界：“Note that r = 1 might be a necessary but not sufficient condition for a successful episode e.g., the agent might issue the return without explicit user confirmation, which violates the policy.” ⇒ **规则遵循没被计入 reward**。
- **pass^k（新指标）**：k 次独立试验**全部成功**的任务概率（跨任务平均），无偏估计 `C(c,k)/C(n,k)`；对应 `pass@k = 1 − E[C(n−c,k)/C(n,k)]`；默认主指标 `pass^1 = pass@1 = E[r] = E[c/n]`。用途原文：“pass^k can capture the reliability of the agent at handling variations in conversations with the same underlying semantics while adhering to the domain policies and rules.”
- **Table 1 逐格**：

| | τ-retail | τ-airline |
|---|---|---|
| Databases | 500 users, 50 products, 1,000 orders | 500 users, 300 flights, 2,000 reservations |
| API tools | 7 write, 8 non-write | 6 write, 7 non-write |
| Tasks | 115 | 50 |

### 3. 构造三阶段（§4）

- **Stage I 手工设计** schema/API/政策，理由原文：“Simplicity is important for the logical consistency of various components and the ease of API and task annotation”，但 “a minimally realistic domain requires at least tens of schemas, APIs, rules”。
- **Stage II LM 生成数据**：“we create an example entry and use gpt-4 to generate a systematic code snippet to sample scalable entries, and manually polish minor bugs in the code”（附录 B.2 给出完整 users 生成代码：城市-zip 表、姓名表、Poisson 采样支付方式、500 用户）。
- **Stage III 手工标注 + agent 试跑消除歧义**：难点原文 “the key challenge is to ensure the user instruction leads to a unique database outcome”；做法是先写 instruction、用 gpt-4-turbo FC agent 试跑、看轨迹改写，直到确定无歧义——“gpt-4-turbo trials and check all tasks with zero or low success rates”，且 Fig 7 说明**每道 τ-retail 题至少 40 次 gpt-4-turbo 试跑**。
- **两条权衡（原文）**：“we trade off quantity for quality”；“we trade off slow, careful task annotation for fast, faithful evaluation.” ⇒ 用慢标注换掉主观人评。

### 4. 两域政策的“规则形态”（附录 B.1）

- **认证不可跳过**（原文）：“At the beginning of the conversation, you have to authenticate the user identity by locating their user id via email, or via name + zip code. This has to be done even when the user already provides the user id.”
- **写前显式确认**（原文）：“Before taking consequential actions that update the database (cancel, modify, return, exchange), you have to list the action detail and obtain explicit user confirmation (yes) to proceed.”
- **一次写保护**（原文，retail 政策正文，注意是 `changed` 不是 `exchanged`）：“Exchange or modify order tools can only be called once. Be sure that all items to be changed are collected into a list before making the tool call!!!”
- **airline 行李矩阵**按会员 × 舱位（原文首行）：“If the booking user is a regular member, 0 free checked bag for each basic economy passenger, 1 free checked bag for each economy passenger, and 2 free checked bags for each business passenger.” 另有支付组合限制（1 张 travel certificate + 1 张信用卡 + 最多 3 张 gift card）、basic economy 不可改签、24 小时内可免费取消等；这些是**多跳推理题**，也是 §5.2 的主要失分点。
- 还有两条交互约束：一次只发一个工具调用且不同时回话；**当且仅当**超出能力范围才转人工。

### 5. 评测协议（§5）

- 方法三选一：**function calling（FC，system prompt = 政策）**、文本 ReAct、Act-only；并明确排除两类方法（原文）：“Notably, some agent methods are not suitable for a user-in-the-loop setup, e.g., self-reflection [19] is unrealistic as real-world agents only have one chance to serve the user”。
- 约束（原文）：“We limit each task to at most 30 agent actions (either tool calls or user responses).”；主结果每题 ≥3 次 trial；“The LM temperature is 0.0 for agent and 1.0 for user.”；不测 7/13B 小模型（“due to the difficulty of the benchmark”）。

## 主结果

### Table 2 逐格（pass^1，除 Llama-3 走 text-ReAct 外均为 FC）

| Model | retail | airline | avg |
|---|---|---|---|
| **gpt-4o** | **61.2** | **35.2** | **48.2** |
| gpt-4-turbo | 57.7 | 32.4 | 45.1 |
| gpt-4-32k | 56.5 | 33.0 | 44.8 |
| gpt-3.5-turbo | 20.0 | 10.8 | 15.4 |
| claude-3-opus | 44.2 | 34.7 | 39.5 |
| claude-3-sonnet | 26.3 | 27.6 | 27.0 |
| claude-3-haiku | 19.0 | 14.4 | 16.7 |
| gemini-1.5-pro | 21.7 | 14.0 | 17.9 |
| gemini-1.5-flash | 17.4 | 26.0 | 21.7 |
| mistral-large | 30.7 | 22.4 | 26.6 |
| mixtral-8x22b | 17.7 | 31.6 | 24.7 |
| meta-llama-3-70B | 14.8 | 14.4 | 14.6 |

- 原注（原文）：“Average is weighted by domains, not by tasks.” ⇒ (61.2+35.2)/2 = 48.2，算术自洽（已核）。
- **airline 普遍更难**：12 个模型里 **9 个** airline < retail；3 个例外 claude-3-sonnet（27.6>26.3）、gemini-1.5-flash（26.0>17.4）、mixtral-8x22b（31.6>17.7）**retail 侧都很差**，属“双差”。gpt-4o 是唯一过 35 的模型，**最好的模型也只解掉三分之一航旅任务**。
- 开放权重差距：llama-3-70B 14.8/14.4、mixtral 17.7/31.6 ⇒ 原文 “SoTA open-weight models (llama-3-70b and mistral-8x22b) still have a significant gap to cover with respect to SoTA”（此句在提取层被 Table 2 打断，后半为 proprietary models）。

### 方法与可靠性（Fig 3 / Fig 4 / §5.1）

- 方法：原文 “natively supported function calling consistently out- performs text-formatted agent methods with the state-of-the-art models”（`out- performs` 为提取层断词）；“For text-formatted agent methods, adding reasoning traces still consistently helps (compare ReAct vs. Act columns)”；给 FC agent 加一个 “think” 函数无效——“it did not boost performance, perhaps because most FC models have not been trained toward such reasoning.”
- **pass^k 崩塌**（原文）：“the chance of reliably and consistently solving the same task multiple times significantly drops as the number of trials k increases.”；引言给的量化值是 pass^1 ≈ “(∼61% onτ-retail and∼35% onτ-airline)”（原文 `onτ-` 粘连），k 增大后 “to as low as∼25% for pass^8 onτ-retail” ⇒ **平均 61% 的任务，8 次全对的概率不足 25%**。
- 成本（原文两句）：“the agent / user simulation costs are $0.38 / $0.23 per task respectively, so running one trial per task costs around 200 dollars.”；“the input prompt / completion output take up 95.9% / 4.1% of the price respectively, so the cost is mainly due to long system prompt (domain policy + function definitions).” ⇒ **成本几乎全在输入侧的政策+函数定义**。
  - 算术核（本报告做的）：115 题 × ($0.38+$0.23) = **$70.2**；两域 165 题单次 = **$100.6**；每题 3 次 = **$301.8** ⇒ 与原文 “around 200 dollars” **三种口径都对不上**，原文未说明是否含多 trial/两域 ⇒ **标未核（原文数字内部口径不明）**。

### 失败分析（§5.2 + Fig 5 + Fig 6）

- 抽样：τ-retail 每题 1 次 trial 共 115 条 gpt-4o FC 轨迹，“out of which 40 tasks have failed (pass^1=65.2%)”（**此 65.2 与 Table 2 的 61.2 不同**：Table 2 是每题 ≥3 次 trial）；人工复查后 “4 of them are caused by user instruction typo or ambiguity (and then fixed), and the remaining 36 failure cases are agent issues”。
- **三类失败与占比**：Fig 5 提取出四个数值 19.4% / 25.0% / 22.2% / 33.3% 与四个标签（Wrong argument / Wrong info / Wrong decision / Partially resolve），但**标签↔数值的对应在提取层不可读**；正文给出的口径是 Failure 1（wrong argument + wrong info）“These failures account for ˜55% of overall failures”、Failure 2 ““wrong decision-making” failures (25% of overall failures)”、Failure 3 “(19% of cases)”。按 55/25/19 反推可唯一对上四值：**Wrong argument 33.3% + Wrong info 22.2%（合计 55.5%≈55%）、Wrong decision 25.0%、Partially resolve 19.4%≈19%** ⇒ 该映射为**反推，标未核**。
- **数据库推理错的具体形态**：“gpt-4o FC agent only makes 0.46 tool calls with non-existent user/product/order/item IDs per τ-retail task, gpt-3.5-turbo FC / Act agents make 2.08 / 6.34”（幻觉 ID 率相差 4.5–14 倍）；另一类是“给错信息导致用户改变请求”（错误价格/漏 tracking ID）。
- **规则理解错**：例证是用户要换两件商品，政策规定一次写保护，gpt-4o “omits the domain knowledge and rule and decides to exchange one item first, resulting in the second item not being exchanged.”（C.2.1 Task 0 全轨迹已读）
- **复合请求漏做（19%）**：Fig 6 显示 ground-truth 写动作数越多越难（x = 0..4；gpt-4-turbo 与 gpt-3.5-turbo 两条曲线，**图内数值提取不可读 ⇒未核**）；例证 C.2.3 Task 42：用户要修**所有**订单地址，agent 只查了一个订单。

### 政策消融（Table 3 逐格）——本文最有解释力的一张表

| Model | τ-retail（有政策 → 无政策） | τ-airline（有 → 无） |
|---|---|---|
| gpt-4o | 61.2 → 56.8（**−4.4**） | **33.2 → 10.8（−22.4）** |
| gpt-3.5-turbo | 20.0 → 14.5（−5.5） | 10.8 → 9.6（−1.2） |

- 解读原文（retail）：“their successful cases mostly stem from using tools in an intuitive and common sense way, and that they may not actually be leveraging the policy documents to the extent possible.”；airline 上 “removing the policy hurts gpt-4o significantly (−22.4%) but gpt-3.5-turbo only slightly (−1.2%), suggesting the former follows rules at times but the latter does not has the capacity to process complex airline rules.”（原文 `does not has` 语法错误照录）
- **两表基线不一致（本报告核出）**：Table 3 的 airline/gpt-4o 有政策基线是 **33.2**，而 Table 2 同格是 **35.2**；差 2.0pp，**原文未解释**（Table 3 自身算术自洽：33.2−10.8=22.4 ⇒ 消融句用的是 33.2）⇒ **标出并存，不改数**。
- 结论（§6）：“agents built on top of LM function calling lack sufficient consistency and rule-following ability to reliably build real-world applications.”，并点名要补的四件事：一致性、规则遵循、long-horizon 信息跟踪与记忆、以及在**信息冲突时聚焦正确片段**——原文 “the ability to focus on the right pieces of information in context for the decision at hand, especially when there may be conflicting facts present.”

## 与 DWC 的映射

> 共享背景：DWC = 世界树(W1–W6) + judge 判分(C3') + δ 失败签名排序 + EL 调度(B/τ) + Dreaming 回放(K₂/β) + M>1 策略修订。

| # | 机制（τ-bench） | DWC 现状（代码级） | 判定 |
|---|---|---|---|
| 1 | **终态比对判分**：真值 = 标注的目标数据库状态；比终态而非比轨迹，允许对话随机 | `organs/judge.py`：`TRUTH_SOURCE = (("dev_anchors","…/config/anchors/dev.json"), ("test_sealed","…/test_sealed.json"))`，锚点文件 agent 不可写；`evaluate(task_id, split)` → `_diff`/`_compare` 规则比对 → `class Verdict` | **确认型**：两侧独立形成同一哲学——**判据放在被评对象写不到的地方、按状态比对**。τ-bench 的补充证据是“这样既客观又便宜”，DWC 已是同一形状，无需改 |
| 2 | **两因子 reward**：`r = r_action × r_output`（终态对 + 必要信息给到） | `judge.Verdict` = pass/fail + 失败签名 (c,q,m)；`pass_rate(v)=k/n over checks`；`overall_score()` 聚合多任务；**无“是否把必要信息告诉了用户”这一因子** | **缺**：DWC 只判“状态/输出对不对”，不判“**该说的说了没有**”。τ-bench 的 r_output 是子串包含检查，成本极低——若 DWC 有对外汇报环节（如报告/通知），可直接加第二因子；当前无人机交互面 ⇒ 暂不适用但**是已知缺口** |
| 3 | **pass^k 可靠性指标**：k 次独立同任务试验全对的概率，无偏估计 C(c,k)/C(n,k) | `organs/el_sched.py`：`B_WINDOW=8`、`TAU=6/8`，`record(bool)` 灌滑窗、`pass_rate` 未满 B 返回 **None**（`status="insufficient"`）、p̂>τ 才推进；`judge.regression_check()` 单批 Δ 出 `ok/regression`；`evolver.stall_signal(window, delta)` 做 Z6 卡住检测 | **半有（最值得补）**：DWC 已经是“**多次观测才下结论**”的窗口纪律（与 pass^k 同源），但窗口吃的是**平均通过率 p̂**，不是**全对概率**；而 τ-bench 证明 pass^1=61% 时 pass^8<25%，即**均值严重高估可复现性**。把 `C(c,k)/C(n,k)` 加进 `judge.score()` 的输出（只读已有逐次判分，不改判据），可直接暴露“δ 排序靠的分其实不稳” |
| 4 | **政策作为 system prompt + 政策消融**（拿掉政策看掉多少分） | `foundation/dial_config.py` 把规则写进**加载器**：`load_world_tree` 校验 Z2（sealed 任务数 ≥ n_pareto_min，缺失 `raise DialError` 而非通过）、Z4（candidates.persist=true、lineage=parent_id）、Z5（merge.require_all、log_rate）、Z6（stuck.n_stuck、on_stuck ∈ {switch_strategy, halt}）；difficulty 走 X1/X2/X3 | **同族但位置相反**：τ-bench 把规则交给被测模型**运行时遵从**（可被忽略，故需要消融测“用到了没有”），DWC 把规则写进**加载器**（违规即 raise，模型碰不到）。⇒ DWC 天然拥有 τ-bench 想要的“规则不可被忽略”，但**反过来缺那个测量**：DWC 没有“规则实际被用到吗”的消融/探针。可搬的是**消融法本身**——对某条铁律做一次性 A/B（关掉看回退多少）即可量化其贡献 |
| 5 | **失败三分类学**：数据库推理错 / 规则理解错 / 复合请求漏做 | `judge.classify_c(expected, actual)` 与 `classify_q()` 分配失败签名 (c,q)；`weakness.z_id_from_signature(sig)` → `z_id = "c:%s\|q:%s"`，`task_delta_map()` 取任务最大 δ 做排序偏置；`z_history_from_scores()` 显式三类（`__pass__` / 签名 / `__unsigned_fail__`） | **同构（二维编码一致）**：τ-bench 的“什么错了 × 什么模式”≈ DWC 的 c×q。差异：τ-bench 的类是人工读轨迹归纳（参数错/信息错/决策错/漏做），DWC 的 c/q 由**规则自动分配**（2609.06396 分工：c/q 归规则、m 归模型）。τ-bench 的三类可作 DWC c 枚举的**外部参照**，检验现有签名是否覆盖“复合请求漏做”这一类（DWC 侧无显式“漏做”签名 ⇒ 可能是盲区） |
| 6 | **唯一终态标注约束**：写 instruction 时保证“只有一种可能终态”，每题 ≥40 次 agent 试跑验证 | `config/anchors/dev.json` 的 golden reference + `SPLIT_TEST` 锁标签；`dial_config._sealed_task_count()` 读 `E:/ARSI/config/sealed_tasks.yaml`，缺失即报错 | **确认型（同一设计约束）**：两侧都要求“目标状态唯一可比”，否则判分退化为裁量。τ-bench 多的是**验证唯一性的动作**（>40 次试跑、零成功题逐题复查）——DWC 的 anchors 是否做过等价的“唯一可解性”验证，`judge.self_check()` 只查任务集与 provenance，**未见唯一性试跑 ⇒ 缺口** |
| 7 | **成本结构**：输入占 95.9%、输出 4.1%，主因是长 system prompt（政策+函数定义） | `harness/run_term.py` `CostLedger` 三账：`term_cost`（每 term 清零）、`cumulative_cost`（永不清）、`rejected_cost`（被拒候选也算进前两者） | **半有**：DWC 记账口径比 τ-bench 细（**被拒候选的成本不丢**，这是对 ARSI 的有意分歧），但**不按 input/output 拆分**、也不单列“常驻政策 prompt 的固定成本”。按 τ-bench 的 95.9/4.1，DWC 若把规则文档塞进 prompt，`rejected_cost` 会**低估**真实开销的主要部分 ⇒ 建议给 CostLedger 加 input/output 拆分 |
| 8 | **方法取舍**：FC > ReAct > Act；think 函数无增益；self-reflection/planning 不适合 user-in-loop | `llm/client.py` 为云端 API 接入；DWC 无 user-in-loop，有跨轮记忆与 `replay.py` Dreaming 回放（`replay_score` 的 V = max s_v − β₁N + β₂·N/k，β₁/β₂ 必传） | **不适用（且结论反向）**：τ-bench 排除 Reflexion 的理由是“真实 agent 只有一次机会”，而 DWC 恰恰**有跨轮持久记忆与回放**，该理由在 DWC 不成立 ⇒ 不可据此排除自反思类改法。其可搬的是**温度/步数上限要写死**（agent 0.0、user 1.0、≤30 动作）这类协议纪律 |

**最可搬的一条**：第 3 行的 **pass^k 进 judge 输出**。DWC 已经在做多观测（EL 的 B=8 窗口），缺的只是把“平均”换成/并列一个“全对概率”；τ-bench 用同一份数据证明两者能差 36pp（61.2 vs <25），这正是 δ 排序与回归判定最怕的那类虚高。

**不可搬**：LM 用户模拟器与“唯一终态”构造法。前者需要 gpt-4-0613 级别的模拟器与每题 ≥40 次试跑的标注预算（且论文自陈因此引入 gpt-4-turbo 调优偏差），后者是**任务设计期**的约束——两者都属于“造基准”，不属于 DWC 现有的改进回路。

## 综述 L 定位

> L 框架（2609.11873 §3）：B0 任务内 / **L1 执行人定程序** / L2 自主选改法 / L3 自定学习议程 / L4 部署改持久态 / L5 改改进机制本身；structural = 改动持久并控制下一轮，effective = 同预算独立评估下产出更好后继。

- **L 几：不在 L 分级里（框架外的评估协议）**。回综述核：f=1，唯一引用位置 = **§1.1**，且**不在 Table 2（族 × 等级）也不在 Table 3（L1 代表系统）**（refmap 书目仅 `Cited by: §1.1 .`）。引用语境是 RSI 动机里的“开发成本瓶颈”句（原文）：“As AI systems take on more demanding tasks, the cost of scaling this end-to-end development process becomes a bottleneck”（后接四条引文：Patwardhan et al. [2026]、Phan et al. [2025]、Jimenez et al. [2024]、Yao et al. [2024]） ⇒ 综述把它当**端到端开发/评估代价**的证据，而**不是**任何自改进系统的实例；τ-bench 自身也没有 improver，不构成 B0 以上任何一级。
- **技术族**：无（它是度量侧，不是方法侧）。最接近的角色是 **effective 判定的度量工具**——L 的 effective 定义要求“同预算独立评估下产出更好后继”，而 pass^k 恰是“同预算、多次独立试验”的一种**严格口径**（比 pass@1 更适合判“更好”是否可复现）。
- **structural / effective L5：均不适用**：它不改任何系统的持久状态，也不产出后继。
- **与 DWC 的关系**：按共享背景，DWC 现处 L4 形状（记忆/技能持久改）+ L1 判据（判据人定固定）；τ-bench 对 DWC 的价值是**给“判得好不好”提供两件工具**：① 终态比对这一判分口径（DWC 已有，属**确认型**）；② pass^k 这一**可靠性读数**（DWC 没有，属**缺口**）。若 DWC 要主张自己某轮改动是 effective，单批 `pass_rate` 的 Δ 不够——这正是 §5.1.2 里两篇论文（Phi-4 的 50 次重复、τ-bench 的 pass^8）共同指向的地方。

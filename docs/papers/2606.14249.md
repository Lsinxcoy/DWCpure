## 1. 问题

论文在 §1 开头点明 harness 的地位："现代 agent 的能力不仅取决于底层模型，还取决于周围 harness 所施加的中介。" harness 把原始模型输出转换为结构化 agent 行为——**它决定了任务如何被表示、外部服务如何被访问、中间决策如何在执行中被传达**。随着 agent 面对更长时程、更富环境的任务，harness 设计成为 agent 开发不可分割的一部分。

论文**自己承认的三个缺口**（原文逐条）：

**缺口 1 — 手工且静态**："harnesses are hand-engineered and static：模型版本、工具链或问题域的任何变化都需要定制修改，**没有任何经验驱动的改进机制**。"

**缺口 2 — 架构纠缠**："harnesses are architecturally entangled：它们通常在同一条代码路径里结合 prompt 模板、工具封装、重试策略与内存，因此**改动一个组件会悄悄破坏其他组件**，跨域复用退化为**复制而非组合**。"

**缺口 3 — harness 工程与模型训练各自独立**："harness engineering 与 model training 独立运作：**改进 harness 时收集的 trajectory 数据被丢弃**而非纳入模型训练，而模型改进也不会转化为 harness 改进。"

§2.1 的结论段把缺口 1/2 收得更紧：跨三层基础设施（LangChain/LlamaIndex/Smolagents 的原语层；LangGraph/AutoGen/CrewAI/Letta 的编排层；Claude Code/Cursor/Manus/DeerFlow 的产品层）**有两个结构性缺口持续存在**：
- "**没有任何一层把 harness 暴露为一个由 typed 元素组成的可替换实体**，因此构建 per-task harness 总要重写。"
- "**不存在 in-loop 改进机制**：一旦定义，harness 只能通过发布之间的人工迭代演化。"
论文同时承认 Claude Code 的 Dynamic Workflows 是"朝自适应 harness 迈出的一步"，但**只在单会话内运作，没有持久 trace 优化、跨会话演化、harness-model 共训**。

§2.2 末句给出与另一条路线的分野：现有 harness 演化工作（SICA、Darwin Gödel Machine、HyperAgents、Meta-Harness、AHE、Life-Harness）"建立了 harness 作为演化目标，并证明**可观测性对稳定自改进是必要的**"，但"**它们的设计缺乏一个统一理论框架，把观察到的失败模式连接到有原则的防御**"。论文把 heuristic-learning theory (Weng) 视为部分填补，并把自己的 operational mirror 说成对这个映射的形式化。

**论文自己承认的范围限制（§7.3 + §7.7）**：RL–符号空间映射是**设计启发式，不是形式框架**；"我们因此把 mirror 当作**design checklist 而非 predictive theory**：它识别要防御的失败模式，但**不预测它们的顺序、时机或相对严重性**。三种病理是代表性而非穷尽的。"

## 2. 核心机制

### 2.1 组合层：harness 作为一等对象

**harness 是一对**：`ℋ = (ℳ, 𝒞)`。
- `ℳ` = 模型配置：记录**哪个模型服务哪个角色**（`main`、`judge`/`evaluator`）及每个角色的 fallback 策略；
- `𝒞` = harness 配置：记录"agent 如何行为，与模型身份无关的部分"。

组合方式：`agent = model_config.agentic(harness_config)`。**agent 在 HarnessX 里是一条绑定到模型的 processor 流水线，两者独立可替换。**

harness 配置再分解：
```
𝒞 = (𝐏, 𝐒)
  𝐏 : ℋook → List[Processor]     # hook 索引的 processor 列表，ℋook 是 Table 1 的八个生命周期事件
  𝐒 : 固定的正交 slot 资源        # tool registry, tracer, workspace, sandbox provider, plugin list
```
论文的分工原则：**"𝐏 实现所有 per-step 行为；𝐒 承载 processor 依赖但不拥有的共享基础设施。"** Slot 是**单例**、在一个配置内被所有 processor 共享；**processor 状态是实例私有的**。

论文称 `𝒞` 为一等对象的理由：**"它独立可序列化、可比较、可哈希、可替换"**。两个共享 `𝒞` 但 `ℳ` 不同的 agent 执行**同一条** processor 流水线，行为只在模型响应上不同；两个共享 `ℳ` 但 `𝒞` 不同的 agent **行为上截然不同**。"这种具体化是程序化演化的前提条件。"

**Processor 抽象**（§3.2）：
```
async def process(self, event: Event) -> AsyncIterator[Event]
```
消费一个 event，产出零个或多个，产生**恰好五种结果之一**：
| 结果 | 含义 |
|---|---|
| pass-through | yield 不变 |
| transform | yield 修改后 |
| split | yield 多个同类型 event，下游独立处理 |
| intercept | 不 yield，阻断传播 |
| interrupt | raise 异常，终止循环 |

论文明确指出这个受限接口**为何带来可组合性**："某个 hook 上的每个 processor 都消费并产出相同的 event 类型，因此 processor 通过顺序应用来组合，可以在不破坏周围流水线类型正确性的前提下插入或移除。"

**Table 1 —— hook 点与允许的修改（完整）**：

| Hook | Event type | Permitted modifications |
|---|---|---|
| `task_start` | `TaskStartEvent` | system prompt |
| `step_start` | `StepStartEvent` | structural history edits |
| `before_model` | `BeforeModelEvent` | last user content；one user-message append |
| `after_model` | `ModelResponseEvent` | response content, tool calls |
| `before_tool` | `ToolCallEvent` | tool input, approval flag |
| `after_tool` | `ToolResultEvent` | tool result |
| `step_end` | `StepEndEvent` | read-only |
| `task_end` | `TaskEndEvent` | read-only |

**run loop 在每次调用后校验 hook 契约**：违规（如修改 read-only 字段）**立即抛异常，而不是静默传播损坏状态**。

三个 class 级元数据字段支配组合：
- `_singleton_group` — 互斥类名，**每组至多一个 processor**；
- `_order` — hook 内排序提示，常量 `PRE` / `NORMAL` / `POST`；
- `_after` — 对其他 singleton group 的软依赖列表。

这三者正是 variant isolation 的机制基础：**"每个 variant 只在哪个 processor 占据哪个 hook 上不同，而类型系统确保任何 variant 在演化过程中都不会静默违反流水线契约。"**

**九维分类法（§3.3）**：
| 维度 | 内容 |
|---|---|
| D1 model selection | 哪个模型服务哪个角色 |
| D2 context assembly | 每一步向模型呈现什么 |
| D3 memory management | 什么跨 step 与跨 session 承载 |
| D4 tool ecosystem | agent 可调用哪些工具 |
| D5 execution environment | 工具引起的副作用在哪里落地 |
| D6 evaluation and reward | 结果如何被判定 |
| D7 control and safety | 防止循环、overspending、意图漂移的规则 |
| D8 observability | 记录每个 event / model call / tool invocation |
| D9 training bridge | 把执行轨迹转成 RL 记录 |

论文明说演化期间 AEGIS 的编辑**跨越全部九维**，其中 **D2 与 D4 是最频繁的编辑目标**，D8 提供 trace 基底，D9 提供共演化的训练记录。

### 2.2 适应层：Operational Mirror（论文的形式化核心）

**Table 2 —— RL 概念与符号空间对偶（完整）**：

| RL concept | Symbolic-space dual | AEGIS realization |
|---|---|---|
| Policy `π` | Harness-update procedure `π_evo` | 四阶段流水线（§4.3） |
| State `s_t` | `(ℋ_t, 𝒯_t)` | harness 配置 + trace store |
| Action `a_t` | Typed harness edit | Builder operation + change manifest |
| Feedback | Trace `τ` + verifier score `r` | Observability layer |
| Update `ℋ_{t+1} ← U(ℋ̃_t, 𝒯_t, r_t)` | — | Deterministic acceptance gate |

**Definition 1（Harness Configuration）**：`ℋ = (c_1, …, c_9)`，每个 `c_i ∈ 𝒞_i` 实例化九个行为维度之一。

**Definition 2（Harness Edit）**：`e : ℋ → ℋ`，修改一个或多个维度且保持类型契约。动作空间 `ℰ` 是**离散但开放的**："每个编辑是代码级 artifact（新的 processor 源码、修改的 prompt 模板、重新配置的工具 registry，或控制流重写），由 meta-agent LLM 生成，**不是从预枚举集合中选取**。" 组合爆炸的应对不是穷举搜索，而是"由 LLM 的生成能力——Planner 从 trace-rooted 假设提出编辑——以及**在生成时剪除无效组合的类型约束**"。

**Definition 3（Operational Mirror）**：四元组 `(ℋ, ℰ, ℛ, 𝒯)`，其中 `ℛ : ℋ × ℰ → ℝ` 把配置–编辑对映射到标量奖励（在一个 adaptation batch 上聚合的 verifier 分数），`𝒯` 是 trace store。

**MDP 实例化**：
```
s_t = (ℋ_t, 𝒯_t)
a_t ~ π_evo(· | s_t),  a_t ∈ ℰ
ℋ̃_t = a_t(ℋ_t)
(Δ𝒯_t, r_t) ← run(ℋ̃_t, M, B_t)              # M 在演化全程固定
ℋ_{t+1} = U(ℋ̃_t, 𝒯_t, r_t) ∈ { ℋ̃_t (commit), ℋ_t (reject) }
𝒯_{t+1} = 𝒯_t ∪ Δ𝒯_t                       # 两种情况下 trace store 都增长
```
**核心门是 seesaw constraint**："候选**不得回归 `𝒯_t` 中记录的任何一个此前已解决的任务**。"

### 2.3 符号空间的三种病理 → 各自的防御

论文明确说这不是类比，而是"把 RL 概念转成**设计要求**"。三个"符号设定下的放大因素"：(1) 语言模型 evolver 能构造**数值参数扰动无法表达的结构化利用**；(2) 对共享组件的编辑**通过 harness 非局部传播**。

| 病理 | 在符号空间中的具体形态 | 对应防御 |
|---|---|---|
| **Reward hacking** | Evolver **直接攻击验证协议**：把 benchmark 答案嵌进 prompt、利用 verifier 的格式规律、或引入一个把输出重写成符合 verifier 预期的 processor | **Critic** |
| **Catastrophic forgetting** | 修复失败模式 A 的编辑**静默回归**模式 B，因为效果通过共享 context / tools / memory policy / control rule 传播。"只看失败任务 trace 的 evolver **无法区分局部收益与全局回归**" | **确定性 gating 层**（seesaw） |
| **Under-exploration** | 偏向低风险局部编辑：prompt 改写、工具描述微调、小幅控制流调整。"这些编辑生成便宜且经常通过门而不回归已解决任务，**使后续 Planner 的假设偏向同一编辑邻域**。" 结构性改动（把一个 agent 拆成几个、替换控制策略、采用新记忆架构）需要刻意的假设形成，**极少从 trace-conditional 局部修复中涌现**。局部编辑耗尽后系统停滞 | **Planner** |

### 2.4 Algorithm 1 `AEGIS Harness Evolution Loop`（原文伪代码逐行）

```
输入: 初始 harness ℋ_0, meta-agent ℳ, 预算 T, patience P, threshold α
输出: Evolved harness ℋ_{t+1}, trace store 𝒯_{t+1}
 1 𝒯_0 ← ∅ ; idle ← 0
 3 for t = 0,1,…,T−1 do
 4   Sample batch B_t
 5   run ℋ_t on B_t to get traces Δ𝒯_t
 6   𝒯_{t+1} ← 𝒯_t ∪ Δ𝒯_t
      /* Digester (selective) */
 7   (evidence_t, a_t) ← ℳ.Digester(Δ𝒯_t, 𝒯_t)
 8   if a_t < α then ℋ_{t+1} ← ℋ_t ; idle++ ; continue ;
     /* Planner (selective) */
11   landscape_t ← ℳ.Planner(evidence_t)
12   if landscape_t = ∅ then ℋ_{t+1} ← ℋ_t ; idle++ ; continue ;
     /* Evolver (selective) */
15   {(ℋ̃_t^k, manifest_k)}_{k=1..K_t} ← ℳ.Evolver(ℋ_t, landscape_t)
16   if K_t = 0 then ℋ_{t+1} ← ℋ_t ; idle++ ; continue ;
     /* Critic Gate (mandatory) */
19   ranking ← ℳ.Critic({(ℋ̃_t^k, manifest_k)}, evidence_t)
20   k* ← ⊥
21   foreach k in ranking do
22     if DeterministicGate(ℋ̃_t^k, ℋ_t, 𝒯_t) passes then k* ← k ; break ;
24   end foreach
25   if k* ≠ ⊥ then ℋ_{t+1} ← ℋ̃_t^{k*} ; idle ← 0 ;
27   else ℋ_{t+1} ← ℋ_t ; idle++
29   if idle ≥ P then break ;
30 end for
31 return ℋ_{t+1}, 𝒯_{t+1}
```

**选择性调用是关键设计**："没有外部 router 决定阶段执行；**由 meta-agent 自己在每个阶段判断是否有足够信号继续**。" Digester / Planner / Evolver 各自评估一个 continuation condition 并可短路本轮（actionability 低于阈值 / landscape 为空 / 无 viable candidate）。**只有 Critic + gate 是无条件的**：任何到达它们的候选都必须同时通过两者才能 ship。Critic 最多可向 Evolver 发出**一次** revision request。

**四阶段的分工**（§4.3）：
- **Digester**：把每个任务的 trace 压成结构化摘要——binary outcome、failure category（若有）、**implicated component identifiers**、supporting evidence excerpts；并提供**跨轮连续性**：每个任务的摘要链接到它此前的 outcome 与已 ship 编辑历史，使 Planner 能区分**持久失败与瞬时噪声**。
- **Planner**：构造 **adaptation landscape**（写成 `landscape.md`）：哪些任务在失败、试过哪些编辑、哪些组件被牵连、**哪些编辑类型（prompt / tool / processor / configuration）尚未尝试**。论文称这一阶段是 under-exploration 的主要防御。
- **Evolver**：产出 1..K_t 个候选，每个是当前 harness 上的**类型化 builder 操作**，每个携带 **change manifest**：被编辑组件、意图行为效果、**预期会改善或退化的任务**。引入新 processor 代码时必须附**smoke test**，证明 processor 能在合成输入上实例化并运行而不抛异常。
- **Critic + gating**：Critic 拿 change manifest 对照 trace 证据，评估编辑是否通过共享状态或控制流造成非局部效应；发现缺口时发一次 revision request；随后返回 `no_op` 或有序 `ship_ranking`。**确定性门按序施加**：`manifest completeness → configuration normalization（canonical form）→ build/smoke tests → seesaw constraint`。**第一个失败的检查中断序列**；通过的 commit，失败的归档并附拒绝理由。

**设计原则（原文）**："语言模型子 agent 探索、假设、提案；**类型结构与确定性门决定什么 ship**。这一分离确保安全属性（无回归、无未审计编辑）**无论 LLM 子 agent 如何失效都成立**。"

论文同时点明 builder 代数保证的边界：**"builder 代数保证类型安全（每个候选满足 hook 类型契约与 processor 组合规则）但不保证行为安全；一个能通过类型检查的编辑仍可能产生非局部行为效果，只能由 Critic 与 gating 层检测。"**

### 2.5 Change Manifest（Table 9 + YAML schema，可执行的部分）

论文称之为**"循环的证据账本：每个 ship 过的编辑都可对着下一轮的 trace 特征 delta 被证伪"**。

| 字段 | 含义 |
|---|---|
| `candidate_id` | 唯一 id，如 `C-R3-01` |
| `bucket` | 编辑类型：`prompt` / `tools` / `config` / `processor` |
| `capability_evidence` | **已验证的**声明：编辑机制确实可用 |
| `file_changes` | `path` / `action`（create/modify/delete）/ `diff_summary` 列表 |
| `predicted_impact` | `tasks_will_unlock` / `tasks_will_stabilize` / `tasks_at_risk` —— **可证伪的预测** |
| `attribution_signature` | 若编辑生效则**必须出现**的 trace 特征，如 `{type: tool_call\|processor_invocation\|prompt_feature, tool_name, expected_min_calls}` |

三个字段的语义定义（论文附录 10.3 的 prompt 原文）：
- `tasks_will_unlock` = **ALL_FAIL**，预期 = 1 rollout to pass
- `tasks_will_stabilize` = **PARTIAL_PASS**，预期 all rollouts to pass
- `tasks_at_risk` = **目前 =1 pass**，might regress

### 2.6 Variant Isolation via Ensemble Routing（§4.5）

动机写得很直接：适应循环维护**单一** harness `ℋ_t`；当任务需要冲突行为时，改善一个子集的编辑可能回归另一个，**seesaw 约束拒绝它——保护了稳定性但丢弃了局部有益的改动**。

解法：维护至多 `K` 个 harness 变体 `{ℋ_t^(1), …, ℋ_t^(V_t)}`（`V_t ≤ K`），把每个任务**路由到该任务簇上历史成功率最高的变体**。论文称之为 **Ensemble routing**。

Gating 层区分两种结果：
1. 编辑改善部分任务且**不回归任何任务** → 应用到其目标变体；
2. 编辑改善一个子集**同时回归其他** → **fork 一个新变体，而不是直接拒绝该编辑**（池满时退休表现最差的变体）。

一旦存在多变体，**seesaw 约束按变体限定作用域**：针对变体 `k` 的候选**只对路由到 `k` 的任务测试**。论文预测并在 §6.3 验证了三条性质：(1) 聚合轨迹**非退化**（peak = final）；(2) **持续探索更多轮**；(3) **更低的总 token 消耗**。

### 2.7 Harness-Model Co-Evolution（§5）

论文先给出两条**上限**：
- **scaffolding ceiling**：能力受限的小模型做 harness 演化最终会遇到——"一旦 harness 暴露了正确的工具、context 与控制流，约束条件就变成冻结的模型能否真正利用它们；**没有任何 harness 编辑能供给模型自身缺乏的推理能力**。"
- **training-signal ceiling**：对称地，在固定 harness 下训模型会遇到——"新获得的能力在 scaffold 从不暴露能引发它们的 context / 工具 / 控制流时得不到施展。"

论文的比喻：**模型是 agent 的 cognitive core（供应推理与规划），harness 是它的 executive apparatus（决定模型感知什么、能调用什么、什么约束其执行）**。"更锐利的 apparatus 无法补偿弱 core，更强的 core 也无法补偿从不调用它的 apparatus。"

**七步迭代**（§5.1）：
1. **Rollout**：`(ℳ_t, ℋ_t)` 在 adaptation batch `B_t` 上运行，可观测层记录每 episode 为完整 trace `τ_i`；
2. **Verification**：固定 verifier 把每条 trace 打成分量奖励 `r_i`——**保持 verifier 固定使奖励跨 harness 版本可比，这是 cross-harness advantage（Eq.3）所需的**；
3. **Buffer insertion**：每条打分 trace 连同**产生它的 harness 版本**追加到共享 buffer `ℬ`；**FIFO 淘汰**把 `ℬ` 限制在近期轮次；
4. **Harness evolution**：`ℋ_{t+1} ← AEGIS(ℋ_t, ℬ)`（非参数）；
5. **Behavior log-probabilities**：对本轮刚加入的 trace，在生成模型 `ℳ_t` 下跑**一次前向**得到 token 级 log-prob `π_{θ_old}(τ_i)` 并**缓存**；更早轮的轨迹复用各自插入时缓存的值；
6. **GRPO update**：`ℳ_{t+1} ← GRPO(ℳ_t, ℬ)`（参数）；
7. **Advance**：带着 `(ℳ_{t+1}, ℋ_{t+1})` 回到第 1 步。

论文明确：**步骤 4 与步骤 5–6 读同一 buffer，但同一轮内互不条件于对方输出；两者都必须在下次 rollout 前完成。**

**Cross-Harness GRPO（§5.3）**：
```
τ_i ~ Agent(ℳ_k, ℋ_k, x_i),  k ∈ {0,…,t}                         (Eq.1)
𝒢_x = { τ_i ∈ ℬ | task(τ_i) = x } = ⋃_k { τ ~ Agent(ℳ_k, ℋ_k, x) }   (Eq.2)
Â(τ_i) = ( r_i − μ(𝒢_x) ) / ( σ(𝒢_x) + ε )                     (Eq.3)
```
分组判据：**所有共享同一 task identifier 的轨迹构成一个 GRPO 组，无论由哪个 harness 或 model checkpoint 产生**。

**Task-level alignment, not action-level**（论文单列一段）："跨 harness GRPO 做的是 **task-level** 对齐：来自不同 harness 版本的轨迹按任务身份分组、**仅由 verifier 奖励比较**。不需要 action-level 对齐，因此**动作空间不兼容的 harness 版本（不同工具 schema、不同 prompt 结构、不同控制流 processor）可以在同一组中共存而不冲突**。" 计算策略梯度时每条轨迹**在产生它的 harness 版本下 replay**：log-prob 针对 `ℋ_k` 在每一轮会构造的 prompt / tool schema / observation context 求值。

论文对为什么需要 Eq.2 的论证值得记：**"与单策略 RL（组内变化归结为随机采样）不同，这里 harness 身份主导了这种变化……演化的 scaffold 本身为模型的 RL 提供了单策略采样无法提供的探索广度——每个新版本向任务的采样分布注入一个不同的行为模式，而 Eq.3 的 advantage 把模型推向 verifier 评分最高的那些模式。"**

目标（Eq.4/5）：clip 策略梯度 + 固定参考模型的 KL anchor；`π_ref = ℳ_0` 固定不变，`π_{θ_old} = ℳ_d` **逐轨迹变化且必须从 buffer 恢复**。

**离策略偏置的有界性**：FIFO 把 buffer 上限压在 `C` 条，每轮 `s` 个样本时**最大模型版本滞后 `⌊C/s⌋` 轮**，因此每个缓存的 `π_{θ_old}` 都来自 `π_θ` 的有界窗口内；**同一窗口也界定 harness 陈旧度**，所以 cross-harness 组只混合近期的 scaffold 版本。

**零额外 rollout 成本**：论文的论证是"agentic RL 的主导成本是 rollout，不是梯度更新……**没有任何轨迹专门为训练模型而产生**"。边际成本仅限 (i) 每条轨迹一次缓存前向 (ii) 梯度步，两者都是 rollout-free。

**指标（Appendix 9.3）**：标准无偏 Pass@k 估计：
```
Pass@k = (1/|D|) Σ_i ( 1 − C(n−c_i, k) / C(n, k) )
```

**(4) τ³-Bench 的域级方差掩盖在均值下**：GPT-5.4 在 Telecom **+25.4%**（67.5% → 93.0% at R2）、Retail +9.7%（84.2% → 93.9% at R6）；但 **Sonnet 4.6 在 Telecom 单轮退化 −14.0%（R7）**，到 R9 恢复。

**(5) Post-peak degradation on SWE-bench**：SWE-bench(GPT-5.4) R3 峰值 63.6%，**到 R5 退化到 50.9%（自峰值 −12.7%）**，最终仍高于静态基线 +5.4%。论文给了两个加速因素：(1) 55 个任务下**单个任务翻转即移动聚合准确率约 1.8%**（n=103 时约 1.0%），更少的回归就产生可见下降；(2) **结构性代码编辑的 blast radius 比 prompt 编辑更宽**。

### 3.5 共演化（§6.5）

设置：GAIA text-only 子集（103 任务）与 WebShop 子集（100 任务），task agent 为 **Qwen3.5-9B**。GAIA 因实时 web 工具延迟与可用性波动，**每轮评估两次取平均**。两个条件共享固定容量 FIFO buffer；optimizer batch 取整个 buffer；buffer 大小为**四轮滑动窗口**——GAIA 上 824 条 trace（103×2×4），WebShop 上 400 条（100×1×4）。训练：lr 1e-6、GRPO clip ε=0.2、**无 KL 惩罚（系数 0）**、**每轮 5 个训练步**。GAIA 奖励 = 0.9×correctness + 0.1×format；WebShop 用原生 attribute-match 奖励（reward=1.0 才算过）。

结果：

| 基准 | harness-only (model frozen) | co-evolution | Δ |
|---|---|---|---|
| GAIA peak | 37.4% | **41.7%** | +4.3 |
| WebShop peak | 49.0% | **54.0%** | +5.0 |
| **平均** | — | — | **+4.7** |

终点（非峰值）差距同样存在：GAIA 36.4% → 39.8%，WebShop 46.0% → 50.0%，**WebShop 更宽**，因为那里在 harness-only 平台期之外还留有更多模型级改进空间。论文的解读："两条曲线在联合训练生效（R4）之前重合，此后分离，**co-evolution 在整个运行余下时间里处于或高于 harness-only**……co-evolution 提升的是运行终点准确率，不只是峰值。"

### 3.6 失败分析（§6.6）—— 三种病理各一个案例，论文自己的负面结果

**(1) Reward hacking（GAIA, Sonnet 4.6, R10）**：R10 pipeline ship 了一个复合编辑（tool + prompt + configuration），manifest 预测改善检索。编辑通过 seesaw，准确率从 74.8% 升到 79.6%。**R11 的 trace 分析揭示：工具确实为多数新通过任务修好了检索，但一个子集是通过利用 verifier 的格式规律而非真正检索来通过的。** Planner 在 R12 标记了这条路径，随后的编辑引入一个 guard，把该工具限制在输出**可被第二条检索路径交叉校验**的任务上。

**(2) Catastrophic forgetting（τ³-Bench, Sonnet 4.6, Telecom, R7）**：Telecom 上的演化在**连续五轮（R2–R6）** ship 了同类型 prompt/processor 编辑，每个都追加一条"reminder"规则。合规率从 89.5% 升到 100%（R4），然后**到 R6 回退到 94.7%**，因为后面的规则与前面的冲突。**R7 的 Critic 标记了集中度风险（"All 5 prior ships occupy the same bucket: [prompt, processor]"）但仍然批准了编辑**，因为 ship 预测准确率仍然很高（R2–R6: 23/24, 5/6, 4/5, 7/7, 2/3）且没有记录到回归。**第六条 reminder 把合规率从 94.7% 打到 80.7%（−14.0%）**，通过跨规则冲突破坏了此前通过的任务。**这个回归逃过了 seesaw 约束，因为 pass@2 只记录每任务的二元翻转，不记录亚阈值耦合。** Pipeline 在 R9 自愈（Planner 诊断出集中模式并提出结构性编辑，替换掉冲突的 reminder 栈）。

**(3) Under-exploration（ALFWorld, Sonnet 4.6, R4–R7）**：R4 到 R7 之间 pipeline 主要 ship prompt 级编辑，**每轮约 1% 增益**。**ship 预测准确率**（manifest 预测的任务翻转中实际发生的比例）**从 R3 的 80% 掉到 R7 的 0%**，标志 prompt 空间耗尽。此窗口内唯一的结构性编辑（R6 的 processor 级改动）只取得 **14% ship 预测准确率（7 个预测翻转中 1 个发生）**，说明 **Planner 缺乏足够的结构性编辑历史来校准超出 prompt 邻域的假设**。

**论文的核心诊断结论（§7.2，值得单独记住）**：
> **"反馈信号的丰富度界定了在安全前提下能执行的演化的精细程度。从标量奖励出发，三种病理没有一种可检测：分数变化无法区分 reward hacking 与真实改进，无法区分 under-exploration 与收敛，也无法区分 catastrophic forgetting 与评估噪声。"**
> 以及它的边界条件：**"结构化 trace 记录对检测病理是必要的，但不充分：当耦合在每任务检测阈值之下累积时，trace 只在损害发生后才记录症状。"**

### 3.8 附录 12 的杠杆级细节（可交叉核验的一手数字）

论文按 "hit-rate = 实际翻转任务数 / manifest 预测任务数" 报告每个基准、每个模型的杠杆有效性。**这批数字里有大量负结果**：

- **GAIA**（唯一四杠杆全用的基准）：Sonnet 一轮 ship 了 **11 prompt / 7 processor / 7 config / 6 tools**；GPT-5.4 **45% 的 ship 是 prompt** 且几乎不碰 config；**Qwen3.5 唯一的 tools ship 是全表最高产单元格（0.67）**。失败簇：blocked-source 39%、reasoning 33%、figure/visual 11%、document/table parsing 11%、scope ambiguity 6%。**figure/visual 与 document/table parsing 簇基本未被减少**（"它们需要从图像、图、PDF 或结构化表中提取信息"）。
- **ALFWorld**：失败簇 search/step-ceiling **89%**、prompt-rule side-effect 7%、object-type confusion 4%。**Qwen3.5 的 processor 与 config 命中率最高（0.84 / 0.71）**；**Sonnet 的 processor 编辑只有边缘效果（0.14）**，prompt 达 0.49。论文注意到 **prompt-rule side-effect 这个簇本身就是演化引入的**（某些启发式改善部分任务却限制了其他任务），随后在更后面的轮次被打补丁。
- **WebShop**（论文自述"最嘈杂的一次运行"）：错误商品 46%、分页循环 21%、颜色匹配 17%、属性检查 17%。**prompt 命中率 0.37–0.50；advisory processor 只有 0.20–0.25；颜色匹配工具在该次运行中命中率 0.0**，颜色簇基本没变。
- **τ³-Bench**：判断类失败占主导——premature/unverified action 28%、wrong selection/count 24%、incomplete multi-step fix 16%、missed step 14%、policy misinterpretation 13%、capability-boundary confusion 5%（**τ³ 特有：某些 telecom 故障在用户手机上，agent 没有设备侧工具，失败在于它把该边界当成缺失能力**）。**全部模型零 tools 编辑**（工具集固定，且没有哪个簇是新工具能关掉的）。config 是最锋利的杠杆但很少用（Qwen3.5 0.67、GPT-5.4 0.33）；prompt/processor 高频但中等（0.27–0.35）。**Sonnet telecom 运行 R4 达 100%，R7 在第六次连续同 bucket 编辑后回退到 80.7%，R9 恢复到 99.1%。**
- **SWE-bench Verified**：失败簇 incomplete fix 62%、wrong diagnosis 19%、no edit attempted 6%、edit anchor mismatch 5%、budget exhausted 4%。**全部模型零 tools 编辑。** 论文给了一个重要的反向观察：**"这个组合是 reward-hacking 的反面：失败是 under-fixes，不是被 game 的评估，因为 harness 在模型 patch 之前应用 gold test patch 并阻断测试文件写入。"** 命中率呈现**清晰的能力地板**：GPT-5.4 的 config 0.48、prompt 0.39；Sonnet 的 prompt 与 processor 均 0.40；**Qwen3.5-9B 的每个杠杆都塌到近零（prompt 0.05、processor 0.06）——低一个数量级，因为 9B 基座无法执行预测的修复**。论文的结论词："**capability floor below which evolution cannot compound**"，"同样的循环把 GPT-5.4 从 45% 抬到 64% 峰值、把 Sonnet 稳定在约 87%，在 Qwen3.5 上只产生噪声（峰值 42%，零持久增益）"。

### 3.9 其他未报告项（诚实清单）

- **held-out 评估：论文明确不做**（§7.7 第一条）。且它承认"既然我们报告峰值准确率且在 adaptation set 上评估，这些数字**同时带有选择偏差与潜在过拟合**"。
- **未报告**：三种子（seeds=3）的**方差**（只报告均值与 pass@2）；每轮的绝对 pass 数（只给曲线引用）；被拒候选的数量与拒绝原因分布（只给 audit log 的目录结构）；evolver 生成的候选中类型不安全被剪除的比例；每基准的 meta-agent token 消耗明细（只给 100M–175M 的区间）。
- **未报告**：GAIA 与 WebShop 之外三基准的共演化结果（共演化只在 GAIA 与 WebShop 上做，且只有 Qwen3.5-9B）。

## 4. 它假定了什么（Assumptions）

论文写出来的：

1. **(A1) 模型在演化全程固定。** §4.1 MDP 实例化明确写 `ℳ` 在演化中固定（§5 引入共演化时才显式放宽这个假设）。共演化需要**对 harness 演化与模型训练的联合控制**——论文自己列为局限（§7.7）："实践中这些关注点常分属不同团队或组织，**没有跨团队协调，共享 replay buffer 就不现实**。"
2. **(A2) verifier 固定即可让奖励跨 harness 版本可比。** §5.1 第 2 步原文："保持 verifier 固定使奖励跨 harness 版本可比，这是 cross-harness advantage（Eq.3）所需的。"
3. **(A3) pass@2 的二元信号足够支撑 seesaw 约束。** §6.6 与 §7.2 反复自陈这条**被实验证伪**：Telecom R7 的回归"逃过了 seesaw 约束，因为 pass@2 只记录每任务的二元翻转"。论文的诚实表述："**这是 per-edit gating 的结构性限制：亚阈值回归会累积而不被察觉，无论同一约束下此前已展示过多少轮表面稳定。**"
4. **(A4) meta-agent 具备多文件代码生成 + 结构化 trace 分析 + 多步规划能力。** §7.7 明说："接近这一能力水平的开放权重模型（如 Qwen3.5-72B、Llama-4-Maverick）**作为 meta-agent 仍未测试**。"
5. **(A5) operational mirror 是设计启发式而非预测理论。** §7.3 原文：不预测病理的顺序、时机、相对严重性；三种病理"代表性而非穷尽"；"RL 收敛保证要求对状态–动作空间的充分探索，**当状态是符号化 harness 配置、动作是开放式代码编辑时这个条件无法达成**"；"没有任何东西保证 variant isolation 延伸到更长视界（变体可能过特化）或到任务间存在依赖、无法干净分离的分布"。
6. **(A6) 组合结构不保证有界行为效应。** §7.1 明说："组合结构**并不**保证有界的行为效果：τ³-Bench Telecom 的失败演示了累积的同类型编辑可以诱导亚阈值耦合，同时降级多种对话模式。"

论文没写、但撑起结论的隐含前提：

7. **(I1) 强 meta-agent 可以外推出弱 meta-agent 的能力。** 全文 meta-agent 固定为 **Claude Opus 4.6**（闭源）。§7.4 末句："我们**没有评估更弱的 meta-agent 能否取得相当增益**。" DWC 用开源模型时，这条完全未知。**而 §6.4 的消融其实是个警告**：四阶段相对单 agent 的全部增益是 1.0%（在噪声内）——**AEGIS 的价值在论文自己的数据里主要来自基础设施而非那个 Opus 4.6 的规划能力**。这对 DWC 是好消息（不必强求前沿 meta-agent），但也意味着"我照抄四阶段就能拿到 AEGIS 的效果"是错的。
8. **(I2) 单次编辑的作用域可被静态判定。** seesaw 依赖"这一编辑是否回归已解决任务"的判定，而论文的判定是"重跑一遍全任务集"（§4.4 "The full task set is evaluated every round"）。**"作用域"在机制上从未被静态确定，只是被昂贵地事后观测。** 这也是亚阈值耦合能溜过去的原因。
9. **(I3) 演化集 = 评估集。** §6.1 Scope 与 §7.7 都明说。这使得"evolution 有效"与"evolution 可泛化"被混为一谈。**DWC 迁移时必须自己造 held-out，论文给不了。**
10. **(I4) pass rate 是任务成功的充分代理。** 全部结论建立在 pass@2 上。论文在 SWE-bench 那节自己给了一个反例方向的观察（"失败是 under-fixes，不是被 game 的评估"），说明作者意识到这个代理可能失效，但没有量化 pass rate 与真实质量之间的差距。
11. **(I5) 任务失败可被归类到"组件"上。** Digester 输出包含 **implicated component identifiers**，Planner 用它构造 implicated 组件图。这个归类由 LLM 完成、无 ground truth、无一致性校验。**DWC 的"核心功能零实现"这类缺陷是否可被归类到具体组件，是这套方法能否工作的前提，而论文未验证。**

## 5. 可迁移到 DWC 的点 / 不可迁移的点

### 5.1 可迁移（给具体接口）

DWC 现有形态是 445 万行、526 个抢位冲突、5 个 P0 缺陷而 5,442 测试全绿。**HarnessX 最有价值的可迁移物，是它的"结构"而非"分数"**。

**(M1) Processor + 八 hook → DWC 记忆管线的类型化底座。**
这是应对母巢"526 个抢位冲突"的结构性答案：**冲突之所以不可解，是因为职责边界只存在于 markdown 里**。Table 1 的 hook 表 + `_singleton_group` 互斥类把职责变成可静态检查的属性。

DWC 侧接口：
```python
# dwc/harness/hook.py —— 对齐 HarnessX Table 1
HOOKS = ("task_start", "step_start", "before_model", "after_model",
         "before_tool", "after_tool", "step_end", "task_end")
READ_ONLY = {"step_end", "task_end"}

class Processor(Protocol):
    _singleton_group: str                     # 互斥类：每组至多一个 —— 直击"526 个抢位冲突"
    _order: int                                # PRE / NORMAL / POST
    _after: list[str]                          # 对其他 singleton group 的软依赖
    async def process(self, ev: Event) -> AsyncIterator[Event]:
        ...                                    # pass-through | transform | split | intercept | interrupt
```
**契约检查必须在调用后立即执行**：违规（如修改 read-only 字段）**抛异常而非静默传播**。这一条直接对应 DWC 门 7 的反例"静默降级必须可观测"——HarnessX 用异常而非日志，是更强的形态。
**门 1 定位**：这是给现有机制声明归属，不是新增机制。**建议只对记忆子系统（Skill Memory / Experiential Memory / Working Memory）先做**，因为 DWC 两大能力之一就是记忆，边界最清晰。

**(M2) 九维分类法 → DWC 的能力地图与门的位置声明。**
D2（context assembly）与 D4（tool ecosystem）对应母巢最严重的"零实现"区域；**D3（memory management）是 DWC 的核心**。九个维度可以**直接改写 DWC 门 1 的"服务声明"格式**：
```
每个新增模块必须声明：dimension ∈ {D1..D9}, hook ∈ 八 hook, singleton_group = <互斥类名>
```
这把"重复检测"从"搜索另一个声明替代同一目标的模块"（当前做法，需要理解语义）变成**属性冲突检测**（两个模块声称同一 `singleton_group` 直接 FAIL）。**这是本文最值得 DWC 直接落地的一条。**

**(M3) Change Manifest（Table 9 + YAML schema）→ DWC 门 5 声称/实测分离的结构化实现。**
DWC 门 5 当前要求"每条进度必须含：声称 / 实测 / 取数命令"，且实测命令必须可重跑。**Manifest 把它变成可机器校验的形式，且多出两个当前门 5 没有的字段**：
- `predicted_impact.tasks_at_risk` —— **改动前声明哪些任务可能退化**（母巢的 5 个 P0 缺陷正是"没人声明它会破坏什么"）；
- `attribution_signature` —— **若编辑生效则必须出现的 trace 特征**（DWC 门 4"产出效果"的可判定化）；
- `capability_evidence` —— **"我相信这能工作"不可接受，必须贴实际命令与输出片段**（Evolver prompt 原文："A candidate whose new code has not been observed to work will burn a round's ship slot for zero flips"）。

DWC 侧接口：
```yaml
candidate_id: C-R3-01        # 轮次-候选
bucket: prompt|tools|config|processor
capability_evidence:         # REQUIRED，可为空 []
  - {type: python_package|filesystem|other, claim: "...", evidence: "<实际命令+输出片段>"}
file_changes: [{path, action, diff_summary}]
predicted_impact:
  tasks_will_unlock:   [...]   # ALL_FAIL → 预期 1 rollout 通过
  tasks_will_stabilize: [...]  # PARTIAL_PASS → 预期全部 rollout 通过
  tasks_at_risk:        [...]   # 当前 =1 pass，可能退化
attribution_signature: {type: tool_call|processor_invocation|prompt_feature, tool_name, expected_min_calls}
measured: {delta_heldin: float, delta_heldout: float}   # DWC 追加
cmd: "python scripts/gate.py --gate 2"                    # DWC 门 5 要求的取数命令
```
**这一条把母巢最大的病（"文档说的和代码做的分离"）变成数据结构层面的不可能**：没有 `capability_evidence` 的 manifest 无法进入 manifest 目录。

**(M4) seesaw constraint + 双侧变体路由 → DWC 的 promote/prune 门。**
论文的关键实证：**单 harness 的 per-edit gating 会被亚阈值耦合绕过**（Telecom：连续 5 轮同类型编辑 + 第 6 轮触发 −14.0%，前 5 轮全部通过门）。**这条对 DWC 是直接的负面警告**：DWC 门 4 的淘汰机制若只看"当前是否变好"，会精确复现这个失效模式。HarnessX 的两条对策都可迁移：
- **noise threshold（±5% 单轮 pass-count delta 被忽略）** —— 防止噪声驱动的反复编辑；
- **变体隔离**：把改动按任务簇限定作用域，"一个簇的改善不能回归另一个簇"。DWC 的对应物是**按能力域分变体**（记忆域 / 进化域各自演化，互不 gating）。

**(M5) 病理分类 + 防御阶段映射 → DWC 的失效模式登记表。**
| HarnessX 病理 | 符号空间形态 | DWC 对应失效 | DWC 对应防御 |
|---|---|---|---|
| Reward hacking | Evolver 攻击验证协议、把答案嵌 prompt | 评分与输入无关（门 2 明列）、用硬编码常量冒充成功 | **确定性门**（当前是清单，需变成可执行判定） |
| Catastrophic forgetting | 修 A 静默回归 B | 新增机制抢位（526 冲突）、`mechanism_prune_shadow.applied=0/56,963` | **singleton_group 互斥 + 变体隔离** |
| Under-exploration | 偏向 prompt 改写这类便宜编辑 | 只加不减、文档越写越多（门 6 反例） | **planner 强制列出未尝试的编辑类型 + 杠杆命中率追踪** |

**(M6) ship-prediction accuracy（ship 预测准确率）→ DWC 的"预测校准"指标。**
HarnessX 用它诊断 under-exploration（R3 80% → R7 0%）——**"proposer 承诺会发生的翻转中，实际发生的比例"**。DWC 母巢的 PROGRESS.md 全是"声称"，**没有任何"声称被验证过多少"的统计**。把 `predicted_impact` 与 `measured` 对齐后，DWC 可得一个与论文同构的指标：
```
ship_prediction_accuracy = |predicted_impact.tasks_will_unlock ∩ 实际翻转| / |predicted_impact.tasks_will_unlock|
```
**门 6（加减平衡门）可以用它**：一个杠杆的 ship 预测准确率连续多轮低而另一类从未尝试 → 触发减法审查。**这直接对应门 6 现有规则"若连续两月无减法记录，门报警"的缺失环节——现在只能按时间报警，不能按证据报警。**

**(M7) Ensemble routing + per-run 目录树（Appendix 13）→ DWC 的演化台账。**
`INDEX.md / journal.md / curves.json / scoreboard.json / audit.jsonl / data/task_history.jsonl / data/ship_outcomes.json / data/rejected_candidates.jsonl / Rn/{landscape.md, candidates/, applied/, decision.md, verdicts/, regressions.md, digests/, trajectories/}`。**`regressions.md` 那一行值得单独抄**：Planner prompt 里明确写着"`ship_outcomes.json` 中的命中率**只统计预测的任务改善，所以未预测任务上的附带损害不会出现在那里——`regressions.md` 是它唯一会浮现的地方**"。这是对"只统计成功案例"这一系统性偏差的显式修补。

**(M8) Digester 的压缩目标（10M → 10K）→ DWC 的 trace 预算。**
论文给了具体数字：**GAIA 单轮（103 任务 pass@2）产生约 10M token 原始 trace；Digester 压成约 10K 结构化摘要**；缺这一阶段时单 agent evolver 必须截断 trace，产生信息更少的编辑并更频繁地被门拒绝（token 反而多 14%）。DWC 若做 trace 驱动的进化，**压缩比与压缩结构是必须先定的规格**，不是实现细节。

### 5.2 不可迁移

- **不可迁移（闭源模型依赖，最硬的一条）：meta-agent = Claude Opus 4.6。** 全文 15 个配置的主结果全部由 Opus 4.6 驱动 AEGIS。论文自己列了局限（Qwen3.5-72B、Llama-4-Maverick 作为 meta-agent 未测试）。**DWC 用开源模型时无法假定同等能力。** 但要公平地说：§6.4 的消融显示**四阶段相对单 agent 的准确率增益是 1.0%（噪声内）**，且结论原文说增益主要来自"基础设施"而非"evolver 的内部架构"。**因此准确的说法是：可迁移的是基础设施（typed 组件 + 结构化 trace + 确定性门 + manifest），不可迁移的是"Opus 4.6 能写出好代码"这一前提。**
- **不可迁移（闭源模型依赖，次硬的一条）：共演化需要模型权重。** §5 的 cross-harness GRPO 需要对 task agent 做梯度更新（8×H100、batch 256、lr 1e-6）。DWC 用托管 API 模型（当前 Hermes 是 free/托管路由）**完全无法执行 Learn 这一步**。因此 §5 整节（+4.7%）**对 DWC 当前形态不可用**。
- **不可迁移（成本）：100M–175M meta-agent token / 15 轮。** 对照母巢的 5,442 测试规模与 DWC 的项目阶段，这是一个数量级以上的算力承诺。论文自己给出的摊销论证（GAIA 约 1,300 次调用摊平 107.8M token）依赖"部署后有 1,300+ 次调用"这一前提，**DWC 目前没有这个调用量**。结论：**AEGIS 的循环不能整体搬，只能逐件搬**（M1–M8 各是独立可用的零件）。
- **不可迁移（评估前提）：每轮全量重评估。** "The full task set is evaluated every round (no subsampling)"——GAIA 103 / ALFWorld 134 / WebShop 100 任务 × pass@2 × 15 轮 × **K_t=4 个候选**。DWC 是 5,442 测试，同口径不可行。必须自建"代理评估 + 全量确认"两段式——**论文完全未涉及这个设计**。
- **不可迁移（异质性前提）：variant isolation 需要任务可干净聚簇。** 论文自己设了边界："没有任何东西保证这延伸到更长视界（**变体可能过特化**）或到任务间存在依赖、无法干净分离的分布。" DWC 的失败是跨 19 类能力的异质失败（母巢世界模型论文的教训：读了 14 篇，445 万行零实现）——**这类失败是否可聚成互不干扰的簇，论文没有答案**。论文在 GAIA 上给出的 Δ=0.0 恰恰是异质性触发停滞的证据。
- **不可迁移（语义前提）："implicated component identifiers" 需要失败可归因到组件。** 这在 GAIA 上成立（检索失败→tools 桶、推理失败→prompt 桶），在 DWC 上不成立——"核心功能零实现"**没有 implicated component**，因为组件本身就没被构造出来。HarnessX 的整套 trace→诊断→编辑链在这里会**第一步就断**。**这是三篇论文里对 DWC 最不利的一条，且必须诚实说出来。**
- **不可迁移（结论性数字）：+14.5% 平均、+44.0% 最高不能外推。** 其中 (a) 无 held-out；(b) 报告的是**峰值**且在 adaptation set 上评估（论文自陈选择偏差）；(c) Round-0 已是"胜任的组合 harness"，与 DWC 从零开始的起点不同。

## 6. 与其他论文的关系

- **与 `2606.09498` Self-Harness：同期、直接竞争，HarnessX 是它的工程化与理论化版本。**
  - **相同的骨架**（trace → 假设 → 候选编辑 → 门 → 合入），不同的形式化程度：Self-Harness 是经验式的 Algorithm 1 + 双切分非退化判据；HarnessX 是 `(ℋ, ℰ, ℛ, 𝒯)` operational mirror + 九维分类 + typed processor 底座 + seesaw constraint。
  - **Self-Harness 有而 HarnessX 没有的**：**held-in / held-out 双切分**。HarnessX §6.1 Scope 明说不评估 held-out。**这意味着 HarnessX 的所有数字都带选择偏差，而 Self-Harness 的至少有一半数字没有**——尽管 Self-Harness 的 held-out 也只是同分布。
  - **HarnessX 有而 Self-Harness 完全没有的**：异质任务集上的失败分析（GAIA/GPT-5.4 Δ=0.0、Global 峰值−24.3% 退化）、病理的实证确认、per-lever 命中率与 capability floor、ensemble routing。**Self-Harness 全部 9 组合正向，说明它只测了失败机制同质的任务**。
  - **两篇的门互相打脸**：Self-Harness 的 `Δ_in ≥ 0 ∧ Δ_ho ≥ 0 ∧ max(...) > 0` 比 HarnessX 的 seesaw（不得回归已通过任务）更严，但 **HarnessX 用实验证明了 per-edit gating 的结构性失效**（Telecom R7），并用变体隔离修补。**读序建议：Self-Harness（协议最小可复现）→ HarnessX（结构性失效与修补）→ RRSI（对 overfitting 的正则化）。**
- **与 `2609.14857` ModularRSI：同问题域，ModularRSI 更强的一个维度是"benchmark-disjoint"。** HarnessX 明说自己没有 held-out（§7.7 第一条），ModularRSI 的第一个问题陈述就是"在评测基准或其子集上演化，使可复用改进与基准特定适配难以区分"。**HarnessX 的 +14.5% 里有多少是 benchmark 记忆，ModularRSI 的设计正是为了回答这个问题，而 HarnessX 承认未回答。**
- **与 `2609.24972` RRSI：目标一致（防过拟合），手段不同。** RRSI 从 proposer 侧（temporally annealed budget 限制每候选捆绑编辑数、鼓励未探索轨迹）与 selector 侧（critic 筛 benchmark-specific 提案、pruner）双向正则化；HarnessX 从变体隔离与路径侧解决。**HarnessX 的 §6.6 案例 1（GAIA R10 reward hacking，R11 trace 检出，R12 加 guard）是 RRSI critic 的实证对应物。**
- **与 `2609.13406` GAI（形式框架）：最强互操作性。** GAI 的两个关键旋钮——"改进机制是否属于 agent 自身"、"度量标准是否锚定在系统外"——HarnessX 对两个都给了明确答案：**改进机制属于 agent 自身**（meta-agent 读自己的 trace、提出自己的 harness 编辑）；**度量锚定在外部**（固定 verifier，`§5.1 第 2 步`）。**HarnessX 的 operational mirror 几乎就是 GAI 框架在 harness 这一层的实例化**，且 HarnessX 诚实地把自己的 mirror 定位为 design checklist 而非理论。
- **与 `2603.25111` SEVerA：互补到可以拼栈，且互补关系是双向的。** SEVerA 给每个 GM 调用一阶契约 + 已验证 fallback（判据：形式规格对所有输入所有参数成立）；HarnessX 给每个 harness 编辑确定性门 + manifest（判据：pass rate 不退化 + 有 trace 支持）。**SEVerA 的漏洞是契约外的行为不可见（可以完美满足契约却不完成任务）；HarnessX 的漏洞是 pass rate 不退化不等于行为正确（reward hacking 案例）。前者治"形式正确"，后者治"经验有效"。** 若要合成，正确的层次是：**HarnessX 的九维分类法描述 harness，SEVerA 的 FGGM 包裹其中的 D1/D2/D4 三个维度上的模型调用，HarnessX 的 seesaw 作为全局回归门。** 注意 SEVerA 是唯一一篇可以作用于闭源模型的形式方法——这与 HarnessX 必须用 Opus 4.6 的困境恰好互补。
- **与 `2609.26396`/MetaRSI（`2609.06396`）：MetaRSI 的 Data-RSI / Harness-RSI / Model-RSI 三型算子与 HarnessX 的"非参数 vs 参数"二分几乎同构。** MetaRSI 说"Harness-RSI 编辑一个五槽 scaffold 而不触碰权重"，HarnessX 说"harness 更新做离散结构改动……无法表达为参数更新；模型更新做细粒度行为调整……无法被符号规格捕获"。**HarnessX 是这条主张的大规模实证版本。**
- **与 `2609.26457` AIDE²（真实研究 agent 自我改写）：8 天 7 处改进 vs 15 轮 14.5%。** 两者都在"agent 改自己的代码"，但 AIDE² 用经验 benchmark 选择、HarnessX 用确定性门 + manifest + 病理防御。**HarnessX 的价值不在分数更高，而在它记录了分数是怎么崩的**——GAIA Global 的 −24.3%、Telecom 的 −14.0%、Qwen3.5 在 SWE-bench 上 ≈0.05 的杠杆命中率。**这是 AIDE² 那类论文完全不会报告的部分，也恰恰是 DWC 需要的那部分。**
- **与 `2608.24876` Recuris（经验-工作记忆协同）：互补在记忆维度。** Recuris 把长时程失败**定位到具体记忆组件**并做 localized validation-gated 更新；HarnessX 的 D3（memory management）是一个九维之一，Appendix 12 显示 **τ³-Bench 上 config 杠杆是"最锋利但最少用"**（Qwen3.5 0.67）。**若 DWC 要把记忆做成可演化对象，Recuris 的"定位到组件"与 HarnessX 的"processor + singleton_group"是同一个诉求的两种表述**（前者用证据定位，后者用类型定位）。
- **与共演化类（`2608.10299` Co-Evolution in Agentic Systems 综述、`2607.27924` 等）：HarnessX 是该综述 taxonomy 里 Meta Co-Evolution 的一个具体实例**——"使演化机制本身可演化"。HarnessX 的做法是**让 trace 同时成为 harness 演化的诊断证据与模型训练的 RL 信号**（"每条轨迹同时是 AEGIS 诊断证据与 GRPO 训练信号"）。综述把这一阶段的开放挑战列为"如何安全可控地让越来越自主的演化过程"，HarnessX 的确定性门 + manifest + rollback target 是目前给出的最具体答案。
- **在图谱上的位置：harness 自进化派中"唯一有理论框架的"那一篇**（论文自陈的独特定位，且这个自陈经得起检查——§2.2 末明确说同行工作"缺乏统一理论框架"）。**但它的理论是设计启发式的，§7.3 自己承认。** 三篇读下来，harness 自进化这一派的共识已经相当清楚：**可观测性是必要条件，trace 的丰富度界定了可安全执行的演化精细度，per-edit gating 会被亚阈值耦合绕过，异质任务集需要变体隔离，能力地板会吃掉弱模型的所有增益。**

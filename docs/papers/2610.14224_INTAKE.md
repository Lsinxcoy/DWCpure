## 1 · 机制清单

| # | 机制名 | 一句话描述 | 出处 |
|---|---|---|---|
| M1 | **两层递归** | 任务级递归改「执行 harness」；harnessing 级递归改「改进 harness」 | §2.1 Def. |
| M2 | **对比式 Propose-Probe-Compose** | 无 ground truth 时，靠「参考执行 vs 候选执行」的行为对比来指导编辑 | §2.2.1 |
| M3 | **双候选作用域** | 每次提两个候选：invariant（通用能力缺陷）+ domain-specific（领域知识/流程） | §2.2.1 Propose |
| M4 | **并行 / 串行递归** | 并行=宽度 k（k 个候选 × k 次组合）；串行=深度 k（链式改进） | §2.2.2 |
| M5 | **改进库** | 每个领域一个库；条目 = 采纳的完整 harness 树 + EXPERIENCE.md | §2.3 / D.2 |
| M6 | **经验必须有证据才入库** | `cue`/`lesson`/`evidence` 三项全非空才 `add()`；否则返回 None | `library.py:43-47,120` |
| M7 | **选择性复用而非继承** | 下个任务从 H0 开始，库里的组件按需复用/改写，不自动继承 | §2.3 |
| M8 | **8 组件文件级分解** | C1 系统提示 / C2 护栏 / C3 记忆 / C4 工具指引 / C5 子代理 / C6 技能 / C7 脚本 / C8 中间件插件 | Fig.2 / Table 5 |
| M9 | **防泄漏 guard** | 写库前断言树里没有 grader verdict；库只保留当前任务之前的条目 | `library.py:122-123,101-104` |
| M10 | **无效树回退** | 树不合法（技能无触发句/脚本不编译/引用未打包的 helper）⇒ 带校验消息重试一次，再失败就继承起始树并记录 fallback | D.2 |

## 4 · 阶段归属

| 机制 | 阶段 | 理由 |
|---|---|---|
| M2 对比式探针 | **新增 P1-c** | 是 P1-b 双目标的自然延伸：先能对比，才谈得上"哪一维变好" |
| M3 双候选作用域 | P2 扩展 | 与"任务选档"同属"按任务特征分化" |
| M7 选择性复用 | **P1-c 的前置修正** | DWC 现在做反了，必须先纠 |
| M1 + M5 + M6 + M9 | **新增 P4** | 改进器自进化 = R438 #14 的完整形态 |
| M8 8 组件对齐 | P3 之后 | 结构收敛工作，不是新能力 |
| M4 并行/串行 | P4 可选 | 成本高，先串行 |

## 6 · 采纳判定

| # | 条件 | 结论 |
|---|---|---|
| 1 | 缺口真实 | ✅ 两层递归 / 对比探针 / 改进库 DWC 都缺 |
| 2 | 可落地 | ✅ 全是本地文件 + 现有 LLM 调用，无新依赖 |
| 3 | 可验证 | ✅ 六个测试都能写成会失败的断言 |
| 4 | 不破坏结构 | ✅ 库是新增目录，不改 19 对象隔离 |

**最终结论：部分采纳**（5 项采纳，3 项拒绝）

### 采纳

| 机制 | 落点 |
|---|---|
| M2 对比式探针 | P1-c |
| M3 双候选作用域 | P2 扩展 |
| M5 改进库 | P4 |
| M6 证据门槛（强化） | P4 |
| M7 选择性复用（纠正 DWC 现有做法） | P1-c 前置 |

### 拒绝

| 机制 | 理由 |
|---|---|
| M4 并行递归 k=5 | 成本 ×5；DWC 日预算 96/80 吃不下。串行 k=2 可作为 P4 的可选项 |
| M8 8 组件文件级重写 | DWC 的对象是配置/规则级，不是文件树；改成文件树会破坏 19 对象隔离 |
| M10 无效树回退 | DWC 没有"树"的概念，暂不适用 |

|---|---|---|---|

| Gemini 3.5 Flash / Codex | 74.5 → **77.5**（+3.0） | 33.9 → **35.3**（+1.4） | 71.6 → **75.6**（+4.0） |
| GLM-5 / OpenCode | 64.2 → **75.7**（+11.5） | 20.6 → **24.2**（+3.6） | 59.6 → **71.4**（+11.8） |
| GLM-5 / Codex | 64.4 → **75.3**（+10.9） | 23.6 → **24.8**（+1.2） | 58.1 → **65.9**（+7.8） |

### 递归预算 k=5 的增量

| 基准 | 增量 |
|---|---|
| WorkBuddy-Bench | +2.9 ~ +3.9 |
| JobBench | +3.0 ~ +4.2 |
| LAB Partial | +2.6 ~ +6.7 |

### 消融（WorkBuddy / JobBench）

| 去掉 | 损失 |
|---|---|
| 改进库 | −3.1 / −1.8 |
| 作用域编辑（双候选） | **−2.9 / −3.7** |
| 组合（Compose） | −1.6 / −1.9 |

### ★ 最重要的一条（对 DWC 的直接警告）

**直接改基础 harness、不看参考执行 / 候选探针 / 库 ⇒ 性能反而下降：**

```
WB-code  73.4 → 63.2   (−10.2)
WB-web   69.9 → 65.0   (−4.9)
```

库在 k=1 时只能"恢复"到基线；k=5 时才开始产生 +0.9 / +4.4 / +5.1 的增益。

> DWC 现在正是"直接编辑"模式：读签名 → 起草 → 试跑。
> 它没有库，也没有显式对比。这条数字说明：**这样做的上限很低，甚至为负**。

### 组件贡献（移除已改进 harness 的某组）

| 配置 | WorkBuddy Avg |
|---|---|
| 完整 | 80.8 |
| 去 prompt 组 | 79.3（−1.5） |
| 去 skills | **75.5（−5.3）** |
| 去 scripts | 77.1（−3.7） |

### 步数

Harness² 往往**用更少步数**拿到更高分（Gemini/OpenCode WorkBuddy 平均 25.4 → 21.9）。

### 同模型当编辑者

五个模型（GLM-5 → Claude Opus 5）全部提升，说明**不需要更强的编辑器**。

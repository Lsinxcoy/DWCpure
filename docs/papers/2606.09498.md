## 1. 问题

论文的出发点是一个**规模性论证**（§1，不是"缺能力"而是"缺人力"）：

- agent 的表现由 base model **和** harness 共同决定；harness 指"围绕模型、调解它与环境交互的系统层"，论文列举其成分：system prompts、tools、runtime mechanisms、verification rules、orchestration logic、failure-recovery procedures。
- 从 ReAct 到 Claude Code / Codex / OpenHands，harness **长期由人类专家手工工程化**。这个范式"随着现代 LLM 愈发多样与快速演化而**无法良好扩展**"——不同模型有不同的行为模式、工具使用习惯、错误模式、对提示的敏感度（Sclar 2024 / Schulhoff 2025 / Qin 2023），**对一个模型有效的 harness 对另一个可能是次优的**；新模型持续快速发布，为每个模型手工重设计并调优 harness "increasingly costly and untenable"。
- 与近期方法的区别（Figure 1 三范式）：Meta-Harness（Lee et al. 2026）与 Agentic harness engineering（Lin et al. 2026）**用更强的外部 agent 指导更弱的目标 agent**。论文反对的理由是这种外部引导"可能昂贵、对前沿模型不可得、或与目标模型的失败模式错配"。Self-Harness 的定位是**把改进循环内化到目标 agent 自身**。
- 论文自陈其研究范围**刻意收窄**（§2 末）："它研究的是一个更窄的受控设定：**同一个固定模型，在当前 harness 下运行，能否提出一个对支配其未来行为的 harness 的有界候选改动**。"

论文自己承认的缺口（分三处）：

1. **缺口（方法层）**：改进 harness 需要**跨 case 的、机制级的、可执行的结构化证据**，而不是"proposer 对一个看似合理的改动的说辞"。§5 原文："self-improvement should be grounded in **behavioral evidence** rather than only in the proposer's rationale for a plausible edit."
2. **缺口（评估层）**：pass rate 上升不等于"改到了机制"——需要一个能区分"改好了可复用机制"与"改好了这一个 case"的门。论文用 held-in/held-out 双切分 + 非退化接受规则来提供这个门。
3. **缺口（方法层，§5 自述局限）**："It studies **bounded** harness edits under **fixed benchmarks**, not open-ended self-improvement. Accepted edits **may still reflect benchmark-specific failure patterns**, and the protocol **depends on the quality of verifier outcomes and trace records**. Higher-stakes harness changes would require **stronger acceptance gates than pass-rate non-regression alone**."

## 2. 核心机制

### 2.1 记号与对象

固定模型 `M`（论文全程不变，包括 proposer 角色）、harness `h`、任务实例 `x`，运行得到执行 trace `τ` 与输出 `y`；trace 记录 messages、tool calls、verifier outcomes。评估器 `ℰ` 同样固定，`z_i = ℰ(x_i, τ_i, y_i)` ∈ {pass, fail}。

论文的核心句：**"由于 `M` 与 `ℰ` 都固定，跨轮的这些记录变化可以归因于 harness 的变化。"** 全部增益因此是 within-model 比较。

对象是一条 harness 世系 `h_0, h_1, …`，**每次转移是对执行协议的一次有界编辑，不是权重更新**。

harness 的工作定义（§3.1）："the **non-parametric scaffolding** that governs how a fixed language model is deployed as an agent … 不修改模型参数；它规定执行协议：模型如何观察任务、采取动作、调用工具、检查中间产物、产出最终答案。"

### 2.2 Algorithm 1 `Self-Harness`（原文伪代码逐行）

```
输入: 固定模型 M, 初始 harness h_0, held-in 切分 D_in, held-out 切分 D_ho, 评估器 ℰ,
      proposal width K, 轮数 T
输出: 最终 harness h_T
for t = 0,1,…,T−1 do
 4  (P_in(h_t), P_ho(h_t), R_t) ← Evaluate(M, h_t, D_in, D_ho, ℰ)
 5  B_t ← BuildEvidenceBundle(R_t)                      ▷ 来自 held-in 的 verifier-rooted 失败
 6  P_t ← ParallelPropose(M, h_t, B_t, K)               ▷ P_t = {(Δ_j, a_j)}_{j=1}^K
 7  A_t ← ∅
 8  for all (Δ_j, a_j) ∈ P_t do
 9    h_t^(j) ← Δ_j(h_t)
10    (P_in(h_t^(j)), P_ho(h_t^(j)), R_t^(j)) ← Evaluate(M, h_t^(j), D_in, D_ho, ℰ)
11    Δ_in^(j) ← P_in(h_t^(j)) − P_in(h_t)
12    Δ_ho^(j) ← P_ho(h_t^(j)) − P_ho(h_t)
13    if Δ_in^(j) ≥ 0 and Δ_ho^(j) ≥ 0 and max(Δ_in^(j), Δ_ho^(j)) > 0 then
14      A_t ← A_t ∪ {(h_t^(j), Δ_j, a_j, Δ_in^(j), Δ_ho^(j))}
15      Accept(Δ_j)   ▷ 通过接受规则
16    else
17      Reject(Δ_j)
18    end if
19  end for
20  if A_t = ∅ then
21    h_{t+1} ← h_t                                    ▷ 无候选被接受
22  else
23    h_{t+1} ← MergeAccepted(h_t, A_t)                 ▷ 接受的编辑被合并
24  end if
25 end for
26 return h_T
```
（原文伪代码第 13 行的第三个条件在 LaTeX 中丢失了 `>`，但 §3.4 正文明确写为 `max(Δ_in, Δ_ho) > 0`，且 Algorithm 2/3 的正文表述一致——按正文取 `> 0`。）

### 2.3 Stage 1 — Weakness Mining：从聚类 trace 到失败签名

第一层：trace record `r_i = (x_i, τ_i, y_i, z_i)`，轮级集合 `R_t = {r_i}_{i=1}^{|D_in|}`。取失败子集：
```
F_t = { r_i ∈ R_t | z_i = fail }
```

第二层（论文的关键设计）：对每个失败记录做**归因**，产出**失败签名**
```
φ(r_i) = (c_i, q_i, m_i)
  c_i : 终止级 verifier 原因（terminal verifier-level cause）
  q_i : 相关 agent 行为的因果状态（causal status）
  m_i : trace 暴露出的抽象 agent 机制（abstract agent mechanism）
```

第三层：**按签名精确一致聚类**
```
C_φ = { r_i ∈ F_t | φ(r_i) = φ }
```
论文对这一步的论证值得逐字记住：**"聚类是确定性的、evaluator-grounded 的：两个失败 case 只有在它们对『verifier 最终拒绝了什么』『agent 行为如何促成该拒绝』『涉及哪个可复用行为机制』三点一致时才被归到一组。"** 目的明确否定了另一种做法——"目标不是发现 trace 之间的潜在语义相似性，而是聚合那些**合理地接受同一处 harness 级干预**的失败。"

论文给出了这条设计要防的具体错误：**两个 run 可能共享同一个 verifier 结果（如 timeout 或缺失产物），却需要不同的 harness 改动，因为底层 agent 行为不同。**

第四层：每簇构造结构化失败模式，含 cluster size、代表性任务实例、共享 trace 症状、verifier 证据、推断出的 agent 机制。簇**按 support 与估计的可操作性排序**，使 proposer **先看到更可能映射到高价值 harness 改动的复发机制**。

输出是证据包 `B_t`。论文强调 `B_t` **不规定任何 harness 编辑**——"它把 verifier 级失败与 agent 级机制分开，让 proposer 能针对具体的可复用弱点，而不是去 patch 一个粗糙的结果（timeout、assertion failure、missing output 之类）。这让评估器与优化器保持分离。"

### 2.4 Stage 2 — Harness Proposal：多样在分支之间，最小在分支之内

proposer **不是外部优化器**，而是**同一个固定模型 M** 在当前 harness `h_t` 下进入 proposer 角色。给它的是**有界 proposal context**（不是原始日志）：
1. 当前 harness 的**可编辑面**（editable surfaces）；
2. 来自评估系统的 verifier-rooted 失败模式；
3. **应被保留的通过行为记录**（"records of passing behaviors that should be preserved"）；
4. **此前尝试过的编辑摘要**（"summaries of previously attempted edits"）。

产出 `P_t = {(Δ_j, a_j)}_{j=1}^K`，`h_t^(j) = Δ_j(h_t)`；`a_j` 是**审计记录**，含四要素：目标失败模式、被编辑的 harness 面、预期行为效果、回归风险。

三条硬约束：
- **每个 proposal 必须落在某个 primary failure mechanism 上，且映射到一个具体可编辑面。**
- **候选必须实质互异**："不应只是用不同措辞重述同一个 cluster / surface / mechanism。"
- **可寻址性判据**（论文自称 important）：一个失败簇只有在"**既有证据支持、又能被某个可编辑 harness 面处理**"时才是合适目标。论文明说不是每个失败簇都蕴含有用改动——"有些簇反映任务特定难度、不稳定结果，或模型能力上限，而非缺失某条执行规则"。

多样性/minimality 的精确划分：**"多样性在 proposal 分支之间被鼓励，最小性在每个分支之内被强制。"** 每个单独编辑被约束为：只修改其选定机制所需的表面、保持无关 harness 行为、**避免对 agent 控制架构的大范围重写**。

### 2.5 Stage 3 — Proposal Validation：非退化接受规则

接受判据（§3.4 正文，公式化的最终形态）：
```
Δ_in^(j) ≥ 0 ,  Δ_ho^(j) ≥ 0 ,  max(Δ_in^(j), Δ_ho^(j)) > 0
```
论文称之为 **conservative promotion criterion**，并给出一条**反直觉但重要的规则**：**"在两个切分之间做交易的 proposal 会被拒绝，即使其总通过数上升。"**

其余规则：
- **随机性处理**："当评估是随机的，我们**重复候选评估**并把同一规则应用到跨重复的聚合通过数上。这降低了 harness 编辑因单次有利运行而被提升的机会。"（协议为每个候选评估两次重复，Appendix A.2）
- **额外的机械拒绝**："验证会拒绝那些**没有修改任何可编辑面**、或在得到有效评估结果之前**执行失败**的 proposal。"
- **审计要求**：每个被评估候选都记录 changed surfaces、split-wise outcomes、evaluation repeats、proposal summary、accept/reject decision，使 harness 世系中每次转移**可审计**。
- **合并语义**：同轮多个兼容候选通过时，其编辑**被合并进下一版 harness**；被拒候选**保持日志但不改动活跃 harness**。

### 2.6 可编辑面的具体形状（Figure 3 完整初始 harness）

初始 harness 基于 **DeepAgent (LangChain)** SDK，故意做到极简。允许 Self-Harness 修改的**声明式配置点**（全部是 Python 函数，构成可编辑面）：
```python
def build_system_prompt() -> str
def build_memory_sources() -> list[str]              # 初值 ["/AGENTS.md"]
def build_subagents() -> list[dict[str, Any]]         # 初值 []
def build_skills() -> list[str]                      # 初值 []
def build_bootstrap_instruction() -> str
def build_execution_instruction() -> str
def build_verification_instruction() -> str
def build_failure_recovery_instruction() -> str
def build_runtime_control_policy() -> dict[str, Any]:
    return {"enabled": False,
            "max_recent_tool_errors": None,
            "max_total_tool_messages": None,
            "instruction": None}
def build_fixed_harness_agent(model, *, backend=None)  # → create_deep_agent(...)
```
初始 system prompt 全文（Figure 3）只有 6 行 + 3 条禁令，核心是"用内建文件系统与 shell 工具检查工作区、做具体编辑、**对着真实任务环境验证结果**"、"不要假设合成数据集、领域专用工具或隐藏 fixture，除非你在 repo 或运行时里发现它们"。

**这张图是全文最重要的工程细节**：可编辑面是**一份 Python 配置文件的函数返回值**，不是自由文本 prompt。这决定了"最小性"可以被结构性地强制（改一个函数 vs 重写整个 agent），也让"哪些面被改了"天然可审计。

## 3. 关键实验与数字

### 3.1 设置

**基准与样本**（§4.1 + Appendix A.2）：
- **Terminal-Bench-2.0**：原 89 个容器化任务 → **固定 64 例子集**。排除两类：依赖不稳定外部 web 资源的；需要多模态输入的（论文说明理由：多模态任务需要 modality-specific 输入处理，而**极简初始 harness 不暴露该功能**，纳入只会测量"不支持的 harness 功能"而非 Self-Harness 编辑的效果）。执行环境 **Harbor**，出网带宽上限 2 MB/s，对稳定但下载慢的外部资源做镜像。人工阅读论文全文后确认：该子集是**全部可用**而非随机抽样。
- **SWE-bench Verified**：固定 100 例，按 repository **按比例采样**，切分为 **67 held-in / 33 held-out**，切分在所有 harness 变体间固定。每任务独立 Docker sandbox，官方 evaluator 评分。**timeout：案例 3,600 秒 / 工具 120 秒**。
- **AppWorld**：固定 180 例 = **90 held-in / 90 held-out**。held-in 是官方 **train** 分区的全部样本；held-out 从官方 **test_normal 与 test_challenge** 按比例采样后固定。**每任务最多 50 个 agent turn。**

**模型**（三个不同家族）：**MiniMax M2.5、Qwen3.5-35B-A3B、GLM-5**。模型在所有 harness 变体间固定，**并且也担任 proposal 阶段的编辑生成器**。所有比较是 within-model：解码配置、预算、工具集、benchmark 环境、评估器全部不变。

**推理服务（Appendix A.1）**：MiniMax M2.5 走 MiniMax 托管 API；GLM-5 走 OpenRouter（`openrouter.ai/z-ai/glm-5`）；**Qwen3.5-35B-A3B 自建部署，4× NVIDIA H200，基于公开 SGLang Docker 镜像 `lmsysorg/sglang:v0.5.12-cu129` 派生**。访问时间 2026/05。

**指标**：`Pass (%)` = 通过对应 benchmark 官方 verifier 的评估尝试百分比，**除非另注，每个 harness 候选计算两次重复尝试**。

**协议控制**：任务集与切分在运行 Self-Harness **之前**固定；held-in 提供 trajectory、verifier outcome、失败证据给 proposer；**held-out 从不展示给 proposer，仅供自动提升门使用**；每任务从全新 benchmark 环境开始。

### 3.3 被保留的编辑：按模型分化的机制（§4.3 + Appendix B）

论文的核心定性主张："Self-Harness 不只是把 prompt 写长或加通用指令，而是引入反映每个模型在执行中遇到的复发问题的针对性改动。"

- **MiniMax M2.5**（TB overall 42.2% → 53.9%）：保留的编辑针对**缺失必需产物、schema 非法的工具内容、停滞的工具使用循环**。`build_bootstrap_instruction` 从"识别最小相关编辑面"改为"**识别必需的输出产物并尽早创建一个初始版本**"；`build_runtime_control_policy` 被**启用**并设 `max_total_tool_messages` 上限。轨迹证据（Figure 7，`count-dataset-tokens` 任务）：从长时间数据集探索 → 改为具体工作流：识别相关 metadata split → 计算所需计数 → 写答案文件 → 读回验证再停。
- **Qwen3.5**（TB 18.0% → 36.7%）：针对**产物检查、缺失产物恢复、重试纪律、工具错误触发的 middleware**。轨迹证据（Figure 8，`extract-elf` 任务）：初始 harness 下 agent 创建 extractor 脚本、遇覆盖与编辑失败、反复尝试修改同一产物、最终**删除 `/app/extract.js` 才停**，verifier 因必需文件缺失而失败；编辑后，**工具错误触发的 system prompt** 把 agent 重定向回缺失产物：重建 extractor → 修解析逻辑 → 写出输出文件 → 对 JSON 结果做定向验证 → 留下 verifier 需要的产物。
- **GLM-5**（TB 46.1% → 57.0%）：针对**迟延产物、外部计算、会话作用域工具、实现导向的探索**。编辑使环境变更**跨 shell 命令持续**，并加了一条验证阶段约束：若一直在探索而未产出必需产物，应转向实现与测试。轨迹证据（Figure 9，`build-pov-ray`）：初始 harness 花大量预算在长单块外部下载上，之后**为反复失败的 sanity check 找理由**；编辑后**在超时证据后切换策略**，尽早验证替代源，修复失败的渲染检查，再收尾。

**跨 benchmark 的收敛**：
- **SWE-bench Verified（三个模型都强化验证，但结构不同）**：MiniMax 把**空 diff 检测与定向局部测试分离**（一个 diff-inspection subagent 检查 patch 是否存在，一个 test-verifier subagent 跑最相关的失败测试），46.0% → 52.5%；Qwen 组合**一个 patch-verifier subagent + 提交前的直接指令**（检查当前 diff 并跑定向测试），19.5% → 41.5%；GLM 把**依赖感知的恢复内嵌进验证指令**（解析 import 失败 → 识别并安装缺失包 → 重跑该测试 → 仍不成功则继续调试），52.0% → 55.5%。
- **AppWorld（三个模型收敛到"完整状态检索 + 正确完成语义"）**：MiniMax 加 **state-auditor subagent + 分页与时间边界指引**，48.6% → 58.9%（Venmo 案例：初始 harness 向全部 7 人索款，编辑后翻完交易页、应用时间边界、识别出 4 人已付、只向剩余 3 人索款）；Qwen 保留两条 **prompt 级 guard**——**completion-contract guard**（区分 action-only 任务与信息请求）与 **pagination guard**（要求完整记录检索 + 最终目标对象检查），22.5% → 52.2%；GLM 加 **action-versus-information 完成规则 + 状态变更前的穷尽分页**，44.4% → 85.0%。

具体的测试数字（论文给了可核验的细节）：Qwen @ Django window-function——编辑后把 SQLite casting guard 放在 inner window-compatible expression 处，提交前跑 **49-test `expressions_window` 套件，通过全部 1 个 FAIL-TO-PASS 与 46 个 PASS-TO-PASS**；GLM @ Astropy——初始 harness 仅做语法检查就提交，留 4 个 FAIL-TO-PASS 与 5 个 PASS-TO-PASS 失败；promoted harness 完成后 **4 个 FAIL-TO-PASS 与全部 68 个 PASS-TO-PASS 通过**。

  2. "the protocol **depends on the quality of verifier outcomes and trace records**."
  3. "**Higher-stakes harness changes would require stronger acceptance gates than pass-rate non-regression alone.**"（**这是论文对自己方法的直接否定性评价：门不够强**）

## 4. 它假定了什么（Assumptions）

论文写出来的：

1. **(A1) 模型与评估器固定。** 这是全文所有归因的基础："由于 `M` 与 `ℰ` 都固定，跨轮记录的变化可归因于 harness 的变化。"
2. **(A2) verifier outcome 可信。** §5 明确列为局限：协议"depends on the quality of verifier outcomes and trace records"。
3. **(A3) 存在一个非退化即安全的门。** 接受规则把"held-in 与 held-out 都不退化且至少一边严格提升"当作足够的门槛；§5 自己承认对高风险改动不够。
4. **(A4) 失败签名可被确定性归因。** 论文主张聚类是"deterministic and evaluator-grounded"，但 `φ(r_i) = (c_i, q_i, m_i)` 由**评估系统（实为 LLM 分析 trace）**产出，不是形式化计算。论文未说明 c/q/m 三元组由谁生成、如何保证跨轮一致、如何避免分析本身的漂移。**这是全文最未被审视的假设。**
5. **(A5) proposer 与执行共享同一模型不会导致自我确认偏差。** 论文强调这是有意设计（内化循环），但没有做任何对照实验检验"更强的外部 proposer 是否更好"（Meta-Harness 路线）。

论文没写、但撑起结论的隐含前提：

6. **(I1) 极简起点这一强假设。** 所有增益都是在"从几乎空的 harness 出发"上测的。论文从未回答：**如果起点是一个已被专家充分调优的 harness，还剩多少可挖？** Figure 3 的初始 harness 是 6 行 system prompt + 默认工具——这是一个人为压低的基线。附录 B 的定性分析显示大部分保留编辑是"加一条提醒""启用 runtime 控制""加一个 subagent"，这些在起点更丰富的系统里**大概率已经存在**。
7. **(I2) held-out ≈ 泛化。** held-out 只从同一 benchmark、同一分布中切出。论文在 §5 承认这是 benchmark-specific，但在 §4.2 却用它论证"gains are not confined to the held-in failures"。**这两个陈述之间存在张力**：held-out 证明了"不是记忆单个 case"，没证明"不是记忆 benchmark 模式"。
8. **(I3) 可编辑面是低维的。** 整个论文的"最小性"建立在"编辑 = 改一个 Python 函数的返回值"这一形态上。母巢 445 万行代码的架构**不是 8 个函数**；若 DWC 把可编辑面定义成"7 个配置文件"，那么"有界编辑"的成本估算、合并语义、回滚语义全部需要重新设计。
9. **(I4) 收敛速度依赖任务同质性。** 三个基准都是单一 verifier、单一 domain 的同质任务集。母巢的失败是**跨 19 类能力的异质失败**——论文自己在 HarnessX 论文里会遇到的那个问题（heterogeneous task sets 上单 harness 演化停滞），Self-Harness 这篇**没有触及**。

## 5. 可迁移到 DWC 的点 / 不可迁移的点

### 5.1 可迁移（给具体接口）

**(M1) 失败签名三元组 `(c, q, m)` → DWC 的失败归因数据模型。** 这是全文最可复用的一件工程品。
- `c` = verifier 层的终止原因（"声称完成但产物不存在" / "超时" / "测试未跑"）
- `q` = 该 agent 行为的**因果状态**（是否为根因 / 是否只是伴随现象）
- `m` = 抽象机制名（"缺产物早交付"、"工具失败后无恢复动作"、"未验证完成声明"）

DWC 侧接口（对齐 DWC 门 2 / 门 3）：
```python
# dwc/diagnosis/signature.py
@dataclass(frozen=True)
class FailureSignature:
    c: str        # verifier-level terminal cause，来自外部真值源，枚举
    q: str        # causal status of the implicated behavior: root|contributing|symptom
    m: str        # abstract mechanism name，稳定标识，跨轮可比

def cluster(failed: list[TraceRecord]) -> dict[FailureSignature, list[TraceRecord]]:
    """按三元组精确一致聚类——不按语义相似度。"""
```
**DWC 侧的直接落点**：母巢的 5,442 测试全绿却有 5 个 P0 缺陷，这个"缺陷在测试系统外"的判定恰好就是 `c` 与 `q` 的分离。门 3（活性六层单调）已经给了 `q` 的候选值——"弱判据不得越级点亮强判据"就是一次因果状态判定。

**(M2) 三元组精确聚类 + 支撑度排序 → DWC 的淘汰判据生成器。** 论文强调"确定性、evaluator-grounded"与"簇按 support 与可操作性排序"。对 DWC 门 4（生灭配套门）的价值：新增能力必须同时提交淘汰判据，而**判据应当由跨 case 的机制聚类导出，而不是拍脑袋写**。接口：
```python
def prune_criteria(clusters: dict[FailureSignature, list[TraceRecord]],
                   min_support: int) -> list[PruneCriterion]:
    """min_support 过滤掉单例机制；返回可自动判定的淘汰判据。"""
```
母巢的反例"编译 1,447 / 停用 5，淘汰率 0.0035"对应的正是"簇的 support 极不均衡"——**19 个失败机制里可能 15 个是单例**。论文的 `min_support` 阈值能把它们显式分出来，而不是混在 stale 里。

**(M3) `Δ_in ≥ 0 ∧ Δ_ho ≥ 0 ∧ max(...) > 0` 的非退化接受规则 → DWC 的 promote 门。**
这条规则的价值在于**它拒绝"总量上升但结构变差"**。母巢的门 5（声称/实测分离门）写的是"无对照组的改进声明 → 标记 UNKNOWN"，但没有说 UNKNOWN 的机制。DWC 可以直接把这个判据作为机制层门：
```python
def accept(before: Slice, after: Slice) -> GateResult:
    d_heldin  = after.heldin  - before.heldin
    d_heldout = after.heldout - before.heldout
    ok = d_heldin >= 0 and d_heldout >= 0 and max(d_heldin, d_heldout) > 0
    return GateResult(ok, claimed="...", measured=f"Δin={d_heldin} Δho={d_heldout}")
```
**"必须同时有 held-in 与 held-out 两组"这一条是关键**：母巢的 5,442 测试**只有一组**。这意味着母巢根本不具备判定"这是可复用改进还是过拟合"的能力。Self-Harness 的双切分协议可以直接落成 DWC 的测试集重组（held-in / held-out 两组，且 held-out 对改进者不可见）。

**(M4) 审计记录 `a_j` 的四要素 → DWC 门 5 声称/实测分离的可执行化。**
`a_j = (目标失败模式, 被编辑的 harness 面, 预期行为效果, 回归风险)`。这四项正好填 DWC 门 5 要求的"声称 / 实测 / 取数命令"三栏之外的一项——**预期效果可被下一轮证伪**。接口：
```python
@dataclass
class EditAudit:
    target_mechanism: str      # FailureSignature.m
    edited_surface: str        # 具体面，母巢的"526 个抢位冲突"就死在这个字段
    expected_effect: str       # 可被下一轮数据推翻
    regression_risk: list[str]
    measured: dict[str, float] # 实测：Δin/Δho
    cmd: str                    # 取数命令，门 5 要求可重跑
```

**(M5) 可编辑面 = 声明式配置函数（Figure 3）。** DWC 若要"门 1 的定位声明"可被自动检查，就把每个新增模块的服务声明做成一个函数返回值而非 markdown 段落。这与 SEVerA 的 fallback 可判定是同一类思路。**但**（见不可迁移第 2 条）这在 DWC 现有代码形态下工作量巨大——母巢是 445 万行，HarnessX 的回答是走"processor + hook"路线而非"配置文件"路线（见第 6 节）。

**(M6) 被保留编辑的分类清单 → DWC 的"缺失机制"清单。** 论文附录 B.2/B.3 给出了三套可复用机制的命名：**验证前提交（空 diff 检测 / 定向测试 / 依赖修复）、完整状态检索（穷尽分页 / 时间边界）、完成语义区分（action-only vs 信息请求）、工具错误触发的恢复重定向、产物早交付、运行时控制上限**。这六条对任何 agent 框架都成立，与论文用的模型无关。**DWC 可直接把这份清单作为记忆模块的验收项。**

### 5.2 不可迁移

- **不可迁移（量级差太多）：算法 1 的 per-candidate 全量重评估。** 每个候选 `(Δ_j, a_j)` 都要在 `D_in ∪ D_ho` 上**完整重跑**。论文规模：TB 64 例、SWE 100 例、AppWorld 180 例，每候选两次重复，SWE 单例 timeout 3,600 秒。**DWC 是 5,442 测试的规模 —— 单候选评估成本 ≈ 论文单个 benchmark 的整个搜索预算。** 且 `ParallelPropose` 的宽度 K 未报告，无法判断这是否是成本瓶颈。**结论：判据可迁移，评估循环不可按原样迁移。** 必须先做"用采样代理评估 + 全量确认"的两段式，这是论文完全未涉及的设计。
- **不可迁移（前提不成立）："弱模型受益更大"的隐含期待。** 论文报告的绝对增益在 Qwen3.5-35B-A3B（家族中最弱、35B-A3B MoE，本地部署于 4×H200）上最大（TB +104%、SWE +113%、AppWorld +132% 相对增益）。DWC 若用 Hermes 当前的 free 模型，**不等于这个 regime**——free 模型的失败模式更可能是"知识/推理能力不足"，而论文的六条保留机制全是**执行协议类**（早交付产物、跑测试、翻完分页），对能力不足无能为力。HarnessX 论文在同一现象上给出了相反方向的警告：SWE-bench 上 9B 模型的所有 lever 命中率塌到 ≈0.05（"capability floor below which evolution cannot compound"）。**两篇合起来意味着：DWC 用弱模型做 harness 自进化，大概率遇到 capability floor。**
- **不可迁移（闭源模型依赖）：** 论文三个模型中 **MiniMax M2.5 与 GLM-5 均走托管 API**（MiniMax 官方 API、OpenRouter）。GLM-5 在 AppWorld 上的 85.0% 依赖 OpenRouter 端点的具体行为。DWC 用开源/本地模型时，**API 层面的确定性（seed、版本漂移、限流）不复存在**——而论文的接受规则完全建立在"同一模型在两次重复中行为稳定"之上（"评估是随机的时我们重复评估"）。若模型端点会漂移，`Δ_in ≥ 0` 的噪声底会高到无法区分真实改进。**这是论文未讨论但对 DWC 最致命的一条。**
- **不可迁移（结构前提）："8 个配置函数"的可编辑面。** DWC 母巢 445 万行、526 个抢位冲突——这不是 8 个函数能表达的编辑面。强行套用会退化成 HarnessX 论文警告的"copy rather than composition"。
- **不可迁移：缺失的合并/回滚语义。** `MergeAccepted` 无冲突检测、无回退路径。DWC 门 6（加减平衡门）要求净增长受控，而论文**只增不减**——9 个运行最终全部是净增（AppWorld GLM-5 从 44.4% 到 85.0% 的 harness 经历了多少轮叠加编辑，论文未报告最终 harness 的大小）。**DWC 若照搬，会精确复现母巢"≈ 只加不减"的产品层病。**

## 6. 与其他论文的关系

- **与 `2606.14249` HarnessX：同期、直接竞争、且 HarnessX 明显更了解 Self-Harness 型的弱点。**
  - **相同的骨架**：都是"trace → 假设 → 候选编辑 → 门 → 合入"。HarnessX 把它形式化为 **operational mirror (H, E, R, T)**，Self-Harness 保持经验形式。
  - **HarnessX 引用的近邻里就包括 Self-Harness 的对头**：Meta-Harness (2603.28052) 与 Agentic harness engineering (2604.25850) —— 后者正是 Self-Harness §1 用来定义"外部 agent 路线"的那篇。
  - **Self-Harness 没有触及、HarnessX 明确处理的三件事**：
    1. **可组合的结构底座**：HarnessX 的 Processor + 八 hook + `_singleton_group`/`_order`/`_after` 元数据，让"编辑的作用域"成为一等公民；Self-Harness 只有"改配置函数返回值"。
    2. **异质任务集上的停滞**：HarnessX 报告 GAIA/GPT-5.4 在 15 轮内 **Δ = 0.0**（Global 策略峰值 73.8% 后跌到 49.5%，peak−final = −24.3%），并给出 variant isolation 解法（87.4%，non-degrading）
   > **数字出处**：以上数字全部来自 `2606.14249` HarnessX 原文，**非 Self-Harness(本文) 的实验数据**。本文 9 个 model–benchmark 组合的实测结果见 §3。。**Self-Harness 全部 9 个组合都正向，说明它只测了"失败机制同质"的任务**——这是选择性的证据，不是更强的证据。
    3. **病理学的预先分类**：HarnessX 从 operational mirror 推出三种病理（reward hacking / catastrophic forgetting / under-exploration）并逐一给出防御阶段与实证案例；Self-Harness 没有这层结构，它的"非退化门"是经验规则，HarnessX 的 seesaw constraint 则被实验证明**也会被亚阈值耦合绕过**（τ³-Bench Telecom R7：连续 5 轮同类型编辑，R7 第 6 条触发 −14.0%）。
  - **反向的差别**：Self-Harness 的门**比 HarnessX 强在"必须双边不退化"**——HarnessX 的 seesaw 是"不得回归已通过任务"，Self-Harness 要求 held-in 也 ≥ 0。HarnessX 在 GAIA GPT-5.4 上恰恰因为任务冲突而卡住，说明双边约束在异质任务集上代价不小。
- **与 `2609.14857` ModularRSI：同一问题域的更完整回答。** ModularRSI 的三个问题定义（benchmark-disjoint / contrastive / modular）直接覆盖了 Self-Harness 的三个隐含弱点：(a) benchmark-disjoint 对应 Self-Harness 的"accepted edits may still reflect benchmark-specific failure patterns"；(b) **contrastive（同任务成功与失败轨迹对比）** 对应 Self-Harness 的 verifier-grounded 聚类，ModularRSI 认为只对比失败不够；(c) modular 分解对应 HarnessX 的组合底座。**Self-Harness 是这三篇里最简的一版，也是唯一把 proposer 与执行者统一为同一模型的。**
- **与 `2609.24972` RRSI：直接针对 Self-Harness 弱点。** RRSI 的问题陈述就是"harness 递归演化可能过拟合记忆训练任务，在 OOD 上收益缩小甚至消失"——这正是 Self-Harness §5 的第一条自述局限。RRSI 的对策（temporally annealed budget 限制每候选捆绑的编辑数、critic 筛 benchmark-specific 提案、pruner）是对 Self-Harness "parallel propose K 个 + 全部合并"的无界策略的直接修补。**读这两篇的正确顺序是 Self-Harness → RRSI。**
- **与 `2603.25111` SEVerA：正交互补，可叠成栈。** Self-Harness 改 harness 非参数构件、判据是双切分非退化；SEVerA 给每个 GM 调用配一阶契约 + 已验证 fallback、判据是形式规格。**Self-Harness 的六个保留机制里"验证前提交""完成语义区分"都可以写成 SEVerA 式的局部契约**；反过来 SEVerA 的契约层看不见 pass rate 之外的退化，正需要 Self-Harness 的双切分门。
- **与 `2609.24972` 之外的世界模型类（`2607.27201` MWM / `2607.27924` ODEWorld）：无直接关系。** 两篇研究的不是"如何改进执行协议"，而是"如何让世界模型正确"。若 DWC 的记忆模块最终要接世界模型，Self-Harness 的失败签名机制（`m` = 抽象机制名）可用来标注"这条记忆的检索机制在哪些任务簇上失败"，但那是借用其数据结构，不是其方法。
- **在 RSI 图谱上的位置：Harness 自进化派的"最小可复现版本"。** 它贡献的不是新机制，而是**一个足够小、足够干净、可以被完整复现的 harness 自进化协议**（9 个组合、全部通过、可审计、代码开源）。在这个意义上它与 `2606.14249` HarnessX 的关系更像**教学版 vs 工程版**——而 HarnessX 的 §6.4 消融（单 agent evolver 86.4% vs 四阶段 AEGIS 87.4%，差异在 1 个标准误内）从某种意义上也支持这个判断：**当基础设施（可观测性、门、审计）到位时，进化循环的架构复杂度不是准确率的来源。**

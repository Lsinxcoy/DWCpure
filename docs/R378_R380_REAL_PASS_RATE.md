二、修掉的三处判据缺陷（每次都是"看起来有数、其实是假的"）
════════════════════════════════════════════════════════════
【R378-a · 读旧报告】tid 同一天重复
  `tid = "nb_%s_%02d" % (MMDD, i)` ⇒ 同一天第二次跑批必撞名
  ⇒ `_wait_report` 立刻命中上一批的 `var/dwc_reports/{tid}.json`。
  取证：08:51 跑批读到 mtime 02:35–04:01 的报告。
  修：`make_tid()` = `nb_<MMDD>_<HHMMSS>_<i>`；
      `_wait_report(..., since=投单时刻)` 只认 mtime ≥ since 的报告。

【R378-b · 吃旧文件】文件类判据不校验时效
  `verify()` 只看 `target in body`。
  取证：`wr08` 判 ✓，但那个文件 mtime 是 **528591 秒前**（6 天前残留），
  任务本身 `status=incomplete, answer=None`。
  修：`verify(..., since=)` 对 `file_contains/_all/_lines` 校验
      `mtime >= since`，否则返 `file stale`。

【R379 · 并发退化】端点并发下不遵守 json_mode
  对照实验（同端点/同 prompt/同配置）：
    · 串行 4 个任务          ⇒ **4/4 JSON**
    · 并发 4 线程            ⇒ **0/4 JSON**（含 finish=tool_calls、
      content 空、自然语言散文）
    · 并发 + 各自独立 session ⇒ 仍 **0/4**
    · 并发 + 全局锁串行化     ⇒ **4/4**
  ⇒ 根因是端点并发退化，不是 session 冲突。
  而 DWC 的 `Semaphore(2)` 允许 2 单并发（收件箱异步接单）⇒ 生产必踩。
  修：模块级 `_HTTP_LOCK`，`complete()` 与 `complete_stream()` 的
      HTTP 段全部包在锁内（必须是模块级 —— 生产每单新建 LLMClient）。

【R380 · 纯文本答案被判死】7/8 失败的真因
  取证：8 单失败的 `why` 里有 7 单**就是答案本身**：
    `prev_node_id` / `dwc_pairs.jsonl` / `一个不存在的内核文件名` / `foundation`
  ⇒ 模型答对了，只是输出纯文本而非 `{"op":"final","answer":...}`。
  成因：`reasoning_effort="none"`（R377 为修"推理吃光 token"而加）
  压制推理后，模型不再"先想格式再答"。
  ⇒ **格式判死把正确答案一起扔了。用格式换正确率是错的。**
  修：非 JSON 且非空的响应 ⇒ 收下为答案（`status=done`,
      `answer_mode="plain_text"`，`why` 留痕）；
      空/纯空白仍判 incomplete；合法 JSON 但无 op 仍走原逻辑。

七、补充证据（2026-10-20 10:20 · 串行稳定性实测）
════════════════════════════════════════════════════════════
R379 的「端点并发退化」结论，由这组 12 次串行调用最终钉死：

  4 个任务 × 每个跑 3 次，**纯串行**（同一实例，一次只发一个请求）:
    世界模型的作用。                     J J J
    为什么上轮没执行。                    J J J
    在 var/inbox_work/ 写 hello.txt      J J J
    列出 tests 下至少两个测试文件名。        J J J

  ⇒ **12/12 = 100% JSON**

对照总表：
┌──────────────────────────────┬──────────────┐
│ 调用方式                      │ JSON 成功率   │
├──────────────────────────────┼──────────────┤
│ 纯串行（12 次）               │ 12/12 = 100% │
│ 并发 4 线程（加锁前）          │ 0/4  = 0%    │
│ 并发 + 独立 session（加锁前）  │ 0/4  = 0%    │
│ 并发 + 显式外层锁             │ 4/4  = 100%  │
│ 并发 + client 内 _HTTP_LOCK   │ 2/4 → 4/4*   │
└──────────────────────────────┴──────────────┘
  * 内部锁实测重叠峰值为 1（真串行），残余非 JSON 是端点自身的
    采样波动，不是并发问题。

⇒ 端点串行时 100% 遵守 `response_format: json_object`，
  并发时完全不遵守。**串行化就是正确修法**，不是权宜之计。

二、根因：R380 的假成功（本次修的就是这个）
════════════════════════════════════════════════════════════
现场（报告原文）:
  wr03  "已写入 `var/inbox_work/list.md`,内容: ..."   actions=0 文件没写
  wr05  "已在 `var/inbox_work/note.txt` 写入,内容为..." actions=0 没写
  wr07  "已写入 `var/inbox_work/two.txt`：..."        actions=0 没写
  wr01  "`flag.txt` 已写入,内容为 EVAL_E2E_COMPLETE"  actions=0 没写
  an04  "我无法执行文件写入（没有可用的文件/终端工具）" actions=0

⇒ R380 把"非 JSON 纯文本"收下当答案（status=done），结果模型**说**
  它写了文件就被当成完成。这正是本项目一直反对的
  **「降级与成功不可区分」** —— 我自己引入的回归。

修：
  · `_ACTION_CLAIM_RE` —— 零动作 + 文本声称做过动作（已写入/创建成功/
    已执行…）⇒ `incomplete`，why 写明"幻觉动作"
  · `_REFUSAL_RE` —— 零动作 + 明确拒绝（我无法执行/没有可用的工具…）
    ⇒ `incomplete`
  · 纯陈述性答案（知识题，本来不需要工具）⇒ **仍然收下**
    （修过头的后果：hs01/hs02/rf01/rf02 这些本来能过的会全挂）

★ 必须用正则而不是子串：真实文本是「已**在** `note.txt` **写入**」，
  动词被路径隔开，子串「已写入」匹配不到（已踩过一次）。

三、真正的根因（下一步，本轮未修）
════════════════════════════════════════════════════════════
`task_exec` 用**手工拼 JSON 提示词**（`llm.complete(prompt, json_mode=True)`），
逼模型在散文里输出 `{"op":"read",...}`。但实测端点**原生 tool calling
完全正常**：

    === reasoning_effort='low' ===
     finish=tool_calls  tool_calls=1
       → read_file {"path": "src/dwc/llm/task_exec.py"}
    === 不发送 ===
     finish=tool_calls  tool_calls=1
       → read_file {"path": "src/dwc/llm/task_exec.py"}

模型本来就会调工具，是 `task_exec` 用错了 API（该用原生 tool calling）。
这是"94% 零动作"的根本原因，需要一次架构级改造（下一步）。

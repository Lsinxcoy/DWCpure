它要解决的问题

Agent 轨迹变长后，KV cache 的 I/O 与存储成为主导成本；轨迹还会超出模型最大上下文。 传统做法是"上下文工程"（裁剪或摘要），但改动轨迹前缀会让后续缓存失效，触发昂贵的 re-prefill。

它的答案

缓存工程：直接控制活跃 KV cache，不改轨迹文本、不 re-prefill。

操作做什么关键点
Drop把选中消息的 KV 从后续注意力中排除轨迹文本原封不动
Repos用 RoPE 旋转调整保留 key 的位置编码压缩位置索引，避免撞上限
Append正常追加—

2 · 核心洞察：为什么"裁剪"反而更贵

方法相对成本精度机制
全上下文1.00×基线不裁剪
Trim（留最近 12 轮）1.85×—前缀变了 ⇒ 保留部分全部重新 prefill
Summary（48K）−7%−5pp摘要本身要调用，且丢信息
AKV（rolling drop）更低更高只改 cache，不动前缀
反直觉之处：裁剪看起来"少传了 token 应该更便宜"，实际上因为破坏了缓存前缀， 导致保留的部分要重新计算。省下的输入 token 抵不过 re-prefill 的开销。

为什么工具响应是首选丢弃目标

论文测量了每 token 的注意力分布（Figure 2）：

  • 越早的 token 注意力越低
  • 同等相对位置上，工具响应拿到的注意力低于 assistant 消息

所以默认策略是"滚动丢弃旧的工具响应 cache，保留全部推理与最近 K 轮工具响应"（K=12）。

为什么必须 Repos

默认位置编码随逻辑轨迹增长，即使 cache 很小，索引也会撞模型上限。 Repos 把位置索引与逻辑索引解耦 —— 消融显示它单独把 BCP 从 55% 拉到 62%， 因为不压缩就会"探索到位置上限直接停摆"。

3 · 方法：策略三元组

代码里这个抽象非常干净（agent/policy.py:26-40）：

DropTrigger      = Callable[[PolicyContext], bool]
MessageSelector  = Callable[[PolicyContext], set[int]]
RepositionRule   = Callable[[PolicyContext, set[int]], bool]

@dataclass(frozen=True, kw_only=True)
class CachePolicy:
    trigger:    DropTrigger | None = None      # 何时丢
    selector:   MessageSelector | None = None  # 丢哪些
    reposition: RepositionRule | None = None   # 何时压缩位置

三者独立，任一为 None 就"不做该操作"。内置实现按"轮"和"token"两种粒度各有一套：

组件轮粒度token 粒度模型粒度
triggerTurnTriggerTokenTriggerModelTrigger
selectorTurnSelectionTokenSelectionModelSelection
repositionTurnRepositionTokenRepositionModelReposition

3.1 服务侧的挑战：历史依赖

同样的 token 序列，在不同的 cache 操作序列下会产生不同的 cache 状态 ⇒ 传统 serving 的"前缀匹配"不足以正确复用 cache。

AKV 的对策：对外提供无状态接口（兼容现有 OpenAI API），内部管理有状态的复用、驱逐、恢复； 并用扩展基数树 + 分段批注意力支持这些操作。

3.2 Cache-as-Tool（CAT）

把"丢哪些 cache"暴露成一个工具，让 agent 自己决定何时减、保留什么。

模型StandardCAT
GPT-OSS-120B52.1 / 13.4¢61.0 / 12.1¢
MiniMax-M2.756.0 / 5.4¢64.0 / 5.9¢

注意 MiniMax 的成本上升（5.4→5.9）—— 因为 agent 决定多跑几轮。这是"精度换钱"的自觉选择。

5.2 一个可直接借的记账细节

系统在 usage.prompt_tokens_details 里报三个数（含 0 值）：

cached_tokens           # 命中缓存的输入 token
drop_skipped_tokens     # 因 Drop 而未参与计算的 token
repos_tokens            # 因 Reposition 而重新编码的 token
这正好补上 DWC P0-a 的盲区：成本必须区分"命中缓存"与"未命中"， 两者单价可能差一个数量级。HarnessPro 也用了 uncached/cached/output 三档计价 —— 两篇独立论文在这一点上收敛，说明这是硬需求。

6 · DWC 能学到什么

6.1 先说不能学的

机制为什么不能
Drop / Repos需要自建 SGLang、改 KV cache 内部、控制 RoPE；DWC 走远程 OpenAI 兼容 API，连 cache 句柄都没有
Cache-as-Tool同上；而且会新增一个工具面，破坏现有工具契约
位置编码解耦DWC 没有位置编码控制权
serving 优化（1.36×/1.51×）DWC 不拥有推理服务

6.2 再说必须学的（四条）

① cached_tokens 记账（P0-a 补充）

DWC 现状要改成
全库 grep cached_tokens 零命中；成本只按总 token 算 解析 usage.prompt_tokens_details.cached_tokens；计价区分 cached / uncached / output 三档

② 前缀稳定性诊断（P0-b 补充）

DWC 的问题比论文批评的基线更严重。
task_exec.py:2333 每轮重建整个 prompt 字符串： "任务: %s\n%s最近轮次: %s\n上一步动作观察(JSON): %s\n请继续"。
稳定部分只有开头的任务描述；从"前情摘要"开始每轮都变 ⇒ 缓存几乎不可能命中。

要改成：稳定前缀在前、易变内容在后，并且只在必要处追加，不重建。

③ 上下文策略三元组（P2 扩展）

DWC 的 context_mgmt 现在只有"留最近 2 轮 + 摘要"这一种硬编码形态。 借 trigger/selector/reposition 的形状，让它变成可进化的策略对象：

trigger   : 何时压缩（轮数？token 数？失败率？）
selector  : 压哪些（旧工具响应？证伪轮？重复读？）
reposition: 何时重整（压缩后是否重排位置/重建摘要）

④ 策略 RSI 作为 P4 的第三份佐证

这是连续第三篇论文指向同一个结论：

论文进化的对象相对人工设计的收益
HarnessProprompt / profile / 预算策略+2.0pp 且 −26.1% 成本
Harness²改进器本身（库）去掉库 −3.1 / −1.8
Cache Engineeringcache 策略比专家设计再省 7.1%

6.3 对 DWC 最扎心的一条

论文实测 trim = 1.85× 成本。DWC 的 compaction 是"留最近 2 轮 + 更早压成摘要"， 正好落在这个区间里。

也就是说：DWC 现在为了省上下文做的努力，可能正在让成本变高。
在 P0-a 的记账落地之前，这一点无法验证；落地之后必须立刻量一次： 开 compaction vs 关 compaction，哪个更贵。

6.4 落地顺序调整建议

阶段原内容本论文带来的补充
P0-atoken 记账加 cached_tokens 三档计价
P0-b输出压缩 + 原文落盘加前缀稳定性度量（公共前缀长度）
P1-a三段预算不变（提醒仍只能追加到 tool result）

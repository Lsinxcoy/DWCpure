## 二、★ 必须先挑明的矛盾

**Q1 把「架构/拓扑 (8)」放进可进化区，Q2 又把「架构 (8)」放进骨骼区 —— 同一个对象，两处判定相反。**

```text
Q1: 8 架构/拓扑  → 追加进"可进化"
Q2: 甲 = 判据+铁律+控制安全+SELF+★架构(8)  → 骨骼区禁进化
```

**这个矛盾不是你的疏忽，它反映了一个真实的设计难点。** 母巢的实现正好证明了这一点：

```python
# 母巢 evolution/arch_ops.py (P64) 原文
"""架构变异算子 (白名单制, 全可逆, 零生产影响).

白名单 (只做这 3 个, 其余一律拒绝):
  1. add_shadow_pipeline — 影子管注册进独立表, 不进 Nexus._pipelines
     (dispatch 不可达, 零生产影响).
  2. tag_mechanism_pipe — 机制管道归属标注 (纯标注, 不改执行).
  3. merge_report — 同义管道检测只出报告 (只记不合).

全部可逆: rollback() 清空本轮变异. 审计: journal[] 全记录.
"""
```

**母巢的解法：架构可进化，但只允许"影子操作"——三件事全是零生产影响、全可逆的。**

```text
add_shadow_pipeline  影子管注册到独立表, dispatch 不可达  ← 加了但不用
tag_mechanism_pipe   纯标注, 不改执行                     ← 记了但不影响
merge_report         只出报告, 绝不动手                   ← 说了但不做
```

**★ 即：母巢把"架构进化"做成了"架构提案 + 报告"，真实架构一行没动。**

## 三、矛盾的正解：架构分两层

用 ARSI 的分界线（`pillars.py` 原文）可以把矛盾解开：

```python
# ARSI/src/arsi/harness/pillars.py 原文
"organization=rho_iron_laws_sealed_goals"      组织 = ρ 铁律，冻结
"structure=omega_harness_host_policies"        结构 = Ω harness/宿主策略，可改
"stage3_may_change_structure_never_organization"
```

**套到"架构"上**：

```text
架构-组织层 (骨骼, Q2 禁)         架构-结构层 (血肉, Q1 可)
─────────────────────────────    ─────────────────────────────
器官的边界与契约                   器官内部的组装方式
  · 哪几个器官                       · 器官内部用什么数据结构
  · 器官之间谁能调谁                  · 器官内部的处理顺序
  · 事件总线的拓扑                    · 器官内部的参数传递路径
  · 铁律约束哪些器官                  · 模块内部的依赖方向
★ 改它 = 改系统的定义                ★ 改它 = 改实现, 不改定义

判据: 改完后 "DWC 还是不是 DWC"?    判据: 改完后功能等价, 只是做法变了
      变了 ⇒ 骨骼                          没变 ⇒ 血肉
```

**★ 正解**：

```text
Q1 的"架构 (8) 可进化" = 架构-结构层 (组装方式)
Q2 的"架构 (8) 骨骼"   = 架构-组织层 (器官边界/拓扑)

两者不矛盾, 是两个子对象。
建议把第 8 项拆成 8a / 8b:
  8a 架构-组织 (器官边界/拓扑)  → 骨骼区 (Q2)
  8b 架构-结构 (内部组装)        → 可进化 (Q1)
```

### 4.2 工具 (5) 的门

```text
载体: 工具定义 (code) —— 但有个前提

★ 前提: 工具必须由 DWC 自己实现。若工具由外部提供 (如 MCP server),
  则只有"工具选择策略"可进化, 工具本身不可。

门:
  ① 工具契约必须声明 (输入/输出 schema) —— 照母巢 tool_contract 八要素
  ② 替换工具不得破坏管线 (母巢 _pipe_contract_ok: 输入事件类型集合 == 输出)
  ③ 新工具必须先在影子期跑通, 才允许进生产工具表
```

### 4.3 架构-结构 (8b) 的门

```text
载体: 器官内部组装方式 (code)

★ 母巢的教训 (arch_ops.py): 它只允许三件事, 全是零生产影响
  add_shadow_pipeline / tag_mechanism_pipe / merge_report

门:
  ① 白名单制: 只允许声明的几种操作, 其余一律拒绝
  ② 全可逆: 必须有 rollback()
  ③ 审计: journal 全记录
  ④ ★ 不许碰器官边界 (那是 8a, 骨骼区)
  ⑤ ★ 影子期必须真跑 (母巢的问题是 @unwired, 从未接线)
```

### 4.4 智能体 (10) 的门

```text

  ③ ★ 不许改决策链的拓扑 (那是架构-组织)
```

### 4.5 评估器/奖励 (16) —— ★★ 与 Q2 直接冲突

```text
Q1 把 16 评估器/奖励 放进可进化
Q2 把 判据层(judge) 放进骨骼区

★ 这两处冲突, 必须区分"评估器的哪一部分"

ARSI 的实际做法 (实测):
  DIMENSIONS 里有 c6 = evaluation_and_reward   ← 可进化 (251/862 条 manifest 用它)
  FROZEN_DIMS = {"c7"} = control_and_safety    ← 冻结
  G10SealedProtection: sealed task content / scoring rules  ← 不可读不可改

★ ARSI 的分法:
  c6 evaluation_and_reward  可进化 —— 指"怎么评分/给奖励"的实现细节
  sealed 评分规则           不可改 —— 指"什么算对"的判定标准
  G10 保护: "Scoring rules must not be modifiable" (原文)

⇒ 正解同架构: 评估器也分两层
  16a 评分实现 (c6)      → 可进化 (Q1)
  16b 评分规则 (sealed)  → 骨骼区 (Q2)
```

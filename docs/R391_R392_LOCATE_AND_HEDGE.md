二、R391 根因：Windows 的 `find.exe` 抢在 GNU find 前面
════════════════════════════════════════════════════════════
实测：

    _do_action("run", {"cmd": ["find","src/dwc","-type","f","-name","*.py"]})
    → ok=False  rc=2  err="FIND: 参数格式不正确"

`C:\Windows\System32\find.exe` 只支持 `find "字符串" 文件` 语法，
模型写的 GNU 写法一律 rc=2。模型不知道原因，就**重试到复读熔断**。

修法：
· `_find_to_python()` —— `find PATH [-type f] [-name|-iname PAT]`
  一律转成等价的 Python `os.walk` 实现（不依赖 PATH 里哪个 find）
· 新增 `find_files` 原生工具（pattern / path / ignore_case）
· **系统提示**明确：
  - 「定位 X 定义在哪个文件」⇒ **第一步就 search_code(pattern='X')**，
    不要用 list_dir / ls 逐层翻目录（现场反复 `ls -la .` 11 轮零进展）
  - 不要直接用 `find`（会命中 Windows 的 find.exe）
· 顺手补齐：旧系统提示的工具清单里**漏了 search_code**
  （只列了 read_file/write_file/run_command/list_dir/final_answer）

三、R392 猜测检测改**句子级**
════════════════════════════════════════════════════════════
R389 的 `_hedge_block` 按**全文**扫描，自查发现系统性误杀：

    "我读了 README。定义在 src/dwc/llm/task_exec.py。
     另外配置项我不确定是否已启用。"
    ⇒ R389 判 ✗（答案是对的）

正确答案常带一句免责声明 ⇒ 通过率被系统性压低。

新语义：**只判"命中答案的那一句"是不是猜测**
· `_sentences()` 按中英文句末标点/换行切句
· `_match_sentences()` 找出命中句（contains/contains_any/
  contains_equiv/contains_all 按 needle；regex 按 match 位置）
· 命中句含猜测 ⇒ ✗；别的句有猜测 ⇒ 不影响
· 定位不到命中句 ⇒ 不判猜测（让"未命中"逻辑判 ✗）

对照：
  "可能是 task_exec.py"              ⇒ ✗（命中句猜测）
  "定义在 task_exec.py。别的不确定"   ⇒ ✓（命中句确证）
  "无法确认。不过可能是 task_exec.py" ⇒ ✗（命中句猜测）

五、诚实边界
════════════════════════════════════════════════════════════
1. **本轮尚未重跑全池** —— 55.6% 是 R390 的数字，P0/P1 的效果待测。
2. `find` 转换只支持 `-name/-iname/-type f`；`-size/-mtime/-exec`
   等高级用法会被忽略（可能给出比原命令更多的文件）。
3. 句子切分靠标点；模型写长句无标点时退化为整段判定（偏严）。
4. `_match_sentences` 对 `contains_all` 返回所有命中句 ——
   任一命中句含猜测即 ✗（可能偏严）。
5. code-locate 的根因可能不止 find：模型是否真的会"先 search_code"
   要看重跑结果。

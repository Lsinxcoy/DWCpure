## 门候选 · 按依赖标注

### 门 1 · 定位门

```text
          同一职责重复实现 → FAIL
```

### 门 2 · 真值门
**依赖架构**：需要先确定 DWC 的"真值"从哪来。

```text
候选判据  硬编码成功常量（return True / 恒定分数）→ FAIL
          判定能力须声明其真值源；无真值源 → 显式 UNKNOWN，不许写成功
```
> 依据扎实：`2607.12790` 实测塌缩评分器 0.811 > 认真 0.767。
> 但**真值源本身怎么设计**是架构问题，未定。

### 门 3 · 活性门
**依赖架构**：★★ **已裁决（2026-10-05 · 用户）: DWC 采用六层活性模型。**

```text
已定判据  "从未被调用"独立成类，不混入 stale
          活性逐层单调，弱判据不得越级
          六层齐备（present→registered→called→succeeded→produced_effect→feedback_closed）
```
> 六层来自 `2608.24876` 的 `Γ` trace 结构，是**一个可行方案**。
> ★★★ 2026-10-05 用户裁决：**采用**。此前"候选，不是必然"的措辞作废。
>
> ★★ 适用范围（裁决的落地细则，2026-10-05 补 · 依据 2608.24876 §5.1.2）
>   六层挂在 **`Γ` 事件上的机制/组件**，不是挂在 Python 文件上。
>   逐层点亮关系（论文原文给的映射）:
>     present       ← 文件 / 注册表
>     registered    ← 登记表
>     called        ← Γ 中出现调用事件
>     succeeded     ← 外部回执匹配
>     produced_effect ← 下游可观测产物
>     feedback_closed ← 回到判分器
>   ⇒⇒ ★ 这修正了 scripts/gate.py 的一个理解偏差:
>     它原按"src/dwc 的 .py 里出现这些字段名"来判定"采用"，
>     而正确口径是"Γ 的字段里有这六层"。两者恰好同名，但载体不同。
>   ⇒ ★ 配套硬要求（论文 Table 4 的启示）:
>     **Γ 必须记录"本应调用但未调用"**（负事件），
>     否则 DWC 会重犯母巢"调用失败看不出"的错 —— 母巢 `MechanismHealth`
>     只有 call_count/is_healthy/last_called 三字段，把"从未调用"塞进 stale。
>
> ★★★ 裁决的后果（诚实记录）:
>   采用 = 六层齐备成为**强制** ⇒ 而 DWC 目前**没有任何器官实现**，
>   `Γ` 尚未落地 ⇒ 六层是**已采纳但未实现**状态。
>   ⇒ scripts/gate.py 的 G3 因此需要一个第五种状态来表达这一点
>     （已采用未实现 ≠ 通过，也 ≠ 未采用）。见 gate.py 的 `adopted_not_implemented`。

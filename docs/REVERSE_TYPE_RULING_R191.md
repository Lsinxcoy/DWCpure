# REVERSE 类型裁决（R191 — 用户指令 "深度思考你认为REVERSE属于哪个类型"）

日期: 2026-10-12 · 前置: R188 实测 REVERSE 恒 0 候选（RULES 7 条无"更简单"类 target）

---

## 零、结论先行

**REVERSE = 类型一「简化 target」（回退到更简单的方案）；「回退到更弱验收」（类型二）应当被显式禁止。**

而且这个禁止**不是保守**——它有机器可判的三条依据（§3），加上一条本地库论文的**反例**（§2）说明类型二已被人试过且后果明确。

---

## 一、两个类型到底差什么

| | 类型一：**简化 target** | 类型二：**回退到更弱验收** |
|---|---|---|
| 动的对象 | **提案侧**（patch/RULES 中的修法） | **判据侧**（task spec 的 rung/验收强度） |
| 原文依据 | design 逐字「后退 (回退到更简单的方案)」——"方案" | 原文里**没有**；是我 R189 计划里自己举的例（"如降 verifier_rung"） |
| 语义方向 | 产出**更容易被接受**的候选 | 产出**更容易通过的验收标准** |
| 改完之后 | 门③⑥仍用**原**强度判 | 验收强度本身变低 |

**关键观察**：类型二根本不在 design 原文里。它是我在 `docs/R189B_TRAIN_SPLIT_PLAN.md` §2 自己写的一句"如降 verifier_rung / 简化 patch"——把两者的合谋写成了一个选项。这是"我发明的，不是设计的"，按 R73 纪律本身就该扣下。

---

## 二、本地库论文的**反例**（2603.25111 fallback —— 最像类型二的那个机制）

2603.25111 的 FGGM 七字段里有 `f_d` **fallback 非参数程序**。看它到底是什么：

```text
论文原话: "虽然 f_d 可能缺乏 GM 的解题能力（低任务性能），
          它阻止候选 agent 进入不安全的程序状态（高约束满足）"
实例: boundedParam 的 f_d(l,u,y) = min(max(l,y), u)   # clamp
```

**这个"退一步"退的是什么**：退的是**任务性能**（不会解题了），**不**退的是**约束**（Φ_l/Ψ_l 契约仍然成立）。

⇒ ⇒ **这正是 REVERSE 的正确形状**：候选能力可以退，**判据契约不能退**。
论文用 K=5 拒绝采样保契约、用 clamp 保区间——**每一步都在守同一个验证器**。

**若照类型二做（降 rung）**：等于让"拒绝采样器"自己改验收公式——2603.25111 整篇论文的存在意义就是反对这件事（性质② Parameter-Independent Correctness："契约对任意 θ 都成立"）。

## 三、机器可判的三条禁止依据（不是品味，是 DWC 已锁的纪律）

### ① 判据必须在系统外（G2 / TRUTH_SOURCE）

```text
judge.TRUTH_SOURCE = config/anchors/*.json
R189 刚抓的洞: train 条目带 label ⇒ 显式 raise（"变成第二个 dev"）
```

类型二 = 让**进化中的系统**修改自己的验收标准。这跟 R189-B 修的洞是**同一个病**
（系统碰判据面）——只是那个洞在数据面，这个洞在强度面。**已在测试里被 raise 的东西，
不能在另一个入口被绕过。**

### ② 「更弱验收下通过」会被门⑥（budget/信用）记成收益

进化闭环的账本（credit/ledgers）只认「落地了」这一个事实，不认"这次验收变松了"。⇒ 类型二会**污染 fitness**：松标准 +1 分，等于奖励放水。这是 fake-success 的经典形态。

### ③ dev/test split 分离纪律

R184 定的 train 无标签面、R161 的 ho 面，全建立在"验收标准不可被进化面改写"上。降 rung 从此不需要任何新机制就能让任务"变简单"——**e2e 数字会好看, 而它们不再意味着同一件事**。

## 四、那类型一在 DWC 真的可行吗——把 RULES 摊开看

```text
RULES 7 条:
  prompt × 4   →  patch = 答案文本（补关键词/补内容）
  control_flow × 3 →  patch = 代码片段（return sum(range(n+1)) 等）
```

"更简单的方案"在 DWC 的三种可能形态, 逐个判:

| 形态 | 是什么 | 可行? |
|---|---|---|
| **a. 简化 patch** | 同类修法里选更短的 | ✗ 退一步就修不好了（代码题修法只有对/错, 没有"半对"——`range(n)` vs `range(n+1)` 没有中间形态） |
| **b. 降 prompt 答案的信息量** | 答案写短一点 | ✗ keyword_match 是"关键词全含才过", 短=**丢关键词**=必然 fail。没有收益 |
| **c. 同 component 的备选修法** | 本 fn 无规则时, 借**同 component 更老/更弱**的规则 | △ **唯一有意义的形态**——但它已经在 R173 的 LATERAL 里了（propose_lateral 借同族 (c,q) 近亲 fn 的修法） |

⇒ ⇒ **诚实的结论: 在当前 7 条 RULES + 10 任务的判据面上, REVERSE 的"简化 target" 实际可行度为 0。**

这不是缺陷, 是**事实**——这个面上"后退"没有产物（代码修法只有对错, prompt 答案只有含不含）。
REVERSE 一旦被硬造候选, 就等于"为了填满三方向而生成注定 fail 的 patch", 违背 R73/R188 的
"None 是合法结果"纪律。

## 五、我的建议：REVERSE 落成「**已锁语义 + 表驱动登记位 + 禁用类型二**」

```text
direction.py 已有:
  REVERSE = "后退 (回退到更简单的方案)"     ← design 逐字, 不动
  reverse_candidates()                     ← R188 落的表驱动登记位

R191 新增（纯声明 + 测试, 零行为变更）:
  1. semantics 表里 REVERSE 的注释后追加**辨析段**:
     "更简单的方案 = 提案 patch/target 侧（能力的退一步, 2603.25111 的 f_d 形状）
      —— **不是**降 verifier_rung / 改 checks / 动判据面（2603.25111 性质②:
      契约对任意 θ 成立; DWC G2: 判据在系统外 ⇒ 类型二禁行）"
  2. 一个真测试锁死:
     test_reverse_type2_is_forbidden():
       - 构造"降 rung 的 REVERSE 候选" ⇒ 必须被拒（raise 或 [] 非候选）
       - 坏味道锁: 若有人给 direction.py 加 downgrade_rung / weaken_checks
         之类的钩子 ⇒ 测试红
  3. reverse_candidates 保持现状（RULES 无简化类 ⇒ []）
     —— 零候选是**如实输出**, 不是 backlog
```

### 为什么不"等将来 RULES 长了再说"

- 现在写死辨析 = 将来 RULES 长出简化类 target 时, 唯一入口（reverse_candidates）
  **已经被纪律标好边界**, 不会长歪
- 若现在不写, 类型二会从 `_dir_generate` 的 REVERSE 分支**自然长出来**
  （因为它太容易写——降个 rung 就能让任务"过"）

二、R388 · run-verify 必须有 **agent 侧证据**
════════════════════════════════════════════════════════════
旧实现（`scripts/dwc_bench2.py::verify`）：

    if t == "rc_and_contains":
        r = subprocess.run(check["cmd"], ...)      # ← 判据在跑
        ok = r.returncode == 0 and target in out   # ← 与 agent 无关
        return (ok, "rerun rc=%d" % r.returncode)

⇒ **agent 什么都不做，只要仓库里那套测试是绿的，就判 ✓**。

新语义（三重证据，全要满足）：

  ① `actions_log` 里有 `op == "run"` 的 obs 动作
  ② 该动作 `ok` 为真（真执行成功，不是失败的尝试）
  ③ 命令命中同一目标（用测试文件路径做 needle，允许
     `-q` / `-p no:randomly` / `--tb=short` 等参数变体）

判据自己重跑**降级为复核**（防止 agent 谎报），不再单独构成通过。
缺 `report` ⇒ 判 ✗ 并写明 `no-agent-evidence`（**禁止静默放行**）。
`allow_self_verify: true` 显式豁免，只用于自测判据本身。

调用方全部补传 `report`：
`dwc_nightbench.py` / `dwc_bench2.py` / `dwc_eval_awareness.py` /
`dwc_organ_ablation.py` / `reverify_eval.py`（后者从会话 jsonl 重建
`actions_log`，否则离线复核会全判 no-agent-evidence）。

三、R389 · 猜测不记功
════════════════════════════════════════════════════════════
现场（rf05，2026-10-20 全池）：

    问：DWC 记忆系统内核类名？
    答：抱歉，我目前没有关于 DWC 记忆系统内核类名的**可用取证信息**，
        无法给出确切的类名（例如**可能是** MemoryKernel…）
    判据：contains "MemoryKernel"  ⇒  ✓

模型自己都说没取证，判据却把"猜对了"当"找到了"。

修法（保守，避免误伤）：
· 统一前置门 `_hedge_block()` —— `contains` / `contains_any` /
  `contains_equiv` / `contains_all` / `regex` 五类全过这道门
· 命中明确的猜测/弃权措辞 ⇒ 判 ✗，how 记 `guess-credit-blocked`
· 措辞表只收**明确的**：「可能是/大概是/估计是/也许是/推测/猜测/
  无法确认/无法读取/没有取证/未能找到/不确定…」
· **"如果…则…"这类假设句不收**（太常见，会误杀正常答案）
· `allow_guess: true` 显式豁免（开放题允许推测）

五、诚实边界
════════════════════════════════════════════════════════════
1. **新语义下的全池通过率还没重跑** —— 70.4% 是旧判据的数字，
   新判据只会更低（run-verify 与部分 read-fact 会被收回）。
   下一轮必须重跑才能拿到**真实**基线。
2. `_HEDGE_PATTERNS` 是**黑名单**式检测，不是完备语义判断：
   模型换个说法（"据我推断"、"从上下文看应该是"）可能漏网。
3. `_agent_ran` 的 needle 匹配是子串式：理论上 agent 跑了
   `pytest tests/foo.py` 而判据要 `pytest tests/foo_bar.py` 时
   不会误配（文件名不同），但**同一文件不同用例**无法区分。
4. 猜测检测按**全文**扫描：一个长答案里只要出现一次"不确定"，
   即使主体是确证结论也会被判 ✗（偏严，宁可错杀）。
5. run-verify 的真实能力仍未知 —— 新判据下可能远低于 100%。

二、根因：R391 的 find→python 转换与 R386 白名单冲突
════════════════════════════════════════════════════════════
R386 给 qa_mode 开了只读白名单（`READONLY_CMDS` = grep/ls/find/…）。
R391 把 `find` 转成 `python -c <os.walk 脚本>` 后，**首 token 变成
`python.exe`** —— 不在白名单 ⇒ `_is_readonly_run()` 判 False
⇒ qa_mode 的 R5 硬约束直接拦。

即：**修 A 打破了 B**（典型回归，靠全池跑批才暴露）。

════════════════════════════════════════════════════════════
三、修法：工具层生成的 step 自带 `readonly: True`
════════════════════════════════════════════════════════════
· `list_dir` / `search_code` / `find_files` 三个工具构造的 step
  一律带 `readonly: True`
· `step_judge._is_readonly_run()` 首先认这个标记
· **`run_command` 不带该标记** —— 模型手写的命令仍走白名单判定，
  不能借 run_command 绕过 qa_mode 的写保护

为什么这个标记是安全的：
  这三个 step 由 `_tool_calls_to_step()` **构造**（不是模型拼的字符串），
  参数是结构化字段（pattern / path），命令模板由代码固定。

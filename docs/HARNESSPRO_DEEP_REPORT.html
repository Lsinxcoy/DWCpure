0 · 一句话结论

能学，而且学到的东西正好戳中 DWC 现在最缺的那一块： DWC 的进化系统只会优化「过不过」，HarnessPro 把「花多少钱」变成与通过率并列的一等目标， 并给出了一个可落地的三段式运行时预算机制。
但它不是"再做一个 R438"：它的仓库不含进化管线（只有最终产物 + 评测 runner）， 核心方法不可复现；而且它的多候选 × 多 epoch 预算，DWC 现在跑不起。

2 · 方法拆解

2.1 优化目标（式 1）

min  ( −PR(h),  C(h) )
h∈H
s.t. PR(h) ≥ PR(h₀)        ← 性能地板，不许为了省钱牺牲正确性

两个目标：通过率 PR、平均每任务成本 C。延迟只作辅助指标（服务器负载波动大）。

2.2 一轮的三段式（Algorithm 1）

阶段做什么关键细节
Stage 1 · 诊断每个候选 × 每题跑 G=3 次独立 rollout，Analyzer 联合看 3 条轨迹 输出三元组：问题 / 对性能与成本的影响 / 证据（文件名 + 行号区间）。跨题合并后 >64K token 就摘要
Stage 2 · 起草每个候选 × 3 个计划（I1 省钱 / I2 平衡 / I3 性能），Editor 在独立 workspace 实现并 git commit Planner 能看到候选间 diff，识别"哪个机制有效、哪个是剩余瓶颈"；验证/测试集对它隐藏
Stage 3 · 评估与选择固定测试集 S(x) 上评一遍 → 过滤（低于地板 / 被 Pareto 支配）→ 三档选代表 最多留 3 个；只用验证集指标，测试集全程不碰

2.3 选择规则（式 8–9）

d_perf(h) = (P_max − PR(h)) / (P_max − P_min)
d_cost(h) = (C(h) − C_min) / (C_max − C_min)
J_m(h)    = α_m · d_perf² + β_m · d_cost²

(lite, medium, heavy) 的 (α, β) = (1,2) / (1,1) / (2,1)

本质是归一化后的加权欧氏距离——先把两个量纲不同的指标压到 [0,1]，再按部署偏好加权。 比"取 top-k"更稳：不会被某一个指标的绝对尺度主导。

2.5 进化后的 harness 长什么样（§5.3）

论文明确否认了"靠压上下文或提高推理力度"的简单解释，实际机制是四件事的协同：

  • 按任务描述选 profile：每个 profile 指定推理力度 + 工具调用预算
  • 运行时 hook 强制预算：Medium 在 TB2 上是「14 次提醒并行、26 次收敛、44 次阻断」
  • 提醒追加到工具结果，不改 system prompt —— 保住 cache 前缀
  • 工具输出压缩（RTK）+ 精简指令，减少重复日志与冗余输入

4.3 hook.py 的实际强制逻辑

PreToolUse:
  count = _increment_tool_count(control_state)      # 文件计数，跨进程
  if count > finalize_after_tools:
      → permissionDecision = "deny"                  # 硬阻断
  ctx = _stage_context(count, selection)             # economy / strict 提醒
  updated_input = _rtk_rewrite(payload) if Bash      # 命令改写
  → additionalContext = ctx                          # 追加，不改 system prompt

PostToolUse:
  if len(output) > max_chars:
      raw 原文写 .rho_runtime/raw/.json   # ★ 可回溯
      compact = head(2400) + tail(900)
      注入提示 "Full raw result: . Read only a targeted range..."
这段代码是整篇论文最值得直接抄的部分。三个设计决定都很硬： (1) 计数落文件而非内存 → 跨 hook 进程可用； (2) 提醒走 additionalContext 追加，不重写前缀 → prompt cache 不失效； (3) 截断但原文落盘 + 给出路径 → 需要细节时可定向回读，不是真的丢信息。

6 · DWC 能学到什么（核心）

6.1 先说结论：HarnessPro 的 harness 定义 ≈ DWC 的 R438 十九对象

HarnessPro 的 harness 组成DWC R438 对应维度状态
instructionsprompt（manifest + A/B）已落地
tools & skillsclient_tool / skill已落地
context & memorymemory / context_mgmt已落地
hookscontrol_flow半具备
verification policiesevaluator（只读）只读
cost无缺失

结构上 DWC 比 HarnessPro 更细（19 个对象 vs 5 类），但少了一个正交维度：成本。 这不是"少一个功能"，而是少一个目标函数——只有一个目标时，Pareto 无从谈起。

6.2 六条可借鉴项（按性价比排序）

① 加 token 记账（前置条件，必须先做）

项内容
DWC 现状LLMClient 不解析 usage；生产日志的 cost 字段是评分不是钱；全库 grep total_tokens 零命中
借鉴每次 complete() 记录 prompt_tokens / completion_tokens / cached_tokens，按模型价目折算
落点src/dwc/llm/client.py 的 LLMResult 加字段 → var/task_scores.jsonl 加列
成本小（~50 行 + 一处写盘）
价值极高：没有它，后面五条全都做不了；也是"热力学智能"里 I_δ 量化的数据基础

② 三段式工具预算 + 阶段提醒（最可直接抄）

项内容
DWC 现状NATIVE_TOOLS_MAX_ROUNDS = 15 硬上限；max_rounds=999（JSON 路径）；全程无阶段提示
借鉴economy(提醒省着用) → strict(停止发散) → finalize(硬阻断)，按任务复杂度选档
落点task_exec.py 的原生工具循环（for rnd in range(1, max_rounds+1) 附近）
成本小（~80 行）；不引入新依赖
红线提醒必须追加到 tool result，不能改 system prompt —— 否则 cache 前缀失效，反而更贵

③ 工具输出压缩 + 原文落盘

项内容
DWC 现状read_default_lines=200 / output_max_chars —— 截断即丢失，模型想看全文只能重读
借鉴head 2400 + tail 900，原文写 var/tool_raw/<id>.json，提示"需要细节读该路径的指定区间"
落点task_exec.py 的 _cap_answer / 工具返回处
成本小（~40 行）

④ 按任务特征路由 profile（而非全局 reasoning_effort）

项内容
DWC 现状reasoning_effort 是全局配置（生产 none）；R411 实测"档位越高越差"，于是干脆全关
借鉴不是"全局开高"，而是按任务选档：简单题 low + 小预算，难题 high + 大预算
落点LLMExecutorFactory（已按 anchor 类型路由 9 个 behavior）→ 扩展为"类型 + 复杂度"双维路由
成本中（需要分类器 + 评测验证）
注意论文消融证明：只加路由不加预算 hook，会掉分（RHO+动态路由 80.0→76.0）。必须成对引入

⑤ 三档 Pareto 输出（lite / medium / heavy）

项内容
DWC 现状每轮 auto_apply_max_per_round: 1，只落一条规则；没有"多档策略"概念
借鉴同一轮产出 3 套 profile 参数（省钱/平衡/性能），部署时按预算选
前提必须先有 ①（成本指标）；否则三档没有可比较的第二维
成本中高
优先级P2 先把 ①③ 做完再谈

⑥ 用"固定测试集"替代 LLM 自评（论文已给出反例）

项内容
DWC 现状judge 产出 llm_asserted:%r；trial 用 obs_skeleton（真实观测值）——这一半已经比论文强
借鉴把 judge 的"我认为失败"换成"用固定用例复现失败"；不能复现的签名不进候选（DWC 已有 filtered_nonreproducible=2093）
判断这条 DWC 已经做对了一半：2093 条不可复现签名被正确挡在候选之外。剩下要改的是 judge 自身的 llm_asserted 措辞

6.3 明确不该照搬的四条（红线）

不要抄为什么
多候选并行（每轮 3 计划 × G=3 rollout）DWC 日预算 96 次 / 80 分；论文一轮就是 10 题 × 3 rollout × 3 候选 = 90 次调用，一轮吃光一天
label-free（放弃 ground truth）DWC 有真实评测池（池 A 53/54 = 98.1%），主动放弃真值是倒退。论文是被迫 label-free（官方测试不可见）
全 harness 重写论文允许 Editor 改任意组件；DWC 的 19 对象已按维度隔离，全放开会破坏结构完整性（你反复强调过的）
用 CoP 当唯一 fitnessCoP = 总成本 ÷ 成功数，成功数为 0 时发散；DWC 现在的失败样本少，这个指标会噪声爆炸

6.4 建议的落地顺序

阶段动作前置预计
P0① token 记账 + 成本字段进 task_scores.jsonl无1 轮
P0③ 工具输出压缩 + 原文落盘无1 轮
P1② 三段式预算 + 阶段提醒（先用固定档，不接分类器）① 有数据可对比1–2 轮
P1把 cost 进 fitness，作为与 pass_rate 并列的第二目标①1 轮
P2④ 任务特征 → profile 路由（必须先有 ②）② + 分类器评测2–3 轮
P3⑤ 三档 Pareto 选择①④ + 足够样本量3+ 轮
最省力、最高回报的一步是 ①+③，一轮能做完，且立刻让 DWC 从"只有一个目标"变成"有两个目标"。 ② 是第二步，也是论文里最可直接抄的代码（hook.py 396 行，纯 stdlib）。
